Веди операции на явно указанном LAN-стенде по общему ранбуку
`.claude/skills/dev-deploy/SKILL.md`. Запрос о 404/502 — диагностика чтением.
Для выкладки нужно поручение обновить dev, для локальной сборки — собрать.

## Перед сборкой или выкладкой

- Проверь основной frontend checkout, ветку `main` и `git status --short`.
  `build-dev.sh` экспортирует рабочие файлы. Убедись, что чужие правки не попадут в сборку.
- Проверь процессы и локи по `docs/WORKFLOW_OPERATIONS.md` §3.4. У dev-скрипта нет
  собственного лока, а `clean_all` удаляет общие `node_modules` и `dist` даже в режиме
  `DEPLOY=0`. На время работы пометь операцию в `.codex-temp/ops/`.
- Проверь наличие `.env.dev` без вывода значений. Скрипт копирует его поверх `.env`;
  сохрани нужное локальное состояние приватно и восстанови по завершении.
  Node и GNU rsync выбирает `scripts/use-node.sh` внутри скрипта.
- Только для выкладки проверь SSH, состояние compose и HTTP baseline из ранбука.
  Запиши маршрут изменённого сценария и состояние зависимого API до запуска.

## Выполнение и отказ

Выбери одну команду из ранбука по цели. Отдельную полную сборку перед обычной
выкладкой запускать незачем — выкладка сама собирает приложение.

`deploy_dev` сначала передаёт экспорт во временный каталог на сервере, затем заменяет
`static/dist` и перезапускает `app` и `nginx`. Замена каталога состоит из двух
операций. Прерывание между ними оставляет пустой корень раздачи. При ошибке
сохрани стадию и проверь HTTP/состояние контейнеров чтением. Предыдущий каталог
скрипт не сохраняет; для разрешённого отката требуется сборка прежней рабочей
ревизии тем же проектным путём. Миграции, изменения compose, mount и Nginx
относятся к владельцу backend.

## Результат

Для сборки укажи ревизию, состояние дерева и наличие `dist/dev/index.html`.
Для выкладки сообщи команду, время, результат baseline и повторных проб нужных
маршрутов, включая сценарий изменения. Непроверенный пункт отметь точной причиной.
Для диагностики сообщи наблюдаемый сбой и владельца следующего действия.
