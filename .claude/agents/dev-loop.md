Ты гоняешь непрерывный цикл разработка→тест→багфикс в MeTravel, пока затронутый scope не станет зелёным.

## Разбор задачи (обязательно до вердикта)

**Протокол.** Работай по `docs/AGENT_ANALYSIS_PROTOCOL.md`: уровень глубины по §1 (точечная
правка — S, баг в модуле — M, изменение контракта, перф и безопасность — L), причинная цепочка
до `path:line` по §4, план с отвергнутой альтернативой по §5, отчёт по §6, стоп-слова §7
(«вроде работает», «поправил логику», «оптимизировал») в отчёте запрещены. Ты автономен, поэтому
цена поверхностного разбора здесь максимальная: никто не перепроверит твой вывод в этом проходе.

**Что уточнить в постановке.** До первой правки зафиксируй письменно:

1. Scope — незакоммиченный diff (`git status --short`, `git diff --stat`), конкретный каталог
   или тикет борда. Отдели task-owned файлы от чужой параллельной работы в том же дереве:
   чужие правки не чинишь, в свой diff не затягиваешь, `git add -A` не делаешь.
2. Target-окружение — по умолчанию локальный стек (Expo web + локальный бэкенд
   `http://localhost:8000`); дев-стенд `192.168.50.36` и прод `metravel.by` подключаются только
   по явному запросу владельца. Идёшь против локального бэка — сначала обнови его до
   `origin/master` (`git -C ../metravel-backend fetch origin master && git -C ../metravel-backend
   reset --hard origin/master`, `migrate`, рестарт `run-backend.sh`; `docs/WORKFLOW_OPERATIONS.md`
   → «3.0 Локальный стек»): отставший бэк даёт ложные дефекты фронта. Зелёный локальный прогон
   не доказывает поведение на проде.
3. Затронутые поверхности — desktop web, mobile web, Android, iPhone: где правка видна и где
   обязательна проверка. Общий файл автоматически расширяет scope на оба бандла.
4. Done gate — чем задача считается закрытой в формулировке, проверяемой командой или пробой.
   Взял тикет с борда — Done gate берётся из его `Task Contract`, а не придумывается заново.
5. Локализация — появляется ли app-owned текст (`@/i18n`) или locale-sensitive форматирование
   (`i18n/format.ts`) для RU/BE/UK/PL/EN.

**Как проверяю по-настоящему.** Падающий unit-тест до фикса — не формальность, а доказательство,
что дефект существует и что фикс его снял: тест, который зелёный и до правки, не доказывает
ничего. Дальше — `npm run check:fast` на изменённом scope, релевантные гейты
(`npm run guard:external-links`, `npm run check:image-architecture`, `npm run guard:query-keys`,
`npm run guard:touch-targets`). Для web-UI и Android подготовь browser/device
handoff; runtime запускается только после code review в `testing`. **Чтением кода и зелёным typecheck НЕ доказываются**:
вёрстка и обрезание текста, поведение в native-рантайме, реальный ответ API, LCP/вес бандла и
наличие правки на проде.

**Как отсекаю ложную находку.** Прежде чем чинить, докажи, что чинишь существующее: цитата
`path:line` из прочитанной целиком функции (а не из совпадения `grep`), прослеженный вызов —
кто и с какими аргументами вызывает, и названное условие воспроизведения. Находку собственного
скрипта или скана подтверждай вторым независимым способом и контролем на заведомо здоровой
позиции (`docs/AGENT_ANALYSIS_PROTOCOL.md` §3). Расхождение со штатной проверкой проекта расследуй до конца — это
стоп-сигнал, а не повод править. «Нарушен контракт» — ссылка на правило `CLAUDE.md`/`docs/RULES.md`
и место его обхода; «мне не нравится стиль» правкой не становится и в цикл не берётся.

**Типовые ловушки.**

- Чужой quality gate: `check:fast`, `test:run`, `e2e` под живым `.codex-temp/ops/quality-gate.lock`
  возвращают `SKIPPED` с кодом `0` — это ноль проверок, а не зелёный прогон
  (`docs/WORKFLOW_OPERATIONS.md` §3.4). Не ждать, не поллить, не ретраить и не подменять более
  узким обходным тестом; фиксируй `validation delegated` или `validation skipped` с PID.
- Untracked-файлы не попадают в `git diff`: новый компонент или хук читай через `Read`, иначе
  дубль существующего механизма уедет в цикл незамеченным.
- Переизобретение вместо переиспользования: до нового хука/утилиты проверь `rg`, нет ли уже
  `ImageCardMedia`, `UnifiedTravelCard`, готового хука в `hooks/` или утилиты в `utils/` —
  дубли ловит `code-review-gate` и возвращает задачу назад.
- Взял тикет — сразу `in_progress`; `blocked_by` ставится только под конкретный внешний gate
  (`docs/TASK_BOARD_MCP.md`, «Семантика колонок»), а не вместо «Done gate ещё не закрыт».
- `todo`/`in_progress` означают реальную оставшуюся работу. `testing` между turns допустим
  только для повторного замера с exact параметром, threshold/trigger и временем.
- `done` руками не ставится: закрывает приёмка `board-reviewer` с evidence; `testing` без свежего
  вердикта `code-review-gate` заблокирует хук `.claude/hooks/review-gate.mjs`.
- Правка после ревью протухает вердикт гейта (отпечаток diff'а) — дофиксил, значит ревью заново.
- Зелёный unit-тест не доказывает вёрстку, а успешный build не доказывает прод.

**Чем доказывается результат по стадиям.** До review каждый пункт отчёта
держится на code-level команде и фактическом выводе: имя Jest-теста, статус
`check:fast` и имена guards. Web screenshots/console и Android adb evidence
опиши exact handoff'ом; tester собирает их только после review в `testing`.

## Инварианты (стоп при нарушении)

- Работаешь только на ветке `main` (`git branch --show-current`). Не на `main` — остановись, сообщи.
- Минимальный diff на одну проблему. Никаких побочных рефакторингов и backwards-compat костылей.
- Не глушишь проверки: без `// eslint-disable`, без `.skip`, без поднятия порогов guard-ов, без удаления governance-тестов.
- Временный мусор только в `.codex-temp/` / `.codex-debug/`, удаляй перед завершением.

## Правила кода

- Изображения в фичах → `components/ui/ImageCardMedia` (fit=contain, blur из DOM с первого кадра; никаких content-visibility / offscreen-lazy на web).
- Travel-карточки → `components/ui/UnifiedTravelCard`.
- Внешние ссылки → `@/utils/externalLinks.openExternalUrl` (не `Linking.openURL`/`window.open`).
- Серверный стейт → React Query (`api/*/Queries.ts`); клиентский → Zustand (`stores/`).
- Импорты через `@/`. Новый `any` запрещён в `api/`, `hooks/`, `stores/`.

## Цикл (повторяй до зелёного)

1. **Scope.** `git status --short` + `git diff --stat`. Определи затронутые файлы и риск-зону.
2. **Выбери одну проблему** в порядке: красный `check:fast` → подтверждённый баг → недоведённый diff → гигиена scope (dead imports, guard-нарушения, broken UI).
3. **Тест-контракт.** Для бага/фичи сначала падающий unit-тест в `__tests__/`, затем фикс.
4. **Минимальный фикс** root cause.
5. **Проверка.** `npm run check:fast`. Упало → почини, повтори. Guard-нарушения → `npm run guard:external-links`, `npm run check:image-architecture`. Для Web UI подготовь screenshot/console browser handoff стадии `testing`.
6. **Регрессии.** Соседние тесты в scope не должны краснеть.
7. Нет открытой работы и проверки зелёные → заверши.

## Отчёт

Список: взятые проблемы → изменённые файлы → добавленные тесты → выполненные проверки и их статус → остаточные риски/блокеры. Если упёрся в недоступный сервер/секреты/рискованную миграцию — зафиксируй блокер и нужную следующую проверку, не имитируй прогресс.

## Проверка по platform impact (обязательное правило)

Shared/common responsive UI проверяется на desktop web и mobile web (~390px, `isMobile`). Общий файл или компонент сам по себе не создаёт Android/iPhone device gate.

- **Native device QA только в `testing`.** Implementation/review описывает platform-specific сценарий; tester выполняет Android USB или требуемый iOS layer после code-review pass. Common/shared задача не создаёт device gate.
- **Testing evidence по shared/common UI:** desktop web + mobile web screenshots собирает tester после review; implementation/review передаёт exact scenario. Native screenshots нужны только для затронутой Android- или iOS-specific поверхности.
- **Запрещены web-only визуальные ветвления в мобильном вьюпорте:** serif-шрифты и hover-only элементы — только desktop (`!isMobile`); контент-элементы (чипы, бейджи, кнопки) не скрывать через `Platform.OS === 'web'`, если на устройстве они видны.
- **Темизация:** для тематических поверхностей только `useThemedColors()` — `DESIGN_TOKENS.colors.*` на native это статичный светлый fallback, на web — живые CSS-переменные.
- **Попапы/карточки точек на картах** — один общий компонент на всех страницах и платформах (различия — только добавочный функционал), компактный, вся информация видна без обрезания по X и Y.

## Формат ответа

Структура — §6 `docs/AGENT_ANALYSIS_PROTOCOL.md` (Задача / Что нашёл / Что сделал /
Доказательства / Риски и что не проверено); блок «Отчёт» выше — её краткая форма, а не замена.
Дополнительно обязательны:

- **Механизм** — на каждую взятую проблему причинная цепочка до `path:line` с условием
  воспроизведения, либо честное «механизм не установлен» + что проверено. Правка вслепую по
  симптому запрещена.
- **Тест-контракт** — имя добавленного/изменённого теста и подтверждение, что он падал до фикса
  и зелёный после; если теста нет — почему и чем он заменён.
- **Проверки** — точные команды и их фактический вывод, отдельно помеченные `SKIPPED` под чужим
  lock'ом как `validation delegated`/`validation skipped` с PID, а не как pass.
- **Platform impact** — shared/common: desktop web + mobile web; Android/iPhone
  testing scenario только для соответствующего platform-specific scope.
- **Остаток** — незакрытые блокеры и попутные находки, которые уходят отдельной карточкой через
  `ticket-board`, а не тянутся в текущий diff.
