# Правка живой статьи: рецепты записи

Читается в режимах «обогащение», «дневник», «правки от instagram-researcher».
Движок `metravel_publish.py` здесь не используется — тело пишется
`scripts/seo-edit.js`, медиа — `POST /api/upload` (`photo-pipeline.md`).

## Дневник владельца без папки фото

Ссылка на статью + заметки (дневник, сторис, текст к видео, Garmin км/+/−,
цены, гостиницы) — папку фото не требовать, EXIF не запускать.

1. `GET /api/travels/{id}/`; автор не 1 (`userIds`) — стоп.
2. Выгрузить `description`, прочитать целиком, пройти `audit-table.md`.
3. Сопоставить заметки с разделами/днями/фото и вставлять ПО КОНТЕКСТУ: абзац
   рядом с днём и кадром, не валом в конец и не отдельным «Дневник»/«Наши впечатления».
4. Личные факты — только из заметок; история места — проверяемые факты рядом с
   её фото. Не сочинять того, чего нет в заметках, статье или на кадре.
5. Цифры дней (км, набор/спуск, цены) — в абзаце дня и одним набором в «Если
   соберётесь», без противоречий между вступлением и хвостом.
6. Существующие `<img>`/`<iframe>` не трогать без просьбы (байт-дубли и
   `address-image` — исключение, это дефект).

## Правки от instagram-researcher (`article-edits.md`)

Файл пакета поста: для каждой правки — цитата текущего фрагмента, замена,
источник. Применять без отдельного «да» (ядро, правило 4, решение 19.10.2026):
найти цитату в теле дословно (нет — правку не применять, отметить в отчёте),
заменить, источник проверить. Разрешено: ошибки, устаревшие и уточнённые
факты (и внутри авторского абзаца — опыт остаётся с годом), структура и
разметка по жанру 2d, понятность, проверенные полезные данные. Рассказ о нас —
впечатления, события, эмоции, оценки и порядок дня — не меняется: такую правку
отклонить с причиной.

## Запись тела

```bash
node scripts/seo-edit.js --id <ID> --desc-file full.html --dry-run   # сначала так
node scripts/seo-edit.js --id <ID> --desc-file full.html
node scripts/seo-edit.js --restore <ID>                              # откат из бэкапа
```

`seo-edit` делает бэкап в `scripts/.seo-backups/`, PUT, re-GET и авто-откат при
регрессии; меняет только `description` (и `meta_description` с `--meta`),
название/slug не трогает, авторство сохраняет. Для контекстной перестановки
собирать ПОЛНОЕ тело и писать `--desc-file`; `--prepend-file`/`--append-file` —
только для лида и действительно финальных блоков: `--prepend-file` поверх
готового лида даёт два определяющих абзаца.

`--meta`: лимит 255 символов; длиннее — 400 на весь upsert, и тело тоже не
записано. `--dry-run` этого не ловит. Сниппет в поиске мета НЕ меняет: SSG берёт
`stripHtmlToSnippet(description, 160)` — сниппет чинится первым абзацем тела.

## Поля вне тела: `plus`/`minus`/`recommendation`/`youtube_link`

Один путь — `buildUpsertPayload` из `scripts/seo-edit.js`: пустое поле уходит
`null` (API отвергает пустую строку и хранит `null`), сентинел
`__draft_placeholder__` не пишется; встреченный сентинел заменить текстом или `null`.

```js
const { buildUpsertPayload } = require('./scripts/seo-edit.js');
const { bodyMaintenanceSession } = require('./scripts/lib/metravel-tool-session');
const d = await (await fetch(`https://metravel.by/api/travels/${ID}/`)).json();
const payload = buildUpsertPayload(d, { plus: '<ul><li>…</li></ul>' });
if (payload.youtube_link === '__draft_placeholder__') payload.youtube_link = null;
await bodyMaintenanceSession().request('/api/travels/upsert/', { method: 'PUT', json: payload });
```

## Имена точек (`travelAddress[].address`)

Имя видно на карте, в списке точек и под фото точки; геокодер оставляет
«Krakowska 149», «964», «S7», одно имя на нескольких точках. При любой правке:

- имя = что за место, по-русски, оригинал в скобках, если нужен для поиска:
  «Парковка у трассы S7 (Pcim)», «Второе Рогачское озеро (Roháčske plesá)»;
- без улиц, номеров домов, кодов дорог в качестве имени (код — только ориентир
  внутри описательного имени); без дублей в статье;
- имя совпадает с тем, как место названо в тексте, и подходит к фото точки
  (`travelImageThumbUrl` открыть Read'ом); категория проверяется тем же проходом.

```js
const payload = buildUpsertPayload(d, {});
const rename = { 16243: 'Парковка у трассы S7 (Pcim)' };   // id точки → имя
payload.coordsMeTravel = payload.coordsMeTravel.map(p => rename[p.id] ? { ...p, address: rename[p.id] } : p);
await bodyMaintenanceSession().request('/api/travels/upsert/', { method: 'PUT', json: payload });
```

Ids сохраняются — фото точек не теряются (`_process_travel_coordinates` в
бэкенде обновляет `address`, `image` без изменений не трогает). Точку с
`id: null` не слать — это пересоздание без фото. Re-GET: тот же набор ids,
прежние `travelImageThumbUrl`, новые имена.

## Дата статьи и точность даты поездки

Контракт: `docs/features/article.md` → «Точность даты поездки и приёмка автора 1».
Каталог сортирует по `created_at` (#1995); у старых записей это могло быть время
создания, а поездка была известна только до года/месяца. Совпадение этих полей
не обязательно. Тип статьи на это не влияет (уточнение владельца 26.10.2026).

1. Нет достоверного дня поездки — сохранить существующие `year`, `month` и
   `created_at`. Не подставлять первое число месяца и не заполнять месяц ради гейта.
2. Есть точный день из EXIF или текста и поставлена задача поправить дату —
   `payload.created_at = '<YYYY-MM-DD>T12:00:00Z'`, затем re-GET байт-в-байт.
   Будущая дата не допускается; `year/month` не подгоняются автоматически.
3. `article-acceptance-check` проверяет заданную дату на корректность и будущее,
   принимает старые записи без точной даты и не требует непустого `month`.

## Типовые отказы

- правка ушла в API, но краулер видит старую статику до выката; новая статья
  или смена `name` отдаёт 404 + noindex до ближайшего выката (а смена `name`
  меняет slug — без 301 не делать);
- SSG-санитайзер когда-то клампил тело (`SEO-SNIPPET-001`) — после выката
  проверять, что хвост («Что рядом», FAQ) есть в статике;
- статья, которой нет в выводе `seo:audit --user-id 1`, — не «чужая», а без
  flagged-проблем; автора смотреть только в `GET` (`userIds`);
- статья создана токеном QA104 — авторство PATCH'ем не меняется, нужен
  `DELETE` и пересоздание токеном owner1.
