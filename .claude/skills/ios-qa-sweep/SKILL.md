# iOS QA Sweep — план → тест → борд → фикс → верификация

Сначала примени `docs/TESTING.md` → «Validation selection gate», до чтения native
runbook и environment/stamp/build. Если назначение iOS опирается только на старый
перечень платформ, верни исполнителю уточнённую матрицу без подготовки симулятора;
текущий явный iOS/capability/release-запрос сохраняется.

Зеркало `/android-qa-sweep` для iPhone. Универсальные правила оценки (целостность
вёрстки, закрываемость оверлеев, все состояния компонента, z-order) не дублируются
— читай их в `.claude/skills/android-qa-sweep/SKILL.md`, пункты 9–12 чеклиста, и
применяй один в один.

## Автоматизация до ручного обхода

Следуй `docs/TESTING.md` → `Native scenario automation and recording readiness`:
tracked Maestro-сценарии с bounded waits и business assertions на iOS simulator,
XCTest helper только для физического Apple device. Выбирай suite по Task Contract,
не расширяй его до всех экранов и пяти локалей для точечной задачи. Идентичность
app/source/backend/locale/account/runner входит в результат; smoke не означает
полное покрытие. Новый продуктовый баг получает failing regression, затем
implementation → review → retest. Запись готового сценария начинается только
после passing suite; во время capture не исследуй UI. После двух одинаковых
operational failures сообщи exact unblock и сохрани checkpoint.

## Предусловия

1. Окружение: `npm run ios:environment:check` — Xcode/SDK, пригодный iPhone-симулятор,
   состояние Pods. Красное чинится до обхода, а не обходится.
2. Панель симулятора: `mcp__Claude_Code_iOS_Simulator__control` → `attach` перед прогоном,
   чтобы владелец видел прогон. Скриншоты и ввод работают и без панели.
3. Кандидат: переиспользуй подготовленную совместимую dev/debug сборку и проверь
   её app/source/backend identity и обязательный native stamp по
   `docs/WORKFLOW_OPERATIONS.md`. Только при необходимом mismatch выбранного
   candidate выполняется одна local Debug build/install через operation gate.
   Подписанные `preview`/`production` профили для QA не собираются — они за
   отдельным разрешением владельца (`/ios-release`).
4. API-гейт: таргет по умолчанию — локальный бэк (`http://localhost:8000`), и он обязан быть
   обновлён до `origin/master` перед прогоном (`docs/WORKFLOW_OPERATIONS.md` → «3.0 Локальный
   стек»): `git -C ../metravel-backend fetch origin master && git -C ../metravel-backend reset
   --hard origin/master`, затем `bash /Users/juliasavran/Sites/metravel/run-backend.sh`.
   Симулятор ходит на `localhost` как и мак; физическое устройство — на LAN-IP мака с
   `EXPO_PUBLIC_IS_LOCAL_API=true`. Бэк не поднят или отстал — приложение покажет **пустоту
   везде** или ложные дефекты по старому API, и это легко принять за UI-баг. Прод-API
   подключается временной правкой `.env` только по явному запросу владельца, с обязательным
   возвратом файла; проверь, что `build-prod.sh` не оставил там прод-URL. `EXPO_PUBLIC_*`
   инлайнятся при сборке, поэтому нужен рестарт Metro `--clear`.
5. Логин e2e-аккаунтом разрешён постоянно (переспрашивать — ошибка), креды в `.env.e2e`.
   Пароль в поля не набирается: токен кладётся программно. На симуляторе это делается через
   dev-сборку; в TestFlight-сборке инжекции нет — там нужен один ручной вход владельца, и
   это не повод блокировать обход, а строка в отчёте.

## Что симулятор НЕ доказывает

Не помечай пройденным на симуляторе и выноси в раздел «нужен физический iPhone»:
камера, фото-библиотека и HEIC, реальная геолокация, sharing во внешние приложения,
Keychain и сессия после холодного рестарта, биометрия, permission allow/deny/restricted,
lifecycle, Universal Links из внешних приложений, APNs, поведение подписанной сборки
и производительность (список — `docs/WORKFLOW_OPERATIONS.md`).
**Safe area, клавиатуру и геометрию окна iPad симулятор доказывает** — их проверяешь здесь
и помечаешь пройденными, на устройство не переносишь. Приёмка релиз-кандидата — только exact
processed TestFlight build. Физическим iPhone и TestFlight-слоем владеет `ios-tester`,
драйвить их этим скиллом нельзя; регламент живого устройства —
`.claude/skills/ios-device-qa/SKILL.md`.

## Инструменты

`mcp__Claude_Code_iOS_Simulator__control`:

- `attach` — панель для владельца; `launch` — установка и запуск собранного `.app`;
- `screenshot` — снимок экрана (координаты в points, origin слева сверху);
- `tap` / `swipe` / `touch_path` / `text` / `button` — ввод. Свайп, начинающийся ближе
  4 pt к краю, выполняет системный жест (back / шторка / домой), а не скролл — начинай
  дальше от бортика;
- `open_url` — deep link (`metravel://<route>`, `https://metravel.by/<path>` для проверки
  роутинга Universal Link внутри симулятора).

Логи и краши читай из симулятора (`xcrun simctl spawn booted log stream` по нужному
предикату) — краш без стектрейса в отчёт не идёт.

## Пайплайн

1. **План:** список фаз — статические экраны → интеракции → локали → тёмная/светлая тема →
   тикеты → фиксы — только для выбранных assertions и слоёв.
2. **Обход:** каждый роут → `screenshot` → критическая оценка (вёрстка, обрезки, пустые
   блоки, контраст, высота шапки ≤20% вьюпорта, safe area под Dynamic Island и home
   indicator, тап-таргеты ≥44 pt) → интеракции: каждая кнопка, скроллы медленные и
   быстрые, скролл до конца списка, тогглы в обе стороны, реальный ввод и сохранение форм
   с тест-аккаунтом. Эти проверки применяй к назначенным сценариям и их рискам;
   непрерывный log capture проверяется на checkpoints/failure, не отдельной
   командой после каждого тапа. Ручной обход дополняет непокрытые assertions.
3. **iPad (когда Task Contract затрагивает iPad или universal release gate):**
   `supportsTablet: true`, guard требует
   `TARGETED_DEVICE_FAMILY = "1,2"`. На iPad-симуляторе проверь full-screen, resizable
   window (Split View), portrait и landscape — по `docs/WORKFLOW_OPERATIONS.md` это
   симуляторный слой, устройство для него не нужно. Растянутый iPhone-макет, обрезки по
   ширине и залипшие фиксированные ширины — дефект.
4. **Локали:** выбери затронутые локали по Task Contract. Матрица RU/BE/UK/PL/EN
   нужна при изменении locale lifecycle/общего i18n-контракта или release gate;
   для точечного сценария не добавляй её автоматически. Проверяй переключение и
   холодный перезапуск там, где это назначенный кейс; ищи обрезки и untranslated UI.
5. **Отчёт:** `.codex-temp/ios-qa/QA_REPORT_<ЭКРАН>.md` — таблица обхода + находки
   `### F-NN (critical/major/minor/info)` со скринами и, где известно, `файл:строка`.
   Отдельным блоком — что осталось непроверенным и на каком слое это проверять.
6. **Борд:** через `ticket-board` — тикеты `[IOS-NN] суть`, `area=front`, с моделью
   симулятора/устройства, версией iOS, `Platform impact` и `Localization impact`,
   привязка к активному спринту. Подтверждённый серверный дефект — `area=back`.
7. **Фиксы** по severity: код и платформенные файлы — `ios-expert`, карта — `map-expert`,
   визуал и HIG — `ios-designer`. Сохраняй web/native-паритет; web-проверку добавляй
   по изменённой web-границе или текущему явному заданию через selection gate,
   а не по расположению правки в общем файле. Каждый фикс проверяется на
   затронутых состояниях и релевантных соседних рисках со screenshot evidence.
8. **Регресс:** failed/affected suite и релевантные соседние состояния. Code-level
   checks выполняет исполнитель/reviewer; полный lint/Jest не повторять в QA
   после каждого шага. Для изменённой конфигурации — назначенный guard.

## Что можно и нельзя

В назначенном QA-сценарии можно создавать и удалять свои тестовые сущности,
менять статусы, проходить квесты, заполнять и сохранять формы; после проверки
восстанови состояние. Сообщения отправляй только при явной авторизации в текущей
сессии на адресата и действие; тест-аккаунт сам по себе её не даёт. Без неё
проверяй ввод и отмену без отправки.

**Нельзя:** деструктив над чужими и продовыми данными, платежи, массовые рассылки,
любые store-операции (build/upload/submit/release — только `ios-deployer` по явной
команде владельца) и подмена физического/TestFlight evidence скрином симулятора.
