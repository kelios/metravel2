# Правка опубликованного квеста

Сюда влит бывший `REVIEW_BRIEF.md`. Исполнители: `quest-editor` (авторский
текст и словарь), `quest-friction-analyst` (словарь по реальным попыткам),
`quest-geo-verifier` (координаты, только патч). Полномочия — блок
«Полномочия» ядра `SKILL.md`: правка по заказу владельца или по разбору
трения рискованного шага — без отдельного «да»; правка авторского текста
опубликованного квеста по собственной инициативе — только после подтверждения.

## Инварианты

- Источник правды по живому контенту — прод: правку начинай со свежего
  `GET /api/quests/by-quest-id/<quest_id>/` (поле `steps` бывает JSON-строкой),
  не со старой локальной копии.
- `quest_id`, `step_id`, `storage_key` не меняются; шаги не удаляются и не
  пересоздаются без явного запроса — по ним ключуется прогресс игроков.
- После любой правки на проде локальный data-файл синхронизируется:
  `node scripts/sync-quest-data-from-prod.js --source=scripts/<city>-quest-data.js`
  (`--dry-run` сначала). Несинхронизированный файл вернёт старый текст при
  следующей перезаливке — это открытый риск, так и пиши в отчёте.
- Контент шагов отдаётся API и виден сразу; посадочные `/quests/<alias>` —
  статика SSG, обновляются выкатом фронта.
- Финал НЕ патчить по id квеста: pk записи `/api/quest-finales/<pk>/` свой и
  с числовым id квеста не совпадает (torun-copernicus = квест 20, финал 21;
  lublin-old-town — наоборот, #2427). API связь квест → финал не отдаёт, поэтому
  pk берётся только через `scripts/lib/quest-finale-pk.js` (маппинг из
  `generate-quest-finale-videos.js` со сверкой текста, иначе перебор с
  детектором коллизии) — так делают `sync-quest-to-prod.js` и
  `update-quest-content.js`. Ручной PATCH финала — после того же резолва, и
  сразу verify через `GET /api/quests/by-quest-id/<quest_id>/`.

## Каким инструментом

| что | инструмент |
|---|---|
| точечная правка полей шага или `quest.title` | `node scripts/apply-quest-patches.js --dry-run …`, затем `--apply`; патч `{quest_id, step_db_id, step_id, changes:{…}}` или `{quest_id, quest_db_id, changes:{title}}`; поля только внутри `changes` (allowlist: task, hint, answer_pattern, lat, lng, maps_url, story, location, title, order, input_type), `answer_pattern` строкой; источник — в отчёте, не в патче |
| сквозная переработка квеста в одну историю | снимок `scripts/.quest-review/<quest_id>.json` + `node scripts/update-quest-content.js --quest-id=<id> --data=… --dry-run`, затем без `--dry-run` |
| синк всего файла на прод | `scripts/sync-quest-to-prod.js --source-file=… --dry-run`, затем `--apply` — шлёт PATCH по ВСЕМ шагам, поэтому для точечных правок не годится; `quest.title` не патчит — его правят патчем квеста |
| порядок шагов | только поле `order`, двухфазно: временные 900+, затем целевые (unique) — `sync-quest-to-prod.js --reorder` или патчи `order` |
| новая точка в живом квесте | патч `{quest_id, quest_db_id, after_step_id, create_step:{step_id, title, location, story, task, hint, answer_pattern, lat, lng, point_role?}}` тем же `apply-quest-patches.js`: POST с временным order, хвост сдвигается двухфазно, точка встаёт сразу за `after_step_id` (после финальной — нельзя); повтор пропускает уже созданный step_id. Data-файл: шаг вписать руками на то же место, затем `sync-quest-data-from-prod.js` — он только сверяет поля и новых шагов не добавляет |

Рабочие файлы и патчи — `.codex-temp/quest-audit/` (gitignored), патч-файл
пишется инкрементально после каждого квеста.

## Переработка живого квеста в одну историю

Цель — из «гуляй и считай» в ЕДИНУЮ ИСТОРИЮ, где игрок участник, без выдумок.

0. Снять прод: intro + steps + finale; у шага `id`, `step_id`, title, location,
   story, task, hint, answer_pattern, lat, lng, maps_url, input_type.
1. Координаты — правило `research-route.md` и скилл `metravel-quest-geocheck`;
   Nominatim экономно (≤1 запрос/с, только подозрительные точки). Неверная точка
   (не тот объект или дальше ~150 м) — новые lat/lng.
2. Сквозная нить — легенда/тема самого квеста (обычно в названии): intro задаёт
   завязку и приём (проводник, тайна, улики к финалу); story каждого шага —
   реальная история + легенда (помечена) + топонимика и двигает сюжет
   (отсылка к соседним шагам). Задание — наблюдательное, по типам 4c: надпись,
   дата, имя (B), спрятанная деталь (C), что изображено и что значит (D),
   культовая вещь места (A); счёт — только по 4/4g; цвет и материал поверхности —
   только по 4f; рискованный вопрос — `any_text`. Держи порог проверяемых из
   ядра.
3. Самопроверка каждого шага: ответ и его ключевые токены не стоят в task,
   hint, title, location, story своего шага и story соседних (4a).
4. Снимок `scripts/.quest-review/<quest_id>.json`:
   `{ intro:{step_id,story,task,hint,answer_pattern}, steps:[{step_id,story,task,hint,answer_pattern,lat?,lng?}], finale:{text} }`
   — у шага ВСЕГДА story+task+hint+answer_pattern, lat/lng — только исправленные.
   Каталог gitignored намеренно (#1448): снимок описывает прод на момент снятия
   и протухает после следующей правки; скрипт отказывается брать git-tracked
   файл, применённый снимок уезжает в `applied/`. Нужен снова — сними свежий.
5. Применить: `update-quest-content.js --dry-run`, затем без него.
6. Синхронизировать data-файл (`sync-quest-data-from-prod.js`), прогнать
   `npm run quest:gates -- --source=scripts/<city>-quest-data.js`.
7. Проверить GET-ом: токены ответа не в task/hint, story богаче, нить есть,
   типы заданий разнообразны.
8. После правки русского текста — переводы затронутого квеста по
   `upload-after.md` → «Перевод» (ручные `origin: human` не перезаписывать без
   разрешения; финал проверять отдельно).

## Отчёт

Нить квеста; по шагам: правки координат (было → стало, метры, источник),
убранные утечки, тип `answer_pattern`, счётный/не счётный; итог проверки (шагов,
утечек — 0); синхронизирован ли data-файл; нужен ли выкат (шаги — нет,
посадочные — да). Другие квесты не трогать.
