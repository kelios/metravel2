## Why

На проде #2818 холодные SSR-страницы отвечают 503 при закрытии повторно используемого API-соединения. Проба 27.10.2026: 108 рендеров при параллельности 4/8/12 дали три 503 до истечения 10 секунд; отдельные 360 API GET дали три ECONNRESET, все на reusedSocket=true. Цель — ноль таких ошибок без увеличения дедлайна.

## What Changes

- Однократно восстановить безопасный GET после сброса старого соединения до начала ответа, открыв новое соединение в исходном бюджете.
- Проверить восстановление и границы отказа регресс-тестами; повторить production-замер после reviewed deploy.
- Зафиксировать backend-зависимость #2819 для отката finalized-релиза. Её реализация требует отдельного прямого поручения.

## Capabilities

### New Capabilities

- `web-ssr-api-connection-recovery`: ограниченное восстановление API GET после сброса повторно используемого соединения.

### Modified Capabilities

Нет.

## Impact

User-visible result: холодные страницы открываются при штатной смене API-соединения.
Platform impact: desktop web | mobile web; Android/iOS — none, транспорт существует только в Node SSR runtime.
Localization impact: none; editorial/UI text не меняется.
Dependencies: frontend не зависит от #2819; полный Done gate #2818 требует принятого backend-отката #2819.
Fallback/mock policy: нет; настоящий отказ API остаётся 503.
Data/API: форма, Host и гостевая авторизация без изменений. SEO: только доступность HTML; URL, meta и содержимое сохраняются. Performance: не более двух попыток на один сброшенный GET в исходных 10 с; очередь и прогрев не вводятся. Security: заголовки, редиректы и лимит тела сохраняются; секреты/URL не логируются. Accessibility/analytics: none, разметка и события не меняются.
Existing behavior to preserve: 404/410, 503 upstream, отмена запроса, ошибочное/слишком большое тело и запрет редиректов.
Non-goals: изменение nginx, количества воркеров, timeout, SSR admission, удаление генератора, backend source.
Open questions: только отдельное разрешение на backend #2819; фронтенд-решение определено.
