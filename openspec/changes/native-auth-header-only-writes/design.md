## Context

См. `proposal.md` → «Why». Существенное для подхода:

- `getApiRequestCredentials` (`utils/authPlatform.ts`) на native возвращает пустой объект. Пустой объект — это не «без cookie»: нативный fetch в React Native по умолчанию берёт cookie общего хранилища системы, поэтому cookie уезжает всегда.
- Заголовок ставится только при наличии токена (`api/client.ts`, `authHeaders`), а токен читается через `utils/secureStorage.ts`, где на native любая ошибка в проде заканчивается `return null`.
- Бэкенд (`../metravel-backend/metravel/common/authentication.py`, read-only) при отсутствии заголовка берёт токен из cookie и на небезопасных методах требует CSRF; на HTTPS Django сначала проверяет `Referer`, которого у нативного запроса нет. Это его штатный контракт для web — менять его не нужно и нельзя из этого репозитория.
- `utils/csrf.ts` на native отдаёт пустой набор заголовков, то есть компенсировать проверку `Referer` нечем даже теоретически.

## Goals / Non-Goals

**Goals:**

- Один явный способ авторизации на native и предсказуемый код ответа при его отсутствии.
- Потеря сессии становится наблюдаемой в момент попытки записи, а не постфактум в прод-логе.
- Разделение «значения нет» и «хранилище не ответило» в чтении секретов.

**Non-Goals:**

- Не меняем бэкенд и его cookie-ветку: для web это штатный и нужный путь.
- Не трогаем `usesWebCookieAuth()` и поведение web/mobile web.
- Не чиним причину пропажи токена на конкретном устройстве: это отдельная проба на этапе testing.
- Не вводим фоновое обновление токена и не меняем экран входа.

## Decisions

**`credentials: 'omit'` на native вместо пустого объекта.**
Пустой объект оставляет решение платформе, и она отправляет cookie. Явный `omit` делает контракт запроса однозначным: нет заголовка — нет авторизации — 401. Альтернатива «подмешивать `X-CSRFToken`» отвергнута: проверка `Referer` идёт раньше и у нативного запроса он отсутствует по определению, то есть лечение не работает вовсе.

**Проверка токена перед небезопасным методом, а не только обработка ответа.**
Ответ 401 приходит уже после отправки тела: телеметрия и отзыв успеют «уехать» в никуда, и пользователь узнает об этом только по отсутствию данных. Предварительная проверка превращает молчаливую потерю в видимое требование войти до отправки. Обработка 401 остаётся вторым эшелоном — для случая, когда токен есть, но сервер его не принял.

**Инвалидация сессии идёт через существующее действие стора авторизации.**
Второй механизм разлогинивания создавать нельзя: у стора уже есть переход в разлогиненное состояние с очисткой ссылок. Задача — вызвать его в новом месте, а не написать своё.

**Чтение секрета различает «нет значения» и «ошибка хранилища».**
Сейчас оба случая дают `null`, и вызывающий не может отличить гостя от сбоя Keychain. Чтение должно возвращать это различие вызывающему; политику (повторить чтение или потребовать вход) решает клиент API, а не само хранилище.

**Текст «сессия истекла» — один ключ i18n, а не сообщение на месте.**
Строка пользовательская, поэтому заводится сразу во всех продуктовых локалях; отсутствие перевода в любой из них — дефект того же изменения.

## Risks / Trade-offs

- **На Android тот же нативный путь** → изменение общее для обеих native-поверхностей; проверяется, что запись и телеметрия на Android продолжают отвечать 200/202.
- **Где-то мог существовать нативный запрос, который фактически работал на cookie** → после `omit` он получит 401 вместо тихого успеха; это и есть цель, но проверить надо весь пишущий путь нативного клиента, а не только квесты.
- **Слишком агрессивная инвалидация сессии** (например, на разовом сбое Keychain) → инвалидация только на пишущем пути и только при подтверждённом отсутствии токена; сбой хранилища сначала даёт повторное чтение.
- **Публичные эндпоинты с `skipAuth`** → для них требование войти не применяется; поведение чтения не меняется.

## Migration Plan

Миграции данных нет. Выкладка обычная, откат — возврат коммита. Отдельный шаг приёмки: после выката прод-лог не должен содержать ответов `403` с телом 63 байта от UA `metravel/* CFNetwork`, а телеметрия и отзывы с Android продолжают отвечать 200/202.
