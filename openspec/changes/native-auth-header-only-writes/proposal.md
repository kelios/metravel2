## Why

На iPhone запись молча пропадает: приложение продолжает считать себя авторизованным, читающие запросы проходят, а любая запись отлетает 403. Прод 13.09.2026, владелец (user 169): `POST /api/quest-reviews/` и два `POST /api/quest-answer-attempts/bulk/` — `403`, тело 63 байта, то есть ровно `{"detail":"CSRF Failed: Referer checking failed - no Referer."}`. Те же эндпоинты в те же часы с Android и из браузера отвечают 200/202. Потеряны отзыв о квесте и две пачки телеметрии; пользователю не показано ни ошибки, ни предложения войти.

Механизм установлен по обеим сторонам. Бэкенд (`common/authentication.py`, read-only для нас) при отсутствии заголовка `Authorization` берёт авторизацию из HttpOnly-cookie и на небезопасных методах требует CSRF, а Django на HTTPS первым делом проверяет `Referer`, которого у нативного запроса нет по определению. Фронт при недоступном Keychain молча отдаёт `null` вместо токена (`utils/secureStorage.ts`), заголовок не ставится, но cookie нативный fetch всё равно отправляет — запрос без токена притворяется cookie-сессией. Вместо честного 401, по которому приложение разлогинило бы пользователя, получается 403 и потерянные данные (борд #1921, P1).

## What Changes

- На native исходящий запрос перестаёт нести cookie: единственный способ авторизации — заголовок `Authorization: Token <token>`. Запрос без токена получает честный 401 вместо 403 CSRF.
- Отсутствие токена при активной сессии перестаёт быть невидимым: приложение инвалидирует сессию и просит войти заново вместо анонимной отправки записи.
- Недоступное защищённое хранилище перестаёт быть неотличимым от «значения нет»: сбой чтения не превращает пользователя в гостя молча.
- Появляется пользовательский текст «сессия истекла, войдите заново» во всех продуктовых локалях.
- Не входит: изменения бэкенда (контракт `CookieTokenAuthentication` остаётся как есть, для web это штатный путь), web-ветка cookie-авторизации, причина пропажи токена на конкретном устройстве владельца (проба на этапе testing).

**Platform impact**: iOS — основная поверхность; Android идёт тем же нативным путём и должен сохранить текущее поведение записи; web и mobile web не затрагиваются, ветка `usesWebCookieAuth()` не меняется.

**Localization impact**: selected locales — одна новая строка про истёкшую сессию заводится сразу в RU/BE/UK/PL/EN через `@/i18n`.

## Impact

- **Код**: `utils/authPlatform.ts` (`getApiRequestCredentials`), `api/client.ts` (сборка заголовков и обработка ответа 401), `utils/secureStorage.ts` (различение «нет значения» и «хранилище не ответило»), строки в `i18n/locales/*`, тесты в `__tests__/api/` и `__tests__/utils/`.
- **API/данные**: новых эндпоинтов и полей нет. Меняется контракт исходящего запроса: на native всегда `credentials: 'omit'`, авторизация только заголовком, ответ 401 трактуется как инвалидация сессии. Затронуты все пишущие вызовы нативного клиента, в том числе `POST /api/quest-reviews/`, `POST /api/quest-answer-attempts/bulk/`, `POST|PATCH /api/quest-progress/`.
- **Наблюдаемое поведение**: в прод-логе исчезают ответы `403` с телом 63 байта от UA `metravel/* CFNetwork`; пользователь вместо тишины видит требование войти.
- **SEO**: none — нативный транспорт, публичных URL и разметки не касается.
- **Доступность**: сообщение о необходимости войти — обычный текст экрана/тоста, доступный скринридеру.
- **Производительность**: none — количество запросов не меняется, добавляется только проверка наличия токена перед отправкой.
- **Безопасность**: улучшение — нативный клиент перестаёт опираться на неявную cookie-сессию общего хранилища iOS и не отправляет запись «наполовину анонимно».
- **Аналитика**: новых событий не вводится.
- **Зависимости**: нет. Мягкая связь с #1922 (очередь доставки прогресса, которая обязана пережить такую потерю сессии).
- **Fallback/mock policy**: моков не вводится; отсутствие токена — честная ошибка авторизации, а не тихий анонимный запрос.
