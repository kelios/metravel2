## Context

Мотивация — см. `proposal.md` → «Why». Здесь фиксируется, как цепочка автосохранения устроена сегодня, потому что без этого не видно, почему точечные правки не дают устойчивости.

### Как автосохранение работает сейчас, от нажатия клавиши до строки в БД

**1. Редактор описания.** Quill на событии изменения текста отдаёт HTML наверх через дебаунс 250 мс (`ARTICLE_EDITOR_CHANGE_DEBOUNCE_MS`). При потере фокуса отложенное изменение принудительно сбрасывается наверх. В самом редакторе есть собственный автосейв-цикл с задержкой 5000 мс (`ARTICLE_EDITOR_DEFAULT_AUTOSAVE_DELAY`) и экспоненциальным повтором, но он активируется только при переданном колбэке `onAutosave`; мастер travel его не передаёт, поэтому цикл сейчас дремлет.

**2. Состояние формы.** `ContentUpsertSection` вызывает `handleChange('description', html)`, что доходит до `formState.updateField`/`updateFields` в `useOptimizedFormState`. На каждое такое обновление выполняется полное `fast-deep-equal` сравнение всей формы с исходной, чтобы пересчитать `isDirty`. В `useOptimizedFormState` есть второй автосейв-эффект, но он включается только при переданном `onSave`; `useTravelFormData` его не передаёт, поэтому он тоже дремлет.

**3. Движок автосохранения.** `useTravelFormPersistence` подключает `useImprovedAutoSave(formState.data, initialFormData, { debounce: 5000, ... })`. Эффект на каждое изменение `data` заново сравнивает форму с последним подтверждённым состоянием и перевзводит таймер на 5000 мс. Автосейв разрешён только при выполнении всех условий: пользователь аутентифицирован, есть доступ, форма гидратирована, нет летящего ручного сохранения, статья не в состоянии `moderation`/`publish`.

**4. Подготовка запроса.** По срабатыванию таймера вызывается `cleanAndSave`. Он собирает payload от пустого шаблона, нормализует галерею, идентификаторы изображений, маркеры, прогоняет описание через `applySmartImageLayout`, чистит пустые поля, фильтрует допустимые ключи и достраивает обязательные поля черновика. Затем `saveFormData` санитизирует текст (`sanitizeRichText`, `stripBase64Images`), выполняет анти-обнуление (пустой payload у статьи с идентификатором блокируется — инцидент 2026-07-21, travel 641) и отправляет `PUT /travels/upsert/` с клиентским таймаутом `LONG_TIMEOUT = 30000`.

**5. Обработка на сервере** (`../metravel-backend`, read-only): `UpsertTravelService.process_request` целиком выполняется в одной `transaction.atomic()`. Первым же обращением берётся `Travel.objects.select_for_update()`, и блокировка строки статьи удерживается до commit. Далее: создание строки `TravelTextVersion` с полной копией `name/description/plus/minus/recommendation`, если текст изменился; `_enforce_text_version_retention()` с `TRAVEL_TEXT_VERSION_RETENTION = 10`; `_set_m2m_relations` по семи полям с `clear()` + `set()` при расхождении; `_process_travel_coordinates` с `ta.save()` и `categories.set()` на каждую точку; финальный `travel.save()` строки с большим текстовым полем.

**6. Применение ответа.** `applySavedData` выполняет объёмное слияние ответа с живым состоянием формы: сохраняет пользовательский текст поверх пустых значений из ответа, сливает подписи галереи, сливает маркеры, синхронизирует страны, пересобирает форму через `formState.reset` и обновляет baseline. Дополнительно запускается асинхронная ветка: при нехватке серверных идентификаторов у точек выполняется повторный `fetchTravel` (`GET /travels/<id>/`) и загрузка отложенных фотографий точек. Параллельно инвалидируется кэш детали статьи, что порождает ещё одно чтение.

**7. Локальный черновик.** `useDraftRecovery` пишет снимок формы в локальное хранилище с дебаунсом 2000 мс под ключом статьи, со сроком жизни 24 часа, и предлагает восстановление при следующем открытии.

### Почему это ломается

- **Дебаунс короче времени обработки.** Сохранение тяжёлой статьи занимает 11–12 с при дебаунсе 5 с. Пока автор печатает, таймер успевает сработать до прихода ответа.
- **Прод-версия обрывает летящий запрос.** В коммите, живущем на проде, `performSave` безусловно вызывает `abort()` предыдущего контроллера перед стартом нового. Отсюда наблюдаемая картина: около двадцати `PUT /travels/upsert/` подряд, каждый в статусе `(canceled)` на ~5,05 с.
- **Отмена на клиенте не отменяет работу на сервере.** Каждый оборванный upsert доработан бэкендом до конца. Двадцать «отменённых» запросов — двадцать реально выполненных тяжёлых транзакций.
- **Блокировка строки сериализует очередь.** `select_for_update` держится до commit, поэтому конкурентные сохранения одной статьи выстраиваются в очередь, и время каждого следующего растёт. При достижении клиентского таймаута 30 с добавляются повторы с экспоненциальной задержкой.
- **Клиентский предохранитель не помогает.** `endpointLimits: { '/travels/upsert/': 120 }` разрешает 120 сохранений в минуту на этот эндпоинт — потолок, до которого описанный шторм не доходит.
- **История версий вырождается.** Версия создаётся на каждое срабатывание автосейва с изменённым текстом при retention 10, поэтому вся история покрывает порядка минуты печати.

Ключевой вывод: узкое место — **контракт**, а не константа. Фоновая правка текста оплачивает полную пересборку графа статьи. Пока это так, любая настройка дебаунса, лимитов и таймаутов лишь меняет частоту дорогих транзакций.

## Goals / Non-Goals

**Goals:**

- Развести стоимость операции по её смыслу: правка текста стоит запись текста, а не пересборку статьи.
- Сделать автосохранение самоограничивающимся: при замедлении сервера нагрузка падает, а не растёт.
- Сохранить все действующие защиты данных: анти-обнуление, гейт гидратации, guard анти-потери текста, локальный черновик, слияние ответа поверх живой формы.
- Обеспечить одинаковое поведение на всех активных поверхностях без платформенных ветвлений в логике сохранения.

**Non-Goals:**

- Введение общего фреймворка offline-first синхронизации или CRDT.
- Оптимистичные обновления и разрешение конфликтов между несколькими редакторами одной статьи.
- Изменение модели данных статьи и её публичного представления.
- Замена дебаунса на «умную» эвристику как самостоятельное решение: без разделения операций она остаётся заплаткой.

## Decisions

### D1. Два контракта сохранения вместо одного

Вводится content-save для текстовых полей и сохраняется существующий full-replace для структуры. Автосохранение по правке текста уходит в content-save.

Почему так: это единственное изменение, устраняющее корневую причину — оплату структурной операции за текстовую правку. Оно же снимает блокировку строки на всю пересборку графа и убирает пересохранение точек, которого автор не запрашивал.

Альтернативы:

- *Только увеличить дебаунс.* Отклонено: не меняет стоимость операции, при медленном сервере очередь всё равно растёт, а автор дольше остаётся без сохранения.
- *Адаптивный дебаунс от измеренного времени ответа.* Отклонено как самостоятельное решение: маскирует симптом и делает поведение автосохранения непредсказуемым для автора. Может рассматриваться позже как настройка поверх правильного контракта.
- *Очередь сохранений на клиенте с коалесцированием.* Частично принято (см. D2), но без разделения контрактов очередь лишь упорядочивает дорогие операции.

### D2. Единственность летящего сохранения и запрет самоотмены

В любой момент времени для одной статьи допускается не более одного фонового сохранения. Более свежие данные не обрывают летящий запрос, а отправляются следующим сохранением после его завершения. Явные действия автора (сохранить, опубликовать) сохраняют право вытеснения.

Почему так: клиентский `abort` не останавливает серверную работу, поэтому «отменить и перезапустить» умножает нагрузку вместо её сокращения. Соответствующая правка уже существует в рабочем дереве как незакоммиченное изменение `hooks/useImprovedAutoSave.ts` с регрессионным тестом; она принимается как часть этого design, а не как временная мера.

Альтернатива — оставить вытеснение и полагаться на серверную идемпотентность. Отклонено: сервер всё равно выполняет работу, а идемпотентность не сокращает её стоимость.

### D3. Диффование на клиенте относительно подтверждённого состояния

Content-save отправляет только поля, отличающиеся от последнего подтверждённого сервером состояния. Подтверждённое состояние уже поддерживается в движке автосохранения как baseline и обновляется по факту успешного ответа на конкретный отправленный payload.

Почему так: baseline и так существует и корректно обновляется отправленным payload, а не ответом сервера — это нужный источник истины для диффа. Отправка полного объекта при правке одного поля — источник и лишнего трафика, и лишней серверной работы.

Альтернатива — считать дифф на сервере. Отклонено: сервер всё равно вынужден принять и разобрать полный объект, а значит стоимость приёма и валидации остаётся.

### D4. Повтор только после гарантированного завершения предыдущей попытки

Клиентский таймаут ожидания ответа не должен быть короче реального времени обработки, а повтор после таймаута не должен запускаться, пока предыдущая попытка может выполняться на сервере. Ошибки, которые повтор не исправит, повторов не порождают — это уже реализовано и сохраняется.

Почему так: таймаут 30 с при очереди сохранений превращается в генератор дополнительных попыток поверх уже перегруженного сервера.

### D5. Устранение дремлющих движков автосохранения

Автосейв-эффект в `useOptimizedFormState` и автосейв-цикл в `ArticleEditor` сегодня неактивны только потому, что им не передали колбэк. Оба приводятся в состояние, где случайная передача колбэка не создаёт второй путь записи той же статьи.

Почему так: спецификация требует ровно одного механизма. Скрытая возможность включить второй — источник будущего рецидива, который воспроизводится один раз и потом ищется неделями.

### D6. Версионирование текста привязывается к смысловой правке (backend)

Версия текста должна создаваться не на каждое срабатывание автосохранения. Возможные критерии — явное сохранение автора, окно времени, либо порог различия — выбирает владелец бэкенда при реализации.

Почему так: сейчас `TRAVEL_TEXT_VERSION_RETENTION = 10` вместе с версией на каждый тик даёт горизонт истории около минуты, то есть заявленная защита от затирания контента не выполняется. Это дефект самой функции, а не только нагрузки.

### D7. Клиентский предохранитель частоты приводится в соответствие с контрактом

Потолок обращений к сохранению статьи должен быть таким, чтобы аномалия останавливалась предохранителем, а не обнаруживалась по алерту на сервере. Конкретное значение определяется после внедрения content-save, исходя из фактической частоты штатного автосохранения.

Почему так: предохранитель, который не срабатывает ни в одной реальной аварии, не является предохранителем. Изменять его до смены контракта бессмысленно — это и была бы заплатка.

## Data/API contract

- **Content-save (новый, backend):** узкое сохранение изменившихся текстовых полей статьи. Не затрагивает точки маршрута, галерею, обложку, справочные связи и статус публикации. Не запускает модерационную валидацию полноты. Возвращает подтверждение сохранённых полей.
- **Full-replace (`PUT /travels/upsert/`, существующий):** без изменений по формату запроса и ответа. Используется для структурных изменений, явного сохранения и публикации. Семантика `enforce_moderation_validation` сохраняется.
- **Совместимость:** до появления серверного content-save фронтенд продолжает использовать full-replace; поведение D2 и D4 при этом уже действует и ограничивает шторм, но не стоимость одной операции.

## Risks / Trade-offs

- **Дифф разошёлся с состоянием сервера** → content-save отправляет поле, которое сервер считает другим. Митигация: baseline обновляется только по факту успешного ответа на конкретный отправленный payload; при расхождении и при любом структурном изменении выполняется полное сохранение.
- **Регресс защиты от потери текста** → узкий путь мог бы обойти анти-обнуление и guard анти-потери. Митигация: обе защиты применяются к обоим путям сохранения, что закреплено требованиями спецификации.
- **Частичное внедрение** → FE перешёл на content-save, сервер его ещё не поддерживает. Митигация: FE-часть D2/D4/D5 внедряется независимо и раньше; переключение на content-save включается только после подтверждённой серверной поддержки.
- **Ограничение параллелизма замедляет доставку правок** → при медленном сервере правки уходят реже. Митигация: локальный черновик покрывает промежуток, состояние автосохранения честно показывает наличие неподтверждённых изменений.
- **Устранение дремлющих движков задевает другие экраны** → `useOptimizedFormState` и `ArticleEditor` используются не только мастером travel. Митигация: изменение не удаляет возможность автосохранения у других потребителей, а исключает второй путь записи для одной и той же статьи.
- **Правка выполняется в общем дереве при нескольких параллельных сессиях** → риск потери чужих изменений при массовых операциях с git. Митигация: работа ограничивается перечисленными путями; коммит и деплой выполняет владелец.

## Migration Plan

1. Внедрить FE-гарантии, не требующие сервера: единственность летящего сохранения, запрет самоотмены фонового сохранения, корректный повтор, устранение дремлющих движков. Это уже снимает шторм.
2. Дождаться серверного content-save (`area=back`).
3. Перевести фоновое автосохранение текста на content-save за явным переключателем поведения, оставив full-replace для структурных изменений и публикации.
4. После подтверждённой работы в проде привести клиентский предохранитель частоты в соответствие с фактической нагрузкой.
5. Отдельно закрыть версионирование текста на бэкенде, проверив, что история покрывает сеанс правок, а не последнюю минуту.

**Rollback / recovery:**

- Шаг 3 откатывается возвратом фонового сохранения на full-replace без изменения формата данных; сохранённые статьи остаются валидными, потому что content-save не вводит новых полей.
- Шаг 1 откатывается возвратом предыдущего поведения движка автосохранения, что восстанавливает и прежний дефект — поэтому откат допустим только как аварийная мера.
- Локальный черновик остаётся страховкой на всех шагах: при любом откате неподтверждённые правки восстанавливаются из локального хранилища.

## Validation matrix

Проверка выполняется исполнителем; перекладывать её на владельца нельзя.

| Поверхность | Сценарий | Доказательство |
| --- | --- | --- |
| Desktop web | Длительная правка описания тяжёлой статьи; счётчик и статусы запросов сохранения | Снимок вкладки сети: одно летящее сохранение, отсутствие `(canceled)`-серий |
| Desktop web | Структурное изменение (точка, галерея, обложка) | Точки и галерея сохранены, идентификаторы не изменились |
| Desktop web | Офлайн → правки → возврат связи | Ровно одно сохранение после восстановления связи |
| Desktop web | Уход со страницы с неподтверждёнными правками | Восстановление черновика при повторном открытии |
| Mobile web 390 | Правка описания, статусы автосохранения | Снимок экрана состояний, отсутствие ложного «Сохранено» |
| Android | Правка описания, сворачивание приложения во время сохранения | Устройство: правки не потеряны, статус корректен |
| iPhone | Правка описания, сворачивание приложения во время сохранения | Симулятор или устройство по риску: правки не потеряны, статус корректен |
| Все поверхности | Истёкшая сессия во время правки | Поток фоновых записей прекращается, показан вход, правки сохранены локально |

Локали RU/BE/UK/PL/EN: подписи состояний автосохранения и относительное время последнего сохранения проверяются на каждом языке; проверка выполняется на одном flow, без дублирования полного сценария на каждую локаль.

## Open Questions

- Точный критерий создания версии текста на бэкенде (явное сохранение, окно времени или порог различия) — выбирает владелец бэкенда при реализации; на требования спецификации и разбиение задач это не влияет.
- Конкретное значение клиентского потолка частоты обращений определяется после внедрения content-save по фактическим замерам.
