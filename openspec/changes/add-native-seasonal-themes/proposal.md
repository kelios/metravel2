## Why

Пользователь не может выбрать праздничную тему на Android; на iPhone действует то же ограничение. Сейчас настройки и меню скрывают контрол на native, а праздничный визуал реализован только через CSS. Требование владельца: темы должны быть доступны и реально применяться в обоих приложениях.

## What Changes

- Открыть одинаковые семь вариантов праздничного оформления: по календарю, выключено, весна, Пасха, осень, Хэллоуин, Рождество/Новый год — в настройках и существующих меню Android/iOS.
- Применять сезонные светлые/тёмные палитры и спокойный статичный декор на native, сохраняя внешний вид mobile web.
- Сохранять выбор локально, восстанавливать после запуска и обновлять автоматическую тему в местную полночь и после возвращения приложения из фона.
- Сохранить независимый выбор светлой/тёмной/системной схемы, календарь, существующие переводы и web boot без мигания.
- Устранить обнаруженный при проверке принудительный светлый режим iOS: согласовать автоматическую схему в канонической конфигурации и SDK-модуле.
- Устранить отдельное нативное окно меню, которое переживает переход к входу и перехватывает нажатия; сохранить оформление, Back, фокус и доступность меню шапки/профиля.

Цель: на Android и iPhone каждый выбор меняет вид приложения сразу и сохраняется после перезапуска; автоматический режим следует тому же календарю, что web.

## Capabilities

### New Capabilities

Нет: расширяются существующие контракты праздничного оформления.

### Modified Capabilities

- `holiday-appearance`: доступность выбора, палитры и статичного декора на Android/iOS, включая гостя и авторизованного пользователя.
- `holiday-calendar`: восстановление и смена календарной темы в нативном жизненном цикле приложения.

## Impact

- **Platform impact:** shared, desktop web, mobile web, Android, iOS (iPhone/iPad).
- **Localization impact:** all current locales — RU/BE/UK/PL/EN; reuse existing labels and localized dates with RU fallback.
- **User-visible:** темы появляются в нативных меню/настройках и меняют оформление без перезапуска.
- **Paths:** `hooks/useTheme.ts`, `constants/designSystem.ts`, сезонный реестр палитр, `app/global.css`, `components/layout/SeasonalTheme*.tsx`, `components/screens/settings/SettingsScreen.tsx`, общая шапка/логотип, tests and theme feature docs. Конкретный diff определяется design.
- **API/data:** API без изменений; сохраняются ключи `theme` и `seasonal-theme`, значения auto/off/id; не требуется миграция пользовательских данных.
- **Dependencies:** нет backend-зависимости; runtime QA требует USB Android и iOS simulator. Store build/upload/release — отдельные разрешения, этот proposal их не открывает.
- **Fallback/mock policy:** неизвестное значение или недоступное хранилище дают auto; реальные темы не заменяются mock. При ошибке записи текущий выбор остаётся действующим, устойчивость после рестарта не обещается.
- **Accessibility:** radio semantics, touch targets ≥44dp, readable translated labels, contrast and input-transparent decoration.
- **Performance:** без внешних запросов декора, polling и анимаций; один таймер местной полуночи с очисткой.
- **SEO:** routes/canonical/metadata/SSG не меняются; сохранить web boot/print.
- **Security:** только валидированные локальные enum preferences; auth, secrets, URLs и WebView не затрагиваются.
- **Analytics:** существующие события не меняются, новые не нужны.

### Existing behavior to preserve

Календарные окна и приоритет Пасхи, ручной override/off, пять локалей, светлая/тёмная/системная схема, web SSR/first frame, печать, навигация и геометрия контента.

### Non-goals

Новые темы, изменения опубликованных текстов, синхронизация выбора через аккаунт, редизайн профиля, изменение карты/статей, публикация в магазинах, backend changes и изменения конфигурации версий/подписи/store. Конфигурация системной темы и необходимый совместимый native SDK-модуль входят в проверенный follow-up.

### Open questions

Нет блокирующих вопросов. Под «темами» понимаются существующие праздничные оформления; обычные светлая/тёмная/системная настройки также входят в regression QA.
