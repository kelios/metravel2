## Context

Мотивация — см. `proposal.md` → «Why». Здесь только состояние механизма, которое определяет подход.

Механизм отзывов квеста уже собран и работает по цепочке:

| звено | путь | состояние |
| --- | --- | --- |
| форма отзыва в финале | `components/quests/QuestReviewSection.tsx`, подключена в `components/quests/questWizardSections.tsx:648` | работает: оценка 1–5 + «понравилось» / «улучшить» |
| отправка | `api/questReview.ts:63` → `POST /api/quest-reviews/` | эндпоинт живой (`quests/urls.py:34`) |
| префилл своего отзыва | `api/questReview.ts:89` → `GET /api/quests/quest{id}/review/users/{userId}/` | живой (проба → `401` без токена, то есть роут есть) |
| публичный список | `api/quests.ts:352` `fetchQuestReviews` → `GET /api/quests/quest{questId}/reviews/` | живой (проба → `200`) |
| читалка | `components/quests/QuestReviewsModal.tsx`, входы из `screens/tabs/QuestCard.tsx:442` и `app/(tabs)/quests/[city]/[questId].tsx:454` | работает |
| агрегат | `rating_avg` / `rating_count` из каталога (`quests/views.py:236`), адаптер `api/quests.ts:147` | приходит, показывается с первого отзыва |

Отсюда три расхождения кода с реальностью, которые и делают задачу «расширением», а не стройкой с нуля:

1. `api/quests.ts:280` и `api/questReview.ts:4` документируют эндпоинты как несуществующие, а `fetchQuestReviews` при `404` подставляет `QUEST_REVIEWS_MOCK` — четыре выдуманных отзыва с именами авторов. Прод от этого защищён (`__DEV__`-гейт, поставленный после инцидента с выдуманными отзывами на проде), но приёмочный таргет проекта — локальный стек, и там мок даёт ложную приёмку.
2. Агрегированная оценка показывается при `ratingCount > 0`: на проде это уже даёт квест с одним отзывом и «рейтингом» 5.0.
3. Фото, модерация и структурная отметка «точка требует проверки» отсутствуют на уровне данных: `QuestReview` (`quests/models.py:411`) — это `user, quest, rating, liked, disliked, created_at, updated_at`, и всё. Жалоба на неточность уходит свободным текстом в общий фидбэк (`components/quests/QuestInaccuracyReportModal.tsx` → `POST /api/feedback/`), без привязки к точке.

Ограничение workspace: этот репозиторий владеет только фронтендом. `../metravel-backend` читается, но не правится, поэтому всё, что требует новой таблицы, поля или коллекции загрузки, физически не может быть закрыто этим изменением.

## Goals / Non-Goals

**Goals:**

- Привести код в соответствие с живым контрактом: убрать мок публичных отзывов и протухшие комментарии «эндпоинта пока нет».
- Сделать агрегированную оценку квеста честной: показывать только при выборке от трёх отзывов.
- Дать измеримость сбору отзывов через `quest_review_submit`.
- Зафиксировать backend-контракт фото, модерации и очереди точек в виде, по которому можно завести `area=back` тикет без второго раунда проектирования.

**Non-Goals (уровень дизайна, сверх границ из `proposal.md`):**

- Не переносить показ отзывов на отдельный экран и не менять вёрстку читалки — меняется только условие показа агрегата.
- Не трогать формулу агрегата: среднее считает бэк, фронт только решает, показывать ли результат.
- Не заводить отдельный эндпоинт живой оценки `/quests/{id}/rate/`: решение #1578
  закрепило `QuestReview` как единственный источник рейтинга и текста.

## Decisions

### 1. Расширяем существующую цепочку, второй механизм не заводим

Карточка прямо требует сверки перед стартом — сверка проведена, механизм найден, поэтому вся работа идёт в уже существующие `QuestReviewSection`, `fetchQuestReviews`, `QuestReviewsModal` и адаптер каталога.

*Отвергнутая альтернатива:* отдельный «UGC-модуль» со своим стором, своим экраном сбора и своим списком. Это дало бы два независимых источника отзывов на одной странице квеста и две разные оценки одного квеста — ровно тот сценарий, от которого предостерегает постановка.

### 2. Мок публичных отзывов удаляется целиком, а не прячется за флаг

`QUEST_REVIEWS_MOCK` и `buildQuestReviewsMock` удаляются, `fetchQuestReviews` при `404` возвращает пустой список во всех окружениях.

*Отвергнутая альтернатива:* оставить мок под `__DEV__`. Приёмочный таргет проекта — локальный стек с копией прод-базы; мок на нём показывает «отзывы есть» там, где их нет, и прячет ровно тот сценарий пустого состояния, который эта задача должна доказать. Плюс мок пережил своё назначение: эндпоинт, ради отсутствия которого он писался, реализован.

*Риск удаления:* если бэк временно отдаёт `404`, читалка покажет пустое состояние вместо контента. Это и есть желаемое поведение — честное пусто вместо выдуманных авторов.

### 3. Порог показа агрегата — одна константа в доменном модуле рейтинга квеста

`QUEST_RATING_MIN_REVIEWS = 3` и предикат `hasPublicQuestRating(count)` живут в `api/questRating.ts` (доменный модуль оценки квеста) и зовутся из трёх мест показа: две ветки `screens/tabs/QuestCard.tsx` (оверлей и телефонная полоса деталей) и `ratingSlot` в `app/(tabs)/quests/[city]/[questId].tsx:331`.

*Отвергнутая альтернатива №1:* инлайн `ratingCount >= 3` в трёх местах. Три копии числа расходятся при первой же правке продуктового правила.

*Отвергнутая альтернатива №2:* положить константу в `utils/ratingHelpers.ts`. Этот модуль общий для путешествий, мест, статей и очков пользователя; квестовый порог там станет соблазном применить его к чужим рейтингам, у которых своё правило.

*Почему порог не трогает чип-читалку:* чип показывает `ratingCount` — количество отзывов, а не выведенную оценку. Один настоящий отзыв читать можно и нужно; вводит в заблуждение именно усреднение по выборке из одного.

### 4. Аналитика — тонкая обёртка, вызов в точке успеха мутации

Событие описывается в `utils/questReviewAnalytics.ts` по образцу уже существующего `utils/questRetentionAnalytics.ts` (имена событий не собираются на месте вызова, согласие проверяет сам `sendAnalyticsEvent`). Вызов — в `onSuccess` мутации `hooks/useQuestReview.ts:52`.

*Почему именно `onSuccess`:* это единственная точка, где сохранение подтверждено сервером, и она срабатывает один раз на `mutate`. Ре-рендер экрана финала её не повторяет — требование «событие не дублируется» выполняется структурно, без рефа-«выстрелить один раз».

*Отвергнутая альтернатива:* стрелять в обработчике кнопки. Тогда событие уходило бы и при неуспешной отправке, и счётчик отзывов в аналитике разошёлся бы с числом строк в базе.

`cityId` в событие приходит прокидыванием из `questWizardSections.tsx` (значение там уже есть — им пользуется соседний `QuestNextStepSection`), через `QuestFinaleFeedback` и `QuestReviewSection` в `useQuestReview`.

### 5. Backend-контракт недостающих звеньев фиксируется здесь, реализуется тикетами `area=back`

Из этого workspace бэкенд read-only. Контракт, по которому заводятся тикеты:

**5.1. Фото в отзыве (до 3).** Загрузка переиспользует существующий `POST /api/upload` (`media_assets.views.FilesView`), который уже коллекционный: `travelMainImage`, `gallery`, `description`, `travelImageAddress`. Нужна новая коллекция `questReviewPhoto` и хранение ссылок с привязкой к отзыву, опционально — к `quest_step`. Публичный элемент списка отзывов дополняется полем `photos: [{ id, url, step_id|null }]`, не более трёх на отзыв.

*Почему через существующую коллекцию, а не новый эндпоинт:* валидация MIME, лимиты размера и запись в хранилище там уже есть и уже проверены на других коллекциях; новый эндпоинт означал бы вторую реализацию тех же проверок.

**5.2. Модерация отзывов.** Флаг на модели по образцу `travels.Travel.moderation` (`travels/models.py:437`): публичный список `GET /api/quests/quest{id}/reviews/` отдаёт только прошедшие модерацию записи, агрегаты `rating_avg` / `rating_count` считаются по тому же множеству. До модерации автор видит свой отзыв как принятый — это уже текущее поведение формы.

*Почему модерация обязательна именно для фото:* текст без фото уже публикуется как есть и на проде живёт; фото с точки — это загруженный пользователем бинарь на публичной странице квеста, и без предпубликационной проверки страница квеста становится открытым каналом для произвольных изображений.

**5.3. Структурная отметка «точка требует проверки».** Отметка с привязкой к `quest_step` и пользователю, уникальная в паре (пользователь, точка). При двух и более отметках от разных пользователей точка попадает в очередь на правку контента. Существующий свободнотекстовый отчёт (`QuestInaccuracyReportModal`, #1480) остаётся как канал для всего, что не сводится к «точка не соответствует»: порог агрегируется только по структурной отметке, свободный текст агрегировать нечем.

## Risks / Trade-offs

- **Порог `>= 3` прячет рейтинг у квестов, где он сейчас виден.** На проде это два квеста (`krakow-podgorze` — 1 отзыв, `minsk-cipher` — 2). → Так и задумано валидацией карточки; чип-читалка и счётчик прохождений на этих карточках остаются, то есть карточка не пустеет.
- **Удаление мока делает локальную приёмку строже.** Разработчик без данных увидит пустую читалку. → Это и есть настоящее поведение; для проверки непустого списка на локальном стеке есть копия прод-базы, а e2e `e2e/quest-reviews-reader.spec.ts` перехватывает роут отзывов сам (`page.route('**/quests/quest*/reviews/**')`) и от `__DEV__`-мока не зависит.
- **Живая оценка консолидирована с отзывом (#1578).** Тап по звезде меняет
  только локальный черновик; один `POST /api/quest-reviews/` сохраняет рейтинг и
  текст. Несуществующий `/rate/`, DEV-мок и отдельная optimistic-мутация удалены,
  поэтому DEV и production используют один контракт.
- **Фото и очередь точек уезжают за границу спринта.** → Фронтовая часть поставляется отдельно и не блокируется: удаление мока, порог и аналитика ценны сами по себе и не требуют backend-изменений.

## Migration Plan

Обратно совместимо, миграции данных нет. Серверная сторона не затрагивается, поэтому откат фронта не требует согласования с бэкендом.

Откат НЕ является revert'ом одного коммита: часть диффа задачи попала в чужой sweep-коммит `fe10f87e` (параллельная сессия сделала `git add -A`), а поверх легли правки #1578 в тех же файлах. Откатывать нужно адресно по изменениям: вернуть ветку мока в `fetchQuestReviews`, снять `hasPublicQuestRating` в трёх местах показа и убрать вызов `trackQuestReviewSubmit` — каждое из трёх независимо и обратимо по отдельности.
