# Design: спайк #2766 — loaders Expo Router 58 для per-entity страниц

Спайк 26.10.2026, маршрут `/travels/[param]`, Expo 58.0.19 / expo-router 58.0.26, React 19.3.0.
Изолированные worktree от `10b650e26` (спайк и база), сборка теми же флагами, что `build-prod.sh`
(`build-web-safe.js -p web -c`, общий `web-build.lock`). Данные loader'а — локальный бэкенд (копия
прод-базы) или фикстуры 402 статей с него; прод-API и прод-CPU не нагружались. Diff спайка —
`spike-2766.diff` рядом. Хост замеров — Mac, 8 ядер, 16 ГБ, параллельно работали другие сессии
(load average 5–300): абсолютное время сборки шумное, сравнивать только порядки и падения.

## Как это устроено в SDK 58 (по коду)

| факт | где |
| --- | --- |
| static-экспорт рендерит все HTML одним `Promise.all` без лимита | `@expo/cli/build/src/export/exportStaticAsync.js:147` |
| loader выполняется на каждый путь, JSON пишется в `_expo/loaders/(tabs)/travels/<slug>` | `exportStaticAsync.js:236–267` |
| `generateStaticParams` раскрывает динамический маршрут в пути | `@expo/router-server/build/loadStaticParamsAsync.js` |
| рендер — `renderToReadableStream` + `allReady` (ждёт Suspense/lazy) | `@expo/router-server/build/server/renderStreamingContent.js:219–249` |
| данные loader'а целиком инлайнятся в HTML (`__EXPO_ROUTER_LOADER_DATA__`) | `renderStreamingContent.js:232` |
| head — только из `generateMetadata`; helmet в экспорт не попадает; JSON-LD в Metadata нет | `renderStreamingContent.js:204,254`; `expo-server/build/cjs/metadata.d.ts:178–209` |
| `generateMetadata` не видит данных loader'а → второй запрос к API на страницу | dev-лог спайка: два `by-slug` на один рендер (разные бандлы) |
| бандл loader'а грузится и **исполняется заново на каждый путь, без кеша** | `MetroBundlerDevServer.js:1438` → `ssrLoadModule` `:603–620` → `getStaticRenderFunctions.js:163–177` |
| babel режет в бандле loader'а только экспорты, импорты экрана остаются (1 848 модулей) | `babel-preset-expo/build/plugins/server-data-loaders-plugin.js:31–113` |
| клиент при SPA-переходе тянет `/_expo/loaders/(tabs)/travels/<slug>`; нет JSON → ошибка | `expo-router/build/loaders/utils.js` (`fetchLoader`); проба спайка |
| `output: "server"`: HTML не пререндерится, рендер на запрос | `exportStaticAsync.js:143` |

## Гейты тела в текущем экране

Экран статьи спроектирован под генератор: SEO-тело даёт генератор, React дорисовывает после LCP.

1. `components/travel/details/TravelDetailsDeferredRuntimeSlot.tsx:32` — поздние секции только при
   `deferredChromeReady` (после LCP на клиенте).
2. `components/travel/TravelDescription.tsx:99–140` — тяжёлый HTML описания раскрывается после idle
   (#1552, TBT); на сервере — заглушка «Загружаем описание».

Решение спайка, совместимое с обоими: описание — **HTML-остров** из `rich_text.description.safe_html`
(санитизировано бэком): один и тот же `<div dangerouslySetInnerHTML>` на сервере и на первом
клиентском проходе (гидрация не обходит его детей, TBT не растёт), богатый рендер подменяет его
после idle, как сейчас. Поздние секции остаются клиентскими (принудительное открытие гейта 1 давало
расхождение гидрации в границе `travel-details-deferred-transition`).

## Измерения

### SEO-паритет (12 статей, есть и на проде, и в локальной базе)

| метрика | генератор (прод) | loader (спайк v4) |
| --- | --- | --- |
| title / canonical / H1 | — | совпадают 12/12 |
| покрытие слов текста статьи в HTML | 0,69–1,0 | 0,91–1,0 |
| JSON-LD | Org+WebSite, Breadcrumb, Article, FAQ (head) | Org+WebSite (head); WebPage+Article+Breadcrumb (body); **FAQ нет** |
| размер HTML | 134–224 КБ | 344–820 КБ |
| gzip (`dolina-mnikovskaia-1`) | 39 КБ | 85 КБ |

Вес: 143 КБ — данные loader'а (полный ответ API; JSON статьи медиана 125 КБ, максимум 844 КБ),
130 КБ — атомарные стили RNW всего отрендеренного дерева. Loader обязан отдавать урезанный payload
(как нынешний preload #1479), FAQ JSON-LD — перенести билдер генератора.

### Гидрация (Playwright, `navigator.webdriver` замаскирован)

- 1440 px: без ошибок, 4/4 статьи. 390 px: React #418 на 4/4. dev-SSR (`expo start`): без ошибок.
- Причина: сервер не знает ширину и рендерит десктопную раскладку (в HTML десктопный сайдбар),
  экран ветвится по JS-`isMobile` → клиент пересоздаёт поддерево маршрута. Критическая часть экрана
  должна верстаться адаптивно через CSS. На проде сейчас ошибки нет, потому что сервер рендерит
  экран без данных (скелетон).
- Ловушка проб: без маскировки `isWebAutomation` (`utils/isWebAutomation.ts`) открывает гейты только
  на клиенте и даёт ложное #418.

### Модель B (static + loaders)

| прогон | итог |
| --- | --- |
| база HEAD, без loaders | 218 с wall, 446 с CPU, пик RSS дерева 2,8 ГБ, 118 HTML (load 57–97) |
| 12 путей с loader | 120–196 с, 2,0–2,9 ГБ (load 12–50) — в пределах шума базы |
| 350 путей | **OOM** кучи 4 ГБ через 151 с |
| 1 400 путей | **OOM** 4 ГБ (220 с); с `--max-old-space-size=10240` — **OOM** на 9,7 ГБ (279 с) |

Во всех падениях фикстурный API не получил ни одного запроса loader'а: память кончается на загрузке
модуля loader'а (1 848 модулей × число одновременных путей). Динамический `import()` экрана в файле
маршрута бандл не уменьшил — в серверном бандле он не выносится. Рабочий B возможен только с
собственным патчем `@expo/cli` (кеш исполненного модуля по файлу + лимит конкурентности рендера).

Дополнительно для B: статья, опубликованная после сборки, — SPA-переход получает HTML-фолбэк вместо
JSON и уводит на `/`; нужен nginx-фолбэк промахов `_expo/loaders/**` на сервер — то есть часть A.

### Модель A (server + loaders)

- Экспорт: `dist/client` 21 МБ + `dist/server` 35 МБ, HTML не пререндерится (515 с при load 66–100).
- Штатный адаптер `expo-server/adapter/express`; серверный бандл читает `EXPO_PUBLIC_*` в рантайме
  (без них рендер падает: `EXPO_PUBLIC_API_URL is not defined`) — env процесса обязателен.
- SEO-подпись ответа = static-варианту (title, canonical, H1, покрытие 1,0).
- Один Node-процесс на Mac, API — фикстуры (чистая стоимость рендера), 402 разные статьи:

| нагрузка | p50 | p90 | p99 | стр/с | CPU на страницу |
| --- | --- | --- | --- | --- | --- |
| последовательно | 32 мс | 51 мс | 97 мс | 27 | 36 мс |
| конкурентность 4 | 105–129 мс | 139–187 мс | 201–340 мс | 28–36 | 30 мс |

  Первый запрос после старта 0,4–2,7 с. На одноядерном прод-хосте CPU на страницу оценочно выше
  (не измерялось — прод-хост в спайке не трогали).
- **Удержание памяти:** после принудительного GC +0,6 МБ на запрос (58 → 1 040 МБ за 1 615
  запросов, и при повторе одного URL); с `--max-old-space-size=384` процесс падает примерно через
  500 запросов. Heap snapshot (150 запросов): 150 копий bootstrap-скрипта с данными loader'а (42 МБ),
  стилей RNW и inline-скриптов `+html.tsx`; 1 350 `Query` и 1 355 `Timeout` — по 9 на запрос.
  Высоковероятная причина: React Query с явным `gcTime` 10 минут (`hooks/useTravelDetails.ts` — `gcTime` 10 мин,
  `utils/reactQueryConfig.ts:28`) ставит таймеры на сервере, и каждый рендер со всеми строками живёт
  ещё 10 минут. Фикс (на сервере без gc-таймеров / `clear()` после рендера) не проверен — первая
  задача плана A.
- `setActiveQueryClient` (`app/_layout.tsx:243`) пишет клиент в модульную переменную — на сервере её
  перезаписывают конкурентные запросы; SSR рендерит только гостевое состояние, аудит синглтонов —
  обязательный пункт.

## План A (выбран владельцем 26.10.2026)

1. Фикс удержания памяти SSR и аудит модульных синглтонов; гейт: heap после GC стабилен на 5 000
   запросах при `--max-old-space-size=384`.
2. Маршрут путешествия: loader с урезанным payload, `generateMetadata` из того же запроса (общий
   кеш процесса на время запроса), остров описания, JSON-LD (Article, Breadcrumb, FAQ) в теле,
   адаптивная критическая часть без JS-ветвления по ширине; гейты: SEO-diff подписи по всем статьям
   = без потерь, гидрация без #418 на 390/768/1440, first-frame e2e.
3. `area=back`: Node-процесс (compose/supervisor, лимит памяти, рестарт), nginx `proxy_cache`
   с `stale-while-revalidate` и фолбэком на статический HTML при недоступности процесса, сброс кеша
   по событию правки статьи/квеста; замер CPU на прод-подобном одноядерном окружении.
4. Переключение `/travels/*` на A; генератор перестаёт писать статьи (поколение HTML без статей).
5. Квесты → города/страны → локализованные пакеты квестов (v1, hreflang) тем же порядком; удаление
   соответствующих частей генератора, `R1/R2`-квитанций для перенесённых маршрутов и проверок
   статики сборки (сняты в #2766) в пользу проверок SSR-ответа.

## Переходный период A: один серверный экспорт

Независимая архитектурная проверка 26.10.2026: два экспорта из одного коммита не гарантируют
одинаковый граф маршрутов и загрузчиков. Смешивать их клиентские пакеты нельзя без отдельного
доказательства совместимости. Целевой переход — один `output: "server"` экспорт с его собственными
`client/` и `server/`; конечный набор старых шаблонов при необходимости рендерится штатным
адаптером из этого же экспорта. Генератор временно обрабатывает только ещё не перенесённые
сущности. Nginx направляет в Node как перенесённые страницы, так и их `/_expo/loaders/**`.

До готовности инфраструктуры #2769 действующий статический выкат сохраняется. Серверный артефакт
собирается отдельно для проверки; `EXPO_PUBLIC_WEB_RUNTIME_SSR=true` включает чтение loader на
клиенте только этого артефакта. Статическая сборка не читает loader при переходах, потому что
для новых slug у неё нет соответствующего JSON. Нельзя включить флаг на статическом выкате или
удалить статьи из генератора до готовности единого артефакта, инфраструктуры и проверки переходов.

## Изоляция запроса и локали

Loader и `generateMetadata` получают разные обёртки `ImmutableRequest`, но общий исходный
`AbortSignal` (`expo-server` 58.0.6, `vendor/environment/common.js` и `ImmutableRequest.js`).
Общий между Metro-бандлами `Symbol.for` хранит `WeakMap<AbortSignal, Map<ключ, Promise>>`:
один API-запрос и одна редакция статьи на рендер, без TTL, таймеров и переноса кеша на следующий
запрос. Проверка на настоящих экспортированных бандлах обязательна.

Серверный QueryClient принудительно задаёт `gcTime: Infinity` после всех настроек конкретного
query/mutation; глобальный `activeQueryClient` в web SSR не регистрируется (#2767).

Перед переносом локализованных квестов нужен запросный источник локали. Текущий
`LocaleProvider.web.tsx` начинает с RU, а non-RU URL включает `BootLocaleGate` с незавершающимся
promise: серверные effects не переключают язык, и ожидание `allReady` не заканчивается.
Глобальный `i18n.changeLanguage` для SSR запрещён: конкурентные запросы разных языков
переписывали бы язык друг другу. Provider, переводчик, форматирование, metadata и `<html lang>`
должны читать одну локаль текущего запроса; гейт — конкурентные RU/BE/UK/PL/EN запросы.

Основа реализована отдельным этапом #2770: запросный ALS bridge, общий серверный кеш четырёх
non-RU каталогов и штатный middleware до metadata. Браузерный `prepareBootLocale` сохраняется.
Code-level и runtime-проверки ещё обязательны; исходники не означают приёмку переводных страниц.

## Выявленная граница переноса квестов (#2771)

Независимый разбор после спайка статьи показал: backend `quests/services/seo_serving.py`
подтверждает доступность локали по активному HTML-release, а `scripts/lib/questPageDepth.js`
считает robots-вердикт относительно всего уровня страниц (300 слов, 30 % собственных 5-грамм).
Loader одного документа этот контракт не сохраняет. Stateful wizard также ждёт клиентские
`guestReady`/hydration и рисует один текущий шаг; засев React Query не делает его SSR-готовым.

Предлагаемый следующий контракт — независимая публикация согласованных данных detail/city/
country, с source/corpus/content revision, текущей доступностью версий и прежним quality-verdict.
Общие безопасные модели и TouristTrip-билдер выделяются из генератора; React рендерит видимое
публичное описание и дайджест, существующее прохождение читает клиентский прогресс.
Новые редакционные тексты не создаются: существующие `seoSsg` строки переносятся в runtime.
В API-проекцию не входят task/hint/answer_pattern/progress. Публикация данных не создаёт HTML
или assets, поэтому выпуск кода не сравнивает R1/R2.

Это отдельная backend-задача #2771, пока backlog: для статей контракт «без изменений API»
сохраняется, а дополнительный API квестов требует прямого поручения и решения владельца
о свежести (активация до ответа сохранения либо согласованный период до 30 секунд).
До решения квесты, их генератор и R1/R2 остаются действующим путём. #2766 нельзя закрыть
одним этапом статей; #2769 разрешает инфраструктуру статей, не новую публикацию данных квестов.

Основа #2770 реализована через общий между Metro-бандлами `Symbol.for` с Node
`AsyncLocalStorage`: runner открывает контекст только вокруг динамического обработчика,
middleware ожидает конечный каталог локали до metadata, а provider на сервере не включает
бесконечный browser boot gate. Каталоги и конечные promises ограничены четырьмя non-RU
локалями; данные запросов в этом глобальном реестре не хранятся. Миграция самих квестов и
реальные конкурентные HTTP-пробы остаются отдельными пунктами приёмки.

Холодный request SSR использует тот же post-`allReady` хунк RNW, что статический экспорт:
`getStyleElement()` до рендера не содержит классы, впервые созданные внутри страницы.
Ответ буферизуется до полного рендера и обновления stylesheet; ошибка не становится
закешированным 200. Паритет первого кадра проверяется на холодном процессе при 390/768/1440.

## План B (не выбран)

1. Патч `@expo/cli` (patch-package): кеш модуля loader'а по файлу + лимит конкурентности рендера;
   гейт: экспорт 1 400 путей в куче по умолчанию.
2. Те же пункты экрана, что A.2.
3. `area=back`: фолбэк промахов `_expo/loaders/**` и непререндеренных путей.
4. Связка выката с контентом остаётся (R1/R2 нужны дальше), вес поколений растёт с payload loader'а.

## Отвергнутое

- Оставить генератор и только ослабить `R1 ≠ R2` — лечит симптом, связка и вес поколений остаются.
- Принудительно открыть отложенные гейты экрана на сервере — расхождение гидрации в поздних секциях
  (замерено), и рост TBT на клиенте.
