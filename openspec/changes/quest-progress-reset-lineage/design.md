## Context

Мотивация — `proposal.md` (Why), требования — `specs/quest-progress-reconciliation/spec.md`.

Текущее устройство (код `main` @ `df7d52e56`):

- **Локальные копии прохождения.**
  - Запись визарда в AsyncStorage: ключ = `storage_key` бандла + владелец, `utils/questProgressStorage.ts`; пишет только `components/quests/useQuestWizardProgress.ts`.
  - Отложенный снапшот экрана: `pendingDataRef` в `useQuestProgressSync`, `hooks/useQuestsApi.ts`.
  - Запись очереди доставки на диске: `quest_progress_queue_v2`, `utils/questProgressQueue.ts`, #1922.
- **Единственный писатель на сервер** — `pushQuestProgressSnapshot` (`utils/questProgressQueue.ts`) поверх `withQuestProgress` (`api/quests.ts`). Цепочка чтение → слияние → запись сериализована по квесту (#1905). `readOrCreateProgress` делает `GET /api/quest-progress/quest/<id>/`, при 404 — `POST /api/quest-progress/`, затем задача сливает и отправляет `PATCH`. Через этого писателя идут флаш экрана, доставка при уходе с экрана и проход очереди.
- **Слияние** `mergeQuestProgress` (`utils/questProgressMerge.ts`) аддитивное: `completed = local || server`, ответы объединяются.
- **Экран** (`app/(tabs)/quests/[city]/[questId].tsx`) передаёт визарду `initialProgress`:
  - `undefined` — чтение ещё идёт;
  - снапшот сервера — строка есть;
  - `NO_SERVER_PROGRESS` (пустой снапшот) — строки нет ИЛИ чтение упало. Сейчас эти два случая не различаются.
- **Бэкенд** (`../metravel-backend` `origin/master` `847d21f`, только чтение):
  - `QuestProgress` на `BigAutoField`, `unique_together=[quest, user]`;
  - `POST` → `get_or_create`, 201 или 200;
  - `PATCH /<id>/` → 404, если строки нет;
  - `DELETE` — физическое удаление с реконсиляцией первопроходца (#1434);
  - `GET quest/<quest_id>/` отдаёт 404 и когда нет строки (`Progress for quest_id=… not found`), и когда квест не опубликован (`Quest with quest_id=… not found`).

## Goals / Non-Goals

**Goals:**

- Одно правило поколения для всех путей записи и для загрузки визарда, без изменений API.
- Разрушительное решение (стереть копию) принимается только по подтверждённому ответу сервера.
- Копии без поколения ведут себя как сейчас (#1803, записи старых версий).

**Non-Goals:**

- Сброс, нажатый без сети: `DELETE` не доходит, строка остаётся — отдельная карточка.
- Любые правки `../metravel-backend`.

## Decisions

### D1. Поколение = `id` серверной строки

PK `quest_progress` — BigAutoField на последовательности PostgreSQL: значения не переиспользуются и растут. Значит, «строку удалили» = строки с этим `id` нет, а «строку пересоздали» = у строки квеста другой, больший `id`.

Альтернативы:
- серверный счётчик поколений или мягкое удаление с `reset_at` — нужны миграция, BE-карточка и новое поле, а гарантия та же, что уже даёт PK;
- `created_at` строки — сравнение времён хрупче, чем сравнение идентификаторов, и не даёт ничего сверх `id`;
- клиентское «надгробие» на устройстве, где нажат сброс, — до других устройств без серверного состояния оно не доходит.

### D2. Поколение живёт в самом снапшоте (`serverId`), а не в отдельной карте устройства

У `QuestProgressSnapshot` появляется поле `serverId: number`, где `0` — поколение неизвестно. Оно сохраняется в записи визарда, в записи очереди и в отложенном снапшоте экрана, поэтому копия несёт своё происхождение по любому пути доставки.

Альтернатива — карта «владелец+квест → последний виденный `id`» в отдельном ключе хранилища. Отвергнута: карта описывает знание устройства, а не происхождение копии. Как только карта переключилась на новую строку, уцелевшая старая копия пройдёт проверку и сольётся в новое поколение. Для этого хватает гонки между командой «стереть» и отложенным на 2 с сохранением.

### D3. Проверка поколения — в `readOrCreateProgress`, до `POST`

`withQuestProgress(questId, task, { lineageId })`: при заданном `lineageId` строка ОБЯЗАНА существовать с этим `id`. Иначе бросается `QuestProgressLineageMismatch`, в котором лежит текущая строка или `null`, и не уходят ни `POST`, ни `PATCH`. `pushQuestProgressSnapshot` передаёт `serverId` снапшота; миграция гостевого прогресса (`useGuestQuestFlow`) и `fetchOrCreateProgress` вызывают без опции и ведут себя как раньше.

Почему здесь: это единственный сериализованный писатель, общий для трёх путей записи. Внутри `task` проверять поздно — строка к тому моменту уже создана.

Альтернатива — проверка в каждом вызывающем. Отвергнута: три копии правила, а очередь уже однажды разошлась с экраном (#1922).

### D4. Реакция на несовпадение — отбросить, а не повторять

- Проход очереди: запись снимается, как при постоянном отказе (4xx), и доставка идёт к следующему квесту.
- `deliverOrEnqueueQuestProgress`: запись снимается с очереди и обратно не кладётся.
- Флаш экрана (`useQuestProgressSync`):
  - отложенный снапшот выбрасывается, запись снимается с очереди, ретрай не планируется;
  - `progressIdRef` и `progress` переходят на строку из ошибки (или `null`), состояние сервера помечается подтверждённым;
  - отметка «Пройден» в кэше каталога и бандла выравнивается по строке из ошибки: `refreshQuestsCatalogCompletion`, если она пройдена, иначе `resetQuestsCatalogCompletion`.
- `resetQuestsCatalogCompletion` снимает только стоящую отметку. Отмена первой загрузки бандла или каталога откатывает запрос в `pending` без повтора, а очередь сбрасывает отметку и на старте приложения, пока бандл ещё грузится.

### D5. Слияние разных поколений — целиком новее, без объединения

`mergeQuestProgress(a, b)`: если у обоих `serverId > 0` и они различаются, результатом становится снапшот с большим `serverId`, а флаги считаются от него. При равных поколениях или одном нулевом — прежнее объединение, а поколение берётся ненулевое.

`serverId` входит в локальный отпечаток: усвоение поколения — это изменение локальной записи, его надо сохранить. В серверный отпечаток `serverId` не входит, потому что в payload сервера такого поля нет и `serverNeedsPush` не должен срабатывать от одного поколения.

Правило общее для визарда (локальная копия против сервера), очереди (новый снапшот против лежащего) и писателя.

### D6. Подтверждённое и неизвестное состояние сервера

- `useQuestProgressSync` отдаёт `progressMissing`:
  - `true` — чтение вернуло 404, удаление подтверждено или несовпадение поколения показало, что строки нет;
  - `false` — строка есть или чтения не было / оно упало. Новое чтение сбрасывает прежнее подтверждение: оно могло принадлежать прошлому аккаунту. Удаление, дошедшее уже на другом квесте, состояние текущего не трогает.
- Чтение, подтвердившее, что квест не пройден, снимает отметку «Пройден» в кэше этого устройства. Визард стирает копию при открытии, и отметка не должна её пережить на 30 минут `staleTime`.
- Экран передаёт `NO_SERVER_PROGRESS` с `serverId: null` при подтверждённом отсутствии и прежний пустой снапшот без `serverId` при неизвестном состоянии.
- Поле `serverId` в `initialProgress`:
  - число — строка есть;
  - `null` — сервер подтвердил, что строки нет;
  - `undefined` — неизвестно: гость, упавшее чтение, старые вызывающие.

Альтернатива — стирать запись визарда из хука синхронизации. Отвергнута: хук не знает ключ записи (он строится из `storage_key` бандла и владельца), а второй писатель той же записи гонялся бы с save-эффектом визарда.

### D7. Визард

- **Первое согласование ключа** (ветка слияния полного снапшота):
  - поколение копии > 0, а сервер подтвердил отсутствие строки → засевается пустое состояние;
  - поколение копии > 0, а у строки сервера другое поколение → засевается состояние сервера.

  В обоих случаях `markSeeded=true` (доливать нечего), сбрасывается `completionFinishedAt`, запись хранилища перезаписывается. В остальных случаях — прежнее слияние.
- **Обновления в сессии** (ветка «уже засеян»): то же правило против живого снапшота. При устаревании берётся и курсор сервера, потому что курсор закончившегося прохождения к новому не относится. При усвоении поколения (0 → S) — прежнее объединение, курсор игрока не двигается.
- **Save-эффект** пишет `serverId` из ref в запись хранилища и в payload `onProgressChange`. `resetProgress` засевает пустое состояние с `serverId: 0`.

## Risks / Trade-offs

- [Копии без поколения — записи старой версии или доставленные только очередью до первого открытия — по-прежнему могут воскресить сброшенное] → Это осознанный fallback. Первое же согласование в сети присваивает копии поколение, после этого дыра закрыта.
- [Офлайн-ответы, сделанные на устройстве ПОСЛЕ сброса на другом и до того, как устройство о нём узнало, теряются] → Так задумано: явный сброс побеждает. Зафиксировано в спеке сценарием «Сеть появилась после офлайн-открытия».
- [404 чтения прогресса приходит и для неопубликованного квеста, а экран такого квеста открывается из офлайн-бандла (`fetchQuestByQuestId` отдаёт кэш на любой ошибке)] → `fetchQuestProgress` считает отсутствием строки только 404 без пометки `Quest with quest_id=`. 404 про снятый квест — ошибка чтения: визард копию не стирает, писатель падает этим 404, и очередь снимает запись как постоянный отказ, как было и раньше, когда падал `POST`. Если бэк поменяет текст этой ошибки, поведение откатится к варианту «строки нет»: строка цела, теряются только офлайн-добавки.
- [Ошибка несовпадения прерывает цепочку писателей квеста] → `withQuestProgress` уже изолирует падение: следующий писатель делает своё чтение.
- [`id` за пределами `Number.MAX_SAFE_INTEGER`] → Нереалистично: для этого последовательность должна выдать 2^53 значений.

## Migration Plan

- Миграции данных нет: `serverId` — необязательное поле. Старые записи читаются как `0` (неизвестно) и согласуются при первом контакте с сервером.
- Выкат — штатный web-деплой после review. Нативные сборки получат изменение со следующим релизом, обратная совместимость та же.
- Откат — revert коммита. Прежний код игнорирует лишнее поле: `normalizeQuestProgressSnapshot` и `snapshotFromRecord` читают только известные ключи.

## Validation matrix

| Слой | Проверка |
| --- | --- |
| unit: слияние | разные поколения → целиком новее; 0 + S → объединение с S; отпечатки |
| unit: `withQuestProgress` | поколение совпало → задача; строки нет → несовпадение без `POST`; другая строка → несовпадение с ней |
| unit: очередь | проход выбрасывает запись чужого поколения и продолжает; `deliverOrEnqueue` не кладёт её обратно |
| unit: хук синхронизации | 404 → `progressMissing`; сбой чтения → не подтверждено; несовпадение при флаше → без ретрая, переход на строку/`null` |
| unit: визард | подтверждённое отсутствие + копия с поколением → пусто без отправки; другая строка → сервер целиком; #1803 доливается; поколение попадает в хранилище |
| desktop web (прод после выката) | два контекста одного аккаунта: пройти квест в первом → «Сбросить» во втором → открыть в первом: ни `POST`, ни `PATCH`, квест не начат |
| mobile web (прод) | тот же поток в мобильном viewport, одним проходом |
| Android / iOS | device gate не нужен: нативного кода нет, общий JS покрыт unit и web-проверкой |
| Локали | none — строк нет |
