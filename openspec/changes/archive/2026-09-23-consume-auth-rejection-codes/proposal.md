## Why

Бэкенд #1993 (OpenSpec бэка `prevent-auth-account-enumeration`, прод `de08e8f`) перестал раскрывать существование аккаунта: сброс пароля на любой корректный email отвечает одинаково `200 {code: "password_reset_requested"}`, вход отдаёт машиночитаемый `code` (`invalid_credentials`, а `account_not_activated` — только после проверки пароля). Фронт этот контракт не потребляет: причину отказа входа угадывает по русскому тексту `error` (`utils/authFailure.ts`), а сброс показывает сырую русскую строку сервера и на успех, и на `400` — это нарушает правило #1946 «строка бэкенда не показывается как есть». Форма сброса отличает успех от ошибки регуляркой по русским словам «ошиб|не удалось», поэтому в EN/BE/UK/PL отказ красится как успех.

## What Changes

- Причину отказа входа по email выбирает поле `code` тела `401`: `account_not_activated` — локализованная подсказка активации, `invalid_credentials` и любой другой код — общий локализованный отказ. Текст `error`/`detail`/`message` в выборе участвует только при отсутствии `code` (переходный fallback для старого бэкенда); противоречащий коду текст игнорируется.
- Ответ сброса пароля `2xx` показывается собственной нейтральной локализованной строкой «Если аккаунт с такой почтой существует, мы отправили письмо…» — одинаковой для известного и неизвестного адреса; серверный `message` не показывается.
- `400` сброса — локализованная ошибка некорректного email (существующий ключ `errorsStatic:api.backendErrors.invalidEmail`), `429` — «слишком много попыток», прочие ошибки сервера и сбой связи — локализованные тексты по статусу/транспорту; сырая строка сервера не показывается ни в одной ветке.
- Результат запроса сброса становится структурным (успех/отказ по статусу ответа) вместо строки; форма входа красит сообщение по нему, а не по тексту. **BREAKING** (внутренний контракт): `sendPassword` в сторе/контексте возвращает результат, а не строку; внешних потребителей нет.
- Не входит: изменения бэкенда (контракт #1993 уже на проде), удаление текстового fallback (бэкенд сохраняет `error`/`message` без даты удаления), соц-входы Google/Apple/Facebook, мёртвые `sendPasswordApi`/`ForgotPasswordScreen` (только согласование типа), регистрация и активация.

**Platform impact**: shared — общий JS для desktop web, mobile web, Android и iOS; нативного кода и platform-specific поведения нет, device gate не требуется. Видимый результат проверяется на desktop web и mobile web.

**Localization impact**: all current locales — одна новая строка нейтрального ответа сброса во всех RU/BE/UK/PL/EN через `@/i18n` (ключ `api.auth.resetInstructionsSentShort` заменён по смыслу на `api.auth.passwordResetRequested`); тексты отказа входа и некорректного email переиспользуют существующие ключи.

## Impact

- **Код**: `api/auth.ts` (`loginApi`, `resetPasswordLinkApi`), `utils/authFailure.ts` (`authRejectionCode`, тип результата сброса), `stores/authStore.ts`, `stores/authState.ts`, `context/authContextBase.tsx`, `components/auth/LoginForm.tsx`, `components/user/ForgotPasswordScreen.tsx`, строки в `i18n/locales/*/static/errors_static.ts` и удаление осиротевшего ключа в `i18n/locales/*/generated/shared_02.ts`, тесты в `__tests__/`, feature doc `docs/features/auth.md`.
- **API/данные**: новых запросов и полей нет. Потребляются `POST /api/user/login/` → `401 {code, error}` и `POST /api/user/reset-password-link/` → `200 {code: "password_reset_requested", message}` / `400` сериализатора / `429` throttle.
- **SEO**: none — форма входа, публичных URL, мета и разметки не касается.
- **Доступность**: сообщение остаётся тем же текстовым блоком с `accessibilityLiveRegion="polite"`; меняется только текст и корректность стиля ошибки/успеха.
- **Производительность**: none — число запросов не меняется, тело `200` сброса больше не разбирается.
- **Безопасность**: улучшение — клиент не восстанавливает перечисление аккаунтов: один и тот же ответ для известного и неизвестного email, подсказка активации только по коду, выданному после проверки пароля.
- **Аналитика**: новых событий нет.
- **Зависимости**: backend #1993 — выполнен и на проде; блокеров нет.
- **Fallback/mock policy**: моков не вводится. Текстовый разбор причины входа — только при отсутствии `code` (старый бэкенд); явный `code` всегда главнее текста.
