## Decisions

1. A focused `useMapCitySearch` hook, owned by the recovery component, consumes the canonical `useLocationSearchQuery` with its default limit of seven (limit is not a cache-key dimension). The public endpoint is direct `https://nominatim.openstreetmap.org/search`, with `format=json`, `addressdetails=1` and the active geocoder language. A current settled empty local query of at least three trimmed characters exposes an idle lookup button; only an explicit press arms that exact query. Editing or a pending/error/offline/local-hit transition immediately hides results and disarms the request. No autocomplete, new fetch adapter/cache/provider or automatic retry. A bounded per-consumer throttle covers explicit starts/retries in this JavaScript context, with duplicate in-flight retries suppressed; it cannot prove a global multi-user request limit. Existing `useDebouncedValueWithPending` has a synchronous `unseenChange` comparison (#2218), so query/radius/category/anchor transitions are pending on their first render. Four permanent controls confirm this without changing the data controller.

   Request identity also includes the subscribed active locale through existing `useLocaleRevision`, so language changes disarm before binding the next canonical locale query. The canonical `api/geoQueries.ts` hook gains an optional `userInitiatedOnly` observer policy for this new consumer: reconnect/window-focus/mount background refetch are false only when opted in, and `networkMode: always` makes an explicit offline attempt fail immediately instead of queuing it for a later reconnect after disarm. TanStack's paused retryer otherwise resumes independently of `refetchOnReconnect`; this is covered by an actual online-manager RED regression. Existing callers receive no option overrides (including their online/paused behavior), and query key, cache lifetime, default limit, retries and AbortSignal remain unchanged. This avoids a second cache or transport owner. Tests drive real focus/online managers and a real locale change to catch background bypasses of the explicit/rate gate; the offline test asserts one explicit failed attempt and zero additional attempts after disarm/reconnect, not zero total transport.
2. Verified settlement results require finite, nonblank WGS84 coordinates, a supported settlement/administrative type, and object identity matching a settlement address field (`city`, `town`, `village`, `municipality`). Use `name` when present, otherwise the first comma-separated `display_name` segment: the canonical legacy JSON output does not guarantee `name`. This rejects a castle whose address includes the searched city while accepting official JSON-shaped settlement fixtures. Preserve API-owned disambiguating region/country. Invalid results fail closed.
3. Add one explicit validated `searchAtCity` action to `components/map-core/useMapController.ts`: cancel pending GPS centering, clear the selected POI, set `searchAreaCenter` with manual source, and focus the current map API. Preserve filters and trusted user location. The screen's existing web feedback owns the caller. Reusing `focusOnCoord` alone is rejected because it leaves list/circle queries at Minsk. Updating GPS coordinates is rejected because it creates a false route origin. AI consumers remain untouched.
4. Compose `MapCitySearchRecovery` from existing text/Chip primitives in `FiltersPanelRadiusSection`; keep the existing empty/status/expansion controls. A shared `LinkPressable` entry goes to `/quests/map`. That existing primitive preserves SPA/modified-click behavior and native Expo Link semantics. A quest overlay is rejected because it duplicates the separate catalog model, loading and renderer integration. Destination city parameters are rejected: the existing route accepts none and uses its catalog center.

## Risks / Trade-offs

- Stale asynchronous offers → locale/query-key identity, current empty-status gating and selection-time validation.
- City camera changes but list remains at old anchor → one controller action updates both, integration regression asserts both effects.
- Late GPS steals city view → cancel pending explicit centering; live GPS remains separate from manual anchor.
- Provider returns unusual settlement metadata → fail closed and retain radius expansion; production Несвиж acceptance validates the real response after review.
- Long translations/display names → wrapping labels, shared controls and mobile-first screenshots; no clipping-only meaning removal.

## Other Contracts

Accessibility: localized status live region, labelled city controls and link semantics using existing primitives/tokens. Localization: five production locales through reactive i18n, API names unchanged. Performance: no city request until explicit lookup, existing cache/AbortSignal/default limit and one-second rapid-action protection, no provider request per keystroke. Security: bounded coordinate validation and constant internal quest href. Results show OpenStreetMap contributor credit independently of basemap, with the fixed copyright URL opened only via `openExternalUrl`; external-link governance is included. Analytics: preserve current search events and #3044 owner; no new event/parameter/PII. SEO/static URLs/canonicals/robots/sitemap and media geometry are unchanged. Auth, storage migrations, paid resources and route geometry are not involved.

Provider evidence (official documentation, not a live API probe): [Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/) forbids client autocomplete and requires a maximum one request per second for the whole application, identification, attribution and caching. This change adds explicit lookup and bounded client protection; existing cross-consumer/global traffic and service switching remain adapter-owner concerns, not claims of this task. [JSON output contract](https://nominatim.org/release-docs/latest/api/Output/#json) documents `type`, coordinates, `display_name` and address details, without guaranteeing `name`.
