## Context

Мотивация и границы — [proposal.md](proposal.md). История: #1518 и `TRAVEL-POINT-CATEGORY-DICTIONARY-001`; другой владелец HTTP-заголовков — #1436, его прежний статус `done` не доказывает текущую свежесть тела ответа.

Подтверждённая цепочка в текущем исходном коде:

1. `hooks/useTravelFilters.ts:419-446` запускает принудительное обновление при смене `currentStep`. В `:427` повтор того же шага отклоняется до проверки времени. Возврат во вкладку не входит в зависимости и не имеет обработчика.
2. `components/travel/upsert/useUpsertTravelController.ts:210-213` получает только `filters` и `isLoading`; `refetchPointCategories` в редакторы не передаётся. Поэтому открытие категорий на том же шаге тоже не обновляет справочник.
3. `components/map/EditMarkerModal.tsx:42-65` строит варианты из переданного массива и локально созданных категорий. `components/forms/SimpleMultiSelect.tsx:89-102` фильтрует `data` и умеет реагировать на его обновление, но не запрашивает данные самостоятельно.
4. `api/miscOptimized.ts:79-125` уже поддерживает обход TTL и дедупликацию. `api/misc.ts:619-644` отправляет принудительный запрос с `_fresh` и `cache: reload`. Сетевой обход существует; в описанном сценарии отсутствует событие, которое его вызывает.

Это доказанный пробел исходного кода, согласующийся со скриншотами. Живое воспроизведение пользовательской сессии, актуальные заголовки production и состояние её кэша не измерялись. В apply до исправления требуется локальная отрицательная проба на том же шаге. Независимый source-review подтвердил отсутствие альтернативного обновления: wizard использует локальный state, общий API-кэш не имеет подписки на него, а `refetchOnWindowFocus` глобально выключен в `utils/reactQueryConfig.ts:55`.

Старые тесты `__tests__/hooks/useTravelFilters.test.ts:203-365` покрывают вход в шаг, 60-секундное окно и гонку стартовой загрузки, но не возврат во вкладку. Строка «Добавить категорию “пла”» не доказывает дефект: совпадение для запрета создания полное, а поиск — по подстроке.

## Goals / Non-Goals

**Goals:** один браузерный триггер свежести у текущего владельца данных, сохранение текущих значений формы и конечный предел запросов; требования — [spec.md](specs/travel-point-category-freshness/spec.md).

**Non-Goals:** новая система server state, отдельный словарь в каждой модалке, передача новых props через всё дерево карты, изменения native AppState, периодический опрос и отдельная кнопка обновления.

## Decisions

### 1. Обновлять при возвращении в активный редактор

В `useTravelFilters` добавить браузерную подписку на уход/возврат окна (`blur`/`focus`) и скрытие/появление вкладки (`visibilitychange`). Она действует только на шагах 2/3, проверяет наличие browser globals и снимается при смене области/размонтировании.

Состояние «пользователь уходил» отмечается один раз и сбрасывается до запуска async-операции. Последовательность `visible` + `focus` одного возврата не создаёт два намерения обновления. Входной фокус без предшествующего ухода и перемещение фокуса внутри поля не запрашивают справочник. Подписка должна быть стабильной при обновлении списка; иначе reset флага между парными событиями снова допускает дубли.

Явный возврат обходит 60-секундное окно шагов: категория могла быть создана за несколько секунд. После начала такого обновления его время учитывается и обычным step-троттлингом. Не добавлять таймерный polling.

Отклонены: общий refetch всех статических query при focus (затронет каталоги и страны), onOpen-обновления в каждой модалке (вторая политика и широкое props-прокидывание), full reload (потеря контекста), один только `visibilitychange` (другое окно может не скрывать вкладку).

### 2. Не терять возврат за медленным запросом

Текущий `refetchPointCategories` возвращает управление сразу при `inFlight` (`:356`). Для нового триггера этого недостаточно: старый ответ мог быть сформирован до добавления категории.

Хранить не очередь событий, а одно отложенное намерение свежести последнего возврата. Если запрос начат до него, дождаться завершения и выполнить один свежий запрос; если после — присоединиться. Уход с шага/размонтирование снимает отложенное намерение. Повторные события одного возврата его не размножают.

Проверить это не только у хука, но и у общего `loadCachedDictionary`: он присоединяет `force` к любому уже выполняющемуся forced-запросу, включая более ранний запрос другого потребителя. При необходимости добавить туда узкую отметку требуемой свежести/начала запроса и одно объединённое следующее обновление. Существующие вызовы без этой опции сохраняют прежнюю дедупликацию. Не отключать дедупликацию глобально и не создавать второй cache helper. Выбор имени внутренней опции — часть реализации, внешний HTTP-контракт не меняется.

Отклонены: безусловно пропускать событие при `inFlight` (повторяет баг); параллельно отправлять запрос на каждое событие (лишняя сеть и гонки); всегда выполнять два forced-запроса (лишняя сеть без необходимости).

### 3. Не менять форму и правила поиска

Переиспользовать `refetchPointCategories({ force: true, silent: true })` и защиту ревизии стартовой загрузки. Обновляется только `categoryTravelAddress`, выбранные id принадлежат форме и не переписываются. Модалки, `MultiSelectField` и `SimpleMultiSelect` получают новые варианты обычным обновлением props; их повторный mount недопустим.

Тестировать отдельно запрос `пла` (категория присутствует) и полное `Планетарий` (нет предложения создать это же имя). Не менять правила создания на основании ошибочной интерпретации короткого префикса.

### Data/API и ошибки

Источник: существующий публичный `GET /api/getFiltersTravel/?_fresh=<timestamp>`, HTTP 200 с `FilterDictionaries`, в том числе `categoryTravelAddress: { id: number, name: string }[]`. Хук приводит id к строкам для формы. Auth, permissions и форма ответа не меняются.

Сетевые ошибки сохраняют последний успешный словарь; существующий fallback не считать доказательством свежести. Следующий действительный возврат снова допускает запрос. Валидный пустой массив не запускает повторный эффект/цикл и не меняет id выбранных категорий в сохранённых данных. Если реальный API не содержит только что сохранённую запись, клиент её не выдумывает; причина передаётся backend-владельцу с точной read-only пробой.

### Ownership и проверки

Планируемые продуктовые пути: `hooks/useTravelFilters.ts`; узкое дополнение `api/miscOptimized.ts` только для доказанной гонки старого forced-запроса. Тесты расширяются в `__tests__/hooks/useTravelFilters.test.ts`, `__tests__/api/miscOptimized.test.ts`, существующем `e2e/travel-wizard.spec.ts`. Соседние consumers — `utils/pointCategoryDictionaryQuery.ts`, `utils/queryClientStaticPrefetch.ts`, `components/travel/hooks/usePointListCategoryDictionaryModel.ts`; не переписывать их без подтверждённой необходимости.

`../metravel-backend`, nginx, scripts, конфигурация приложений и workflows не редактируются. Для реальной приёмки создавать только собственные данные локального API; затем удалить только созданные записи по сохранённым id. Нет неявного разрешения создавать категории на production.

## Risks / Trade-offs

- Парные события или picker диалог вызывают дополнительную активацию → один armed-флаг и замер числа запросов; никаких обработчиков focus на каждом поле.
- Событие теряется за старой загрузкой → одно отложенное намерение и тест с задержанным старым ответом, включая общий helper.
- SSR/native не имеют DOM → browser guard, проверка выполнения без `window`/`document`, без импорта браузерных побочных эффектов на уровне модуля.
- HTTP 200 содержит устаревший массив → сравнивать точный новый id/name в API и UI; отдельно фиксировать отсутствующий контракт.
- Категория появляется после запроса без прежнего выбора → проверять выбранный id и текст поиска во время/после ответа; не размонтировать форму.

SEO, media, analytics и визуальная геометрия не меняются. Accessibility: сохранить активное поле и клавиатурное управление; новых labels нет. Security: новые данные проходят существующую нормализацию, токены и admin-права в frontend не добавляются. Bundle: новых зависимостей нет.

## Validation matrix

Baseline: скриншоты показывают отсутствие новой категории при наличии прежних. Исходный код предсказывает ноль запросов только от возврата на прежний шаг; это ещё не измеренный runtime baseline.

| Поверхность | Проверка | Критерий |
| --- | --- | --- |
| Hook/API | Целевые Jest в существующих suites | Возврат на неизменном шаге, быстрый возврат <60 с, дубли событий, старый forced-запрос, unmount/другой шаг, offline/empty, сохранение свежей ревизии |
| Desktop web 1440×900 | Локальный wizard + реальный API; собственная категория создана после загрузки исходного списка | После возврата один новый GET, новый id/name в ответе и результатах ≤5 с; прежний выбор и поля сохранены |
| Mobile web 390×844 | Тот же сценарий и открытый поиск во время обновления | Те же id, request count, фокус/ввод, без новых console errors; скриншоты до/после |
| Shared соседние consumers | Тесты cache/query/prefetch | Дедупликация, порядок ответов и форма query key без регрессий |
| Android/iOS/SSR | Source и unit-проверка границы DOM | Новый browser trigger не выполняется вне web; device gate отсутствует, пока native код не затронут |
| RU/BE/UK/PL/EN | Сверка diff | Нет изменений app-owned строк/форматирования; новые имена категорий не переводятся клиентом |

Команды после отдельного apply: `node scripts/run-with-quality-gate-lock.js task-1518-categories -- npx jest __tests__/hooks/useTravelFilters.test.ts __tests__/api/miscOptimized.test.ts __tests__/utils/queryClientStaticPrefetch.test.ts __tests__/hooks/usePointListCategoryDictionaryModel.test.ts --runInBand`; `npm run check:fast`; Playwright через тот же wrapper с новым именованным сценарием в существующем `e2e/travel-wizard.spec.ts`. Управляемая Playwright-подмена годится для гонок, но не заменяет отдельную живую локальную проверку: не подменять ответы filters/admin в ней. Измерять тело ответа и request count, а не только 200. Сохранить console/network и снимки в ignored `.codex-temp/`. Независимый `$metravel-code-reviewer` проверяет полный task diff после изменений и исправляет подтверждённые замечания.

## Migration Plan

Данных и схемы мигрировать не нужно. Сначала отрицательная локальная проба, затем исправление и тесты; после отдельного разрешения deploy — повторить production-сценарий на уже созданной пользователем категории, не создавая новых записей. До этого не заявлять исправление production.

Откат: удалить только новый foreground-триггер и связанную опцию свежести, сохранив предыдущий step-refresh и защиту ревизии. Черновики и категории пользователя не меняются при откате. Commit/push/deploy не входят в разрешение этого планирования.
