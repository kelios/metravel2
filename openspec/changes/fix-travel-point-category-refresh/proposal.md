## Why

Закрытая задача #1518 повторилась: 28.08.2026 админка подтвердила создание активной категории «Планетарий», но поиск `пла` в редакторе точки её не показал. Предыдущее исправление обновляет справочник при смене шага; возврат из админки в уже открытый шаг не запускает обновление.

Problem key: `TRAVEL-POINT-CATEGORY-DICTIONARY-001`. Каноническая карточка — #1518, решение истории — `reuse` после её переоткрытия; #1436 остаётся связанной backend-задачей. Скриншоты доказывают симптом, исходный код — отсутствие события обновления. Точная последовательность сетевых ответов в пользовательской сессии не измерена.

## What Changes

- После возвращения во вкладку/окно редактора на шаге с точками справочник запрашивается заново без смены шага и перезагрузки страницы.
- Один возврат вызывает не более одного нового запроса; парные браузерные события объединяются. Обычные переходы 2 → 3 → 2 сохраняют ограничение одного обновления за 60 секунд.
- Запрос, начатый до возврата, не подменяет проверку свежести после возврата. Несколько событий во время загрузки не образуют очередь из повторных запросов.
- Уже выбранные категории, поиск, адрес, фото и страны остаются на экране. При ошибке сохраняется последний доступный справочник; появление новой категории не объявляется успешным без неё в ответе и интерфейсе.
- Регрессия проверяется добавлением ранее отсутствовавшей категории после открытия редактора; прежняя проверка уже известного id=227 остаётся здоровым контролем.

Goal: При успешном ответе, содержащем новую активную категорию, она видна по префиксу в текущем редакторе не позднее 5 секунд после получения ответа. Ноль дополнительных запросов от дублирующих событий одного возврата и ноль фоновых опросов.

User-visible result: После добавления категории в админке можно вернуться к открытой точке и выбрать её, не теряя правки.

Existing behavior to preserve: 60-секундный предел для обычных переходов шагов; обход клиентского кэша существующим загрузчиком; сохранение свежего ответа при гонке стартовой загрузки; выбор нескольких категорий; текущие правила создания категории. Для префикса `пла` строка создания допустима; для полного существующего имени она не должна предлагать дубль.

Non-goals: Изменение API/БД/nginx, удаление дублей категорий, изменение фото (#1599), общий рефакторинг словарей, обновления без возвращения к редактору, native lifecycle и новые тексты интерфейса.

## Capabilities

### New Capabilities

- `travel-point-category-freshness`: свежесть категорий при возврате к открытому редактору, сохранение пользовательского состояния и ограничение запросов.

### Modified Capabilities

Нет: соответствующей living spec в текущем репозитории нет.

## Impact

Platform impact: desktop web и mobile web. Общий хук получает только браузерный триггер; Android/iOS не получают новых lifecycle-обработчиков, их текущая загрузка сохраняется.

Localization impact: none — RU/BE/UK/PL/EN, тексты и форматирование без изменений. Имена категорий остаются содержимым API.

Dependencies: Существующий `GET /api/getFiltersTravel/` должен возвращать новую активную запись в `categoryTravelAddress: { id: number, name: string }[]`. Нового backend-контракта нет. Если прямой ответ не содержит сохранённую запись, это отдельная диагностика владельца backend, а не основание подставить её на клиенте.

Fallback/mock policy: Сохранить последний полученный справочник при ошибке. Управляемые ответы допустимы для гонок и ошибок в тестах; приёмка требует локального реального API и собственной тестовой категории с очисткой. Production-записи для теста не создаются.

Impact summary: Изменение планируется в `hooks/useTravelFilters.ts`, ближайших тестах и сценарии визарда; общий API/cache helper `api/miscOptimized.ts` переиспользуется и при необходимости получает узкое различение запроса до/после возврата без новой формы HTTP API. API/data — форма не меняется; SEO — публичные URL и метаданные не меняются; accessibility — сохраняются фокус и ввод; performance — один запрос на возврат, без polling; security — новые полномочия и секреты не нужны; analytics — события без изменений.

Open questions: Материальных продуктовых вопросов нет. Перед исправлением локально подтвердить сценарий возврата на неизменном шаге; если свежий API не содержит категорию, зафиксировать отдельную зависимость и не объявлять frontend-причину подтверждённой для всего инцидента.

Planning boundary: Эти артефакты не разрешают реализацию, commit, push или deploy. Apply начинается отдельным сообщением пользователя.
