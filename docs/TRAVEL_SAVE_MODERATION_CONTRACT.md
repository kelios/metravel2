# Контракт сохранения и модерации travel

Актуализировано: 2026-10-22 (#2693).

Load-bearing контракт для `components/travel/**`,
`hooks/useTravelFormPersistence.ts`, `hooks/useTravelWizard.ts` и
`api/misc.ts::saveFormData`.

## Главный инвариант

**Save ≠ moderate.**

- Content-save, autosave и инкрементальное сохранение точки персистят данные как
  есть и не меняют publication status.
- Полнота для модерации проверяется только при явном действии пользователя
  «Отправить на модерацию»/«Опубликовать».
- После модерации автор может свободно дополнять travel; обычная правка не
  запускает повторную moderation validation.
- Ошибка backend endpoint не маскируется fake-success или локальным
  «успешно сохранено».

Пользовательские данные нельзя терять ради прохождения validation.

## Status model

Источник истины — `publication_status`, который читает общий адаптер
`utils/travelPublicationStatus.ts`. `moderation_decision` описывает прошлое
решение и не определяет состояние статьи.

| `publication_status` | legacy `publish` / `moderation` | Чип в мастере |
| --- | --- | --- |
| `draft` | false / false | «Черновик» |
| `pending_review` | false / false | «Отправлено на модерацию» |
| `approved` | false / true | «Одобрено» |
| `published` | true / true | «Опубликовано» |

Canonical всегда имеет приоритет над флагами. Только при отсутствующем
`publication_status` разрешён legacy fallback: false/false → draft,
true/false → pending_review, false/true → approved, true/true → published.
`null`, пустое или неизвестное canonical значение сохраняется в форме,
показывает локализованную ошибку и запрещает запись, включая content PATCH.
Два состояния false/false современного API различаются только canonical.

## Frontend flow

- Глобальный autosave живёт в `hooks/useTravelFormPersistence.ts`, действует
  во всех четырёх состояниях и сохраняет прежние hydration/debounce guards.
- Инкрементальное сохранение route point идёт из
  `components/travel/TravelWizardStepRoute.tsx` через `onManualSave`.
- Полный payload собирается единственным `buildTravelPublicationWrite`.
  Он удаляет `publish`, `moderation`, исторические `moderation_decision` и
  `moderation_decision_reason`; обычный save не создаёт нового решения.
- Состояние формы и выбранное следующее действие UI разделены. Только
  подтверждённый ответ меняет состояние; ошибки оставляют текст и комментарий
  доступными для повторной попытки.
- Команда ждёт предыдущие ручные и уже отправленный autosave запросы, после
  чего отменяет отложенный autosave. Обычные сохранения из очереди берут
  актуальный canonical, поэтому старый override не возвращает прежний статус.
- Восстановление локального черновика возвращает содержимое, сохраняя текущее
  серверное состояние публикации. Статус из старого локального снимка не
  становится командой; неизвестный текущий canonical также остаётся видимым.

| Явное действие (`intent`) | `publication_status` | `enforce_moderation_validation` | Причина |
| --- | --- | --- | --- |
| `save` / `autosave` | текущее S | false | отсутствует |
| `submit` | pending_review | true | отсутствует |
| `approve` | published | false | отсутствует |
| `reject` | draft | false | trim, 1–2000 символов |

`moderationDecisionReason` — разовый параметр options только для `reject`;
он не переносится в форму и не повторяется при следующем save/approve.
Подготовка placeholder-полей использует адаптер: pending_review с false/false
не считается черновиком. Завершение мастера также читает canonical.

Обе responsive кнопки обычного сохранения в `TravelWizardHeader` используют
общий обработчик UI-события: он ожидает `onSave: () => void | Promise<unknown>`
и принимает уже показанную persistence-ошибку без повторного toast. Неожиданная
ошибка callback получает обычный error toast. Сам persistence Promise остаётся
отклонённым для программных вызовов и команд модерации; UI не объявляет успех и
позволяет повторить сохранение.

### Design evidence — состояния публикации (#2693)

Сохраняются summary, checklist, панель модератора и ConfirmDialog в прежнем
порядке на desktop web 1440px и mobile web 390px. Чип отражает четыре canonical
состояния сразу после загрузки. У pending_review панель модератора доступна
администратору без переключения отправки; автор видит ожидание и может сохранить
правку. Обычная кнопка «Сохранить» не снимает статью с модерации и не переводит
approved/published в draft. Выбор отправки — отдельное действие для draft.
При неизвестном canonical видна ошибка, запись отключена, форма остаётся.
При ошибке сети состояние не объявляется изменённым, причина reject остаётся.

### Design evidence — обязательная причина отклонения (#2685)

Существующая панель модератора и `ConfirmDialog`, desktop web 1440px и mobile
web 390px: пустая или пробельная причина оставляет кнопку «Отклонить» и
подтверждение неактивными; под полем видна подсказка «Укажите причину отклонения».
При непустом комментарии действие доступно, пробелы по краям убираются, поле
ограничено 2000 символами. Подсказка переведена на RU/BE/UK/PL/EN. При ошибке
сохранения статус восстанавливается, комментарий остаётся для повторной попытки.
Личное сообщение автору сохраняется как дополнительный канал, пока #2669 не
добавила показ причины в мастере. В `testing` проверяются обе ширины, состояния
пусто/пробелы/причина/ошибка, консоль и реальный payload upsert.

Путей записи два, и выбор между ними делает `utils/travelContentSaveDelta.ts`
(#1516):

| путь | когда | эндпоинт |
| --- | --- | --- |
| content-save | фоновый автосейв, где относительно подтверждённого состояния изменился ТОЛЬКО текст (`name`, `description`, `plus`, `minus`, `recommendation`) существующей статьи | `PATCH /travels/{id}/content/` |
| full-replace | структурные правки (точки, галерея, обложка, справочники), создание статьи, ручное сохранение, публикация, а также любое сомнение | `PUT /travels/upsert/` |

Узкий путь не запускает модерационную валидацию, не трогает структуру статьи и
не имеет права быть слабее полного: санитизация (`sanitizeInput`,
`sanitizeRichText`, `stripBase64Images`), лимиты длины, гейт гидратации формы и
анти-обнуление действуют на обоих. Содержательно пустой payload у статьи с id
узким путём не уходит вовсе — план отдаёт его полному пути, где он блокируется.

Там же, на обоих путях, стоит гейт FAQ-разметки (#1764): тело статьи, у которого
санитизация уменьшила число пар `<details>/<summary>` или сняла секцию
`seo-faq`, на сервер не уходит — сохранение падает с
`errorsStatic:api.misc.faqMarkupWouldBeLost`. Санитайзер стоит на пути ЗАПИСИ,
поэтому его allowlist вычёркивает теги не из кадра, а из хранимого тела: до
`ad2fdc9eb` (26.07.2026) в нём не было `details`/`summary`, и статьи 554 и 134
молча потеряли FAQPage. Что считается разметкой — `utils/faqDisclosureMarkup.ts`.

Ручное сохранение и команды всегда идут через
`api/misc.ts::saveFormData` и `PUT /travels/upsert/`. Полный запрос содержит
`publication_status` и `enforce_moderation_validation` по таблице действий,
без legacy-флагов. Узкий `PATCH /travels/{id}/content/` содержит только
изменённые текстовые поля: status, флаги, enforce и причина туда не попадают.

`validateReadyForModeration` запускается на frontend для `intent='submit'`.
Обычный save, autosave и сохранение точки не требуют полноты для публикации.

Route-point save отправляется сразу, включая новую точку без категории: ей нужен
server id для последующей загрузки media. Старые mitigation/defer guards для
uncategorized point удалены и не должны возвращаться.

## Expected backend behavior

Backend должен применять проверку полноты только когда одновременно:

1. текущая запись ещё не промодерирована;
2. `enforce_moderation_validation === true`.

Во всех остальных случаях upsert сохраняет контент без publication validation.
Frontend workspace не редактирует реализацию Django; mismatch подтверждается
read-only probe и оформляется как `area=back` task с Task Contract.

Нельзя обходить backend mismatch новым mock fallback или возвращением
frontend-дефера, который снова создаёт риск потери данных.

## Safe change checklist

- [ ] `save/autosave` и явные `submit/approve/reject` не смешаны.
- [ ] Текущий canonical не трактуется как команда; legacy-флаги не пишутся.
- [ ] Autosave/route save не блокируется publication validation.
- [ ] Полный payload не перетирает более свежий form snapshot.
- [ ] Ошибка сохранения видна пользователю и не превращается в fake success.
- [ ] Draft recovery остаётся отдельным слоем по
      `docs/TRAVEL_DRAFT_RECOVERY.md`.

## Design evidence — решение модерации для автора (#2669)

Нормативный макет до реализации, 2026-10-22. Эта секция дополняет #2693,
не меняя источник publication status и **Save ≠ moderate**. Обратная связь
видна в мастере автору/суперпользователю и в собственном списке поездок;
публичные профили и каталог не показывают её даже при случайном наличии полей.
Доступность редактирования сама по себе не включает приватный блок в каталоге.

### Данные и матрица состояний

Авторизованный detail/list читается с необязательными полями
`moderation_decision: 'approved' | 'rejected' | null`,
`moderation_decision_reason: string`, `moderation_decided_at: ISO 8601 | null`.
Это результат прежнего решения, а не команда и не новое состояние публикации.
Decision отсутствует/неизвестно/имеет неверный тип — нет обратной связи решения,
сохраняется прежний показ canonical или legacy fallback. Отсутствующий reason
не отменяет известное отклонение; причина не выдумывается. Неверная дата
не показывается. Invalid canonical не становится валидным из-за решения.

| Текущий canonical | `moderation_decision` | Чип/обратная связь в обеих авторских поверхностях | Действие исправления |
| --- | --- | --- | --- |
| `draft` | `rejected` | «Отклонено»; непустая причина и валидная дата ниже | «Исправить и отправить снова» |
| `draft` | `approved` / null / отсутствует / неизвестно | «Черновик»; без старого решения | нет |
| `pending_review` | любое | «Отправлено на модерацию»; без старого решения | нет |
| `approved` | любое | «Одобрено»; без старого решения | нет |
| `published` | `approved` | «Опубликовано»; валидная дата решения ниже, без причины отклонения | нет |
| `published` | другое / null / отсутствует | «Опубликовано»; без исторической причины/даты | нет |
| invalid canonical (в том числе null/пустой/неизвестный) | любое | прежняя ошибка неизвестного статуса; нет ложного решения | нет; прежний write-block сохранён |
| canonical отсутствует | любое | сначала разрешённый legacy fallback из Status model, затем строки выше | по разрешённому состоянию |

«Отклонено» — представление `draft + rejected`, не пятое серверное состояние.
Дублировать рядом чип «Черновик» не требуется. Например, автор снял ранее
одобренную статью с публикации: `draft + approved` остаётся «Черновик»,
а не «Опубликовано». После нового подтверждённого submit сервер сбрасывает
решение, причину и дату; до ответа UI не объявляет переход состоявшимся.

### Расположение и раскрытие — 1440px и 390px

Сохраняются оболочка мастера, порядок summary → checklist → admin panel,
сеточные колонки профиля, обложка и её геометрия. Иконки — существующие Feather,
цвета — тематические status tokens; новый арт не нужен.

| Поверхность | Существующий слот | Нормативное содержимое |
| --- | --- | --- |
| Финальный шаг мастера | `PublishStatusSummaryPanel`, существующая карточка «Текущий статус», до выбора отправки и checklist | чип по матрице → hint сохранения → причина при отклонении / дата актуального решения → действие исправления при отклонении |
| Профиль → собственные поездки и `/metravel` | `ProfileTravelGrid`/список → `RenderTravelItem` → `TravelListItem`, прежний status/meta slot после заголовка, приватный feedback footer в той же ячейке, вне ссылки карточки | чип по матрице → причина при отклонении / дата актуального решения → действие исправления при отклонении; год, engagement и прочая мета сохраняются |

Нормативный текстовый макет отклонённой статьи на обеих ширинах:

```text
[Отклонено]
Причина: <текст модератора, не более двух строк в превью>
[Подробнее]                  <дата решения, только если валидна>
[Исправить и отправить снова]
```

Это расширение существующих слотов, не новая карточка над формой или сеткой.
На 390px строки и полная подпись действия переносятся без горизонтального
скролла. Чип не выдавливает причину в остаток узкой горизонтальной строки.
В списке высота закрытых карточек в одной секции остаётся одинаковой:
обложка прежняя, контейнер контента обеспечивает общий минимум для status/
двух строк причины/даты/действия. Отсутствующие поля не получают фиктивный
текст или видимый пустой блок. Появление решения не меняет ширины колонок.

Длинная причина ограничена двумя строками в превью. Действие «Подробнее»
открывает существующий `InfoSheet` с полным исходным plain text; закрытие
возвращает к превью и фокус к открывшему контролу. Весь текст доступен скринридеру
в листе; переносы строк и длинные слова не обрезаются. Раскрытие не растягивает
высоту карточки в сетке. Короткую причину можно прочитать без раскрытия;
одинаковое действие «Подробнее» допустимо для любой непустой причины.
Нельзя скрывать единственный доступ к полному тексту по порогу числа символов:
две строки зависят от ширины, шрифта и локали. Допустим единый контрол без
измерения overflow; дополнительный measurement-hook для этого не нужен.
При пустой причине нет строки «Причина», «Подробнее» или выдуманного объяснения;
чип и исправление остаются. Дата решения форматируется через `i18n/format.ts`
только для `draft + rejected` и `published + approved`; для остальных сочетаний,
при отсутствии или невалидной дате весь её блок отсутствует.

Оба действия — обычные доступные контроли с видимой подписью, keyboard/focus
и touch target из дизайн-системы. В web-карточке они вынесены из `<a>` по уже
существующему hoist-паттерну `TravelListItem`; «Подробнее» не открывает статью,
а исправление не срабатывает дважды. Новых вложенных button/link нет.

### Исправление, ошибки и локализация

- В списке действие открывает существующий `/travel/:id` с прежним returnTo.
  В мастере оно использует существующий `onStepSelect(1)` для первого шага
  редактирования. Переход не вызывает save/submit, не меняет переключатель
  отправки и не сбрасывает решение. После исправлений пользователь отдельно
  выбирает существующее явное «Отправить на модерацию».
- Обычные save/autosave/full/PATCH не записывают decision/reason/date и не
  превращаются в submit. Успешный same-state save сохраняет обратную связь;
  подтверждённый переход на pending убирает старое решение. Ошибка сохраняет
  содержимое и предыдущий подтверждённый статус; fake-success запрещён.
- Authoritative full read и восстановление локального черновика берут все три
  исторических поля только из актуальной серверной записи, включая отсутствие
  и null: старые local snapshot поля не возвращаются. Частичный content-save
  ответ без metadata сохраняет ранее подтверждённые серверные поля и не владеет
  ими. Явный null в полном authoritative ответе очищает metadata; тип
  `TravelContentSaveResponse` не содержит этих полей и не расширяется ради
  гипотетического null. Мемоизация карточки учитывает canonical и все три поля, поэтому
  refetch после решения/повторной отправки обновляет чип и причину.
- Первоначальная загрузка использует прежние skeleton/loading/error состояния:
  не вспыхивает «Отклонено»/«Опубликовано» до ответа. Ошибка загрузки не становится
  отсутствующим решением. При смене статьи/аккаунта старый приватный блок
  не переносится на другую запись; новых запросов ради feedback нет.
- List caller явно включает feedback только на собственных авторских вкладках
  и `/metravel`; дополнительно совпадает viewer с owner id. `canEdit` или
  superuser флаг сами по себе не включают его на других поверхностях.
  Сокрытие прежнего дублирующего чипа — только presentation: `isDraft`,
  навигация, фильтры и счётчики остаются canonical.
- App-owned подписи «Отклонено», «Причина», «Подробнее», дата/состояния a11y,
  «Исправить и отправить снова» принадлежат общему travel namespace и добавляются
  на RU/BE/UK/PL/EN; предпочтительно переиспользовать существующие смысловые ключи.
  Сам текст модератора не переводится и не интерпретируется как HTML/ссылка.

### Проверяемая матрица приёмки

До runtime: unit-тесты матрицы canonical × decision, optional/unknown полей,
нормализации detail/profile, write exclusion всех трёх исторических полей,
Save ≠ moderate, приватности и callback действий; затем i18n, static и независимое
review-and-fix по полному task diff. Browser/API QA — только в `testing`.

В `testing` после штатного выката: 1440px и 390px, все пять локалей, состояния
draft/rejected с короткой и длинной причиной, published/approved, pending после
повторного submit, старый payload без решения, unknown canonical, loading/error.
Проверяются светлая/тёмная тема, полная причина и фокус после закрытия, отсутствие
overflow/вложенных интерактивных узлов, одинаковая закрытая геометрия и console.
Реальные ответы detail/list и payload save/submit доказывают договор полей;
переключение на публичный контекст/другого пользователя не раскрывает причину.
Production QA использует только одноразового обычного автора и его тестовые
статьи; разрешённый QA superuser одобряет/отклоняет их. После прогона fixture
и побочные эффекты удаляются с readback. Реальные статьи и owner-аккаунт не нужны.
