# Локальный AI-помощник на данных metravel.by — архитектура и план

> **Обновление 17.10.2026 (вечер).** Владелец отклонил вариант A (хостед-API
> Claude Haiku): «подменять — не вариант». Принято: собственная модель,
> дообученная на корпусе сайта, на нашем сервере. Разделы 1, 4 и 7 ниже
> описывают первую версию плана; действующее решение и карточки — раздел 8.

Статус: предложение (17.10.2026), решение владельца не принято.
Вопрос владельца: поставить на сервер локальную бесплатную модель, которая
«обучится» на материалах сайта, помогает составлять статьи (знает, какой
материал уже есть) и помогает пользователям подбирать маршруты/статьи/квесты.

## 1. Короткий ответ

1. **«Обучать» модель на сайте не нужно и вредно.** Фактические знания в
   маленькую модель дообучением не кладутся надёжно (FineTuneBench: ~37 %
   усвоения новых фактов, ~19 % — обновлений), а контент сайта меняется
   каждую неделю. Правильный механизм — **RAG**: индекс контента сайта +
   любая модель, которая отвечает по найденным фрагментам. Дообучение
   (LoRA) имеет смысл только для стиля «как пишет Юля», и то позже.
2. **На нынешний прод локальную генерирующую модель поставить нельзя.**
   Замер 17.10.2026 по SSH: 1 vCPU (Xeon Skylake, AVX-512 есть), 1.8 ГБ ОЗУ
   (свободно ~850 МБ), диск 15 ГБ занят на 86 %, GPU нет. Самая маленькая
   осмысленная модель (4B, Q4) требует ~3 ГБ ОЗУ и давала бы 1–3 токена/с,
   то есть 1–3 минуты на один ответ при полной блокировке единственного ядра,
   на котором живут Django, PostGIS и nginx.
3. **Что подходит — двухконтурная схема:**
   - **контур редакции** (помощь в написании статей) — локальная модель на
     Mac владельца (M1, 16 ГБ, Ollama уже стоит) поверх индекса сайта; тот же
     индекс отдаётся существующим агентам Claude Code (`travel-writer`,
     `instagram-*`, `quest-*`) как MCP-инструмент «что у нас уже есть»;
   - **контур пользователей** (подбор на сайте) — семантический поиск по
     предрасчитанному индексу (работает на 1 vCPU, без LLM), а текстовый
     ответ «ассистента» — через хостед-API по цене ~$0.0005 за ответ
     (Haiku 5.5) либо через локальную модель после апгрейда VPS.
4. Полностью локальный пользовательский чат возможен только с апгрейдом
   сервера до ≥4 vCPU / 8 ГБ (Hetzner CPX32 после подорожаний 2026 —
   ~€35/мес) и даст 3–6 токенов/с: один пользователь ждёт ответ 20–40 с,
   двое одновременно — вдвое дольше. Для публичного сайта это плохой UX.

## 2. Исходные данные

### 2.1 Контент (прод-API, 17.10.2026)

| источник | объём | размер единицы (без HTML) | всего |
| --- | --- | --- | --- |
| статьи `/api/travels/` | 429 (все автора 1) | медиана 12.7 тыс. символов, среднее 16.5 тыс., макс. 48 тыс. | ~7 млн символов |
| квесты `/api/quests/` | 280 (с локалями ru/be/uk/pl/en) | 9–15 тыс. символов JSON шагов + intro + finale | ~3.5 млн символов (RU) |
| итого | | | ~10.5 млн символов ≈ 3 млн токенов |

Поля статьи, нужные индексу: `description` (rich text), `title`,
`meta_description`, `countryName`, `cityName`, `coordsMeTravel`, `categories`,
`month`/`year`, `number_days`, `plus`/`minus`/`recommendation`, `gallery`.
Квест: `title`, `intro`, `steps[].story/task`, `finale`, `city`, `tags`,
`duration_min`, `difficulty`.

Индекс после нарезки на фрагменты ~800 символов: **~13 тыс. векторов**.
При 1024 измерениях в fp16 это ~27 МБ — помещается в память любого
процесса, база данных для хранения векторов не обязательна.

### 2.2 Инфраструктура

| площадка | ресурсы | вывод |
| --- | --- | --- |
| прод `metravel.by` | 1 vCPU, 1.8 ГБ ОЗУ, диск 86 %, без GPU; контейнеры app/nginx/redis×2/postgis уже занимают ~600 МБ | только поиск по готовому индексу; LLM и тяжёлые embedding-модели исключены |
| Mac владельца | Apple M1, 8 ядер, 16 ГБ, Ollama 0.40.5, диск свободен | 4B–9B модели работают комфортно (9B Q4 ≈ 6 ГБ, 10–15 ток/с; 4B ≈ 3 ГБ, 20+ ток/с) |
| бэкенд | Django/DRF, `postgis/postgis:17-3.5` (без pgvector), `openai` SDK используется только для картинок значков | pgvector — отдельная `area=back` задача и кастомный образ БД; на старте не нужен |

## 3. Какие бесплатные модели подходят (октябрь 2026)

Критерии: русский как основной язык, белорусский/украинский/польский/
английский — для локалей, лицензия на коммерческое использование, размер
под CPU/M1, GGUF для Ollama/llama.cpp.

### 3.1 Генерация (чат, черновики статей)

| модель | размер | лицензия | языки | где тянет | заметка |
| --- | --- | --- | --- | --- | --- |
| **Qwen3.5-9B-Instruct** (02.03.2026) | 9B, Q4 ≈ 5.5 ГБ | Apache 2.0 | 201 языков, контекст 262K | Mac M1 16 ГБ: да; VPS 8 ГБ: да, медленно | лучшая модель до 10B по Artificial Analysis; основной кандидат для контура редакции |
| **Qwen3.5-4B-Instruct** | 4B, Q4 ≈ 2.8 ГБ | Apache 2.0 | те же | Mac: быстро; VPS 4–8 ГБ: да | кандидат для серверного чата после апгрейда VPS; мультимодальная (можно описывать фото) |
| Gemma 4 E4B | 4.5B эфф. (8B с эмбеддингами), Q4 ≈ 5.3 ГБ | Apache 2.0 | 140+ языков, 128K | Mac: да | альтернатива Qwen; по памяти тяжелее 4B-Qwen |
| YandexGPT 5 Lite 8B | 8B | кастомная лицензия Yandex | русский в первую очередь | Mac | проверить лицензию до коммерческого использования |
| T-pro 2.0 (Т-Банк, на базе Qwen3) | 32B | Apache 2.0 | русский, кириллический токенизатор | не тянет ни Mac, ни VPS | слишком большая |
| Vikhr (Mistral-7B) | 7B | Apache 2.0 | русский | Mac | 2024 год, устарела относительно Qwen3.5 |
| Llama 4 | только 109B+ | Llama Community | — | нет | маленьких версий нет; русский официально не поддержан и в Llama 3.x |
| Phi-4-mini | 3.8B | MIT | английский в основном | — | слабый русский, не подходит |

Рекомендация: **Qwen3.5-9B** на Mac (редакция), **Qwen3.5-4B** как кандидат
для сервера, если когда-нибудь появится ≥4 vCPU / 8 ГБ. Оба — Apache 2.0.

### 3.2 Эмбеддинги (индекс для поиска)

| модель | параметры | ОЗУ (int8 ONNX) | мультиязычный MTEB | роль |
| --- | --- | --- | --- | --- |
| **Qwen3-Embedding-0.6B** | 0.6B | ~700 МБ | 64.3 | индексация на Mac; качество выше |
| **EmbeddingGemma-300M** | 0.3B | ~200–300 МБ | 61.2 | эмбеддинг запроса на проде (1 vCPU) — единственная, что влезает в 850 МБ свободной памяти |
| BGE-M3 | 0.57B | ~600 МБ | ≈ Qwen3-0.6B | проверенный мультиязычный дефолт; dense+sparse |
| multilingual-e5-large-instruct | 0.56B | ~600 МБ | топ MMTEB retrieval | окно 512 токенов — короткое для статей |

Важно: **модель индексации и модель запроса должны совпадать.** Если на
проде считаем запрос EmbeddingGemma-300M, то и индекс строим ею. Поэтому
план предлагает EmbeddingGemma-300M везде, а Qwen3-Embedding-0.6B — как
апгрейд после апгрейда сервера. Выбор закрепляется замером на 30–50
реальных запросах владельца (раздел 6, этап 0).

Запасной вариант без ONNX на проде: считать эмбеддинг запроса на Mac
невозможно (сайт публичный), поэтому либо EmbeddingGemma на проде, либо
хостед-эмбеддинги (Voyage/OpenAI, доли цента за запрос) — это уже не
«локально», но индекс остаётся наш.

### 3.3 Реранкер (опционально)

`bge-reranker-v2-m3` (0.57B) заметно поднимает точность top-5, но на 1 vCPU
это +1–2 с на запрос. На старте — только гибрид лексики бэкенда (`/api/travels/?query=`,
#1581; `searchextended` на проде отдаёт 404) + векторы с RRF-слиянием; реранкер — после апгрейда.

## 4. Архитектура

### 4.1 Общий индекс сайта (ядро, одно для обоих контуров)

```
прод-API (/api/travels/, /api/quests/)  ──►  scripts/ai-index/build.ts
                                               │ нормализация HTML → текст
                                               │ нарезка ~800 символов с метаданными
                                               │ EmbeddingGemma-300M (ONNX, Mac)
                                               ▼
                                     .codex-temp/ai-index/
                                       chunks.jsonl   (текст + meta: id, type, url, city, country, lat/lng, month, tags)
                                       vectors.f16    (N × 768)
                                       manifest.json  (модель, версия, sha источника, дата)
```

- Строится на Mac за минуты (13 тыс. фрагментов × ~20 мс).
- Инкрементально: по `updated_at` статьи/квеста перестраиваются только
  изменённые фрагменты.
- Артефакт кладётся на прод тем же `scripts/deploy-prod.sh` как
  `dist/ai-index/` (≈30 МБ; диск прода на 86 % — перед этим снять старые
  цепочки образов, см. память `project_prod_disk_composition_and_cleanup`).

### 4.2 Контур редакции (владелец, Mac)

```
Claude Code агенты ──► MCP-сервер «metravel-knowledge» ──► индекс + Ollama
(travel-writer,            search(query, filters)           (Qwen3.5-9B для
 instagram-*, quest-*)     similar(article_id)               автономного режима)
                           coverage(place)  → «что уже написано про X»
                           gaps(country)    → «о чём ещё нет статьи»
Ollama + Open WebUI ──► тот же MCP ──► чат «напиши черновик по нашим материалам»
```

- MCP-сервер — Node/TS в репо (`scripts/ai-index/mcp.ts`), регистрируется
  в `.mcp.json` как существующий `metravel-task-board`.
- Генерация: по умолчанию Claude (агенты уже есть и пишут лучше любой
  9B), локальная Qwen3.5-9B через Ollama — для офлайн-черновиков,
  переводов, SEO-вариантов заголовков, где качество 9B достаточно и стоимость
  нулевая.
- Это закрывает «помогать составлять статьи, знать какой материал у нас
  есть» без единого изменения на проде.

### 4.3 Контур пользователей (сайт)

Этап 1 — **умный подбор без LLM** (работает на нынешнем проде):

```
страница /search или блок «Подобрать» ──► POST /ai/search {q, locale, filters}
                                              │ контейнер metravel-assist (FastAPI, ~300 МБ):
                                              │  EmbeddingGemma-300M int8 → вектор запроса (~150–300 мс на 1 vCPU)
                                              │  cosine top-50 по vectors.f16 (numpy, <10 мс)
                                              │  + лексика /api/travels/?query= (#1581), RRF
                                              ▼
                                        карточки статей/квестов с объяснением «почему» (совпавший фрагмент)
```

- Отдельный контейнер в compose бэкенда с `mem_limit: 400m`, `cpus: 0.5`,
  nginx `location /ai/` — всё это серверная работа без правки Django
  (фронт-владение по правилу «сервер ≠ бэк»), nginx-правка — backend-owned
  по `docs/RULES.md` → «Nginx config ownership», значит `area=back` карточка
  на один `location`.
- Защита единственного ядра: очередь на 1 запрос, таймаут 2 с, кэш
  результатов по нормализованному запросу в redis (уже есть), rate-limit
  в nginx.
- Также даёт «похожие статьи» на странице статьи и «квесты рядом с этой
  статьёй» — чистый вектор-поиск, без запроса пользователя.

Этап 2 — **текстовый ассистент** («спланируй выходные под Краковом с
детьми»):

| вариант | где генерация | стоимость | UX | когда |
| --- | --- | --- | --- | --- |
| **A. хостед-API поверх нашего индекса** | Claude Haiku 5.5 ($0.10/$0.50 за MTok): ~3 тыс. токенов контекста + 300 ответа ≈ $0.0005 за ответ; 10 тыс. ответов/мес ≈ $5 | 2–4 с, стриминг | можно сразу после этапа 1 |
| B. локальная Qwen3.5-4B на апгрейженном VPS | ≥4 vCPU / 8 ГБ (~€35/мес у Hetzner в 2026) | 20–40 с на ответ, 1 пользователь за раз | только если принципиально «ничего наружу» |
| C. локальная модель на нынешнем проде | — | невозможно (1.8 ГБ ОЗУ) | — |

Ключевое: модель в контуре пользователей **ничего не знает сама** — она
только переформулирует найденные фрагменты и ссылается на них. Поэтому
замена A→B — это замена одного HTTP-клиента, индекс и промпт те же.

### 4.4 Что модель «знает» и как обновляется

- Единственный источник правды — индекс, перестраиваемый по cron на Mac
  (или в `scripts/deploy-prod.sh` при выкате) по `updated_at`.
- Ответ всегда с цитатой-ссылкой на статью/квест; без найденных фрагментов
  ассистент отвечает «на сайте об этом пока нет» и предлагает ближайшее.
- Гостевой контент (другие авторы) — в индекс только опубликованные и
  прошедшие модерацию (`publish && moderation`), как и в каталоге.

## 5. Оценка применимости

| потребность владельца | решение | вердикт |
| --- | --- | --- |
| модель знает, какой материал есть | индекс сайта + MCP `coverage/gaps/similar` | подходит, дёшево, без прода |
| помогает составлять статьи | агенты Claude + локальная Qwen3.5-9B на Mac поверх индекса | подходит; локальная модель — для черновиков и офлайна, не замена агентам |
| «обучится на данных сайта» | RAG вместо fine-tune; LoRA стиля — опционально, этап 4 | подходит в смысле результата, не в смысле «дообучить» |
| помогает пользователям подбирать | семантический подбор без LLM (этап 1) + ассистент через API (этап 2A) | подходит; полностью локальный чат на сайте — нет без апгрейда VPS |
| бесплатно и локально | модели — бесплатны (Apache 2.0); «локально» выполнимо для редакции; для сайта локально = +€35/мес сервер и медленный ответ | частично |

Риски:

- **прод-ресурсы**: даже 300 МБ-контейнер эмбеддингов — это +15 % ОЗУ на
  машине, где `metravel-app` ограничен 900 МБ; обязателен `mem_limit` и
  замер `docker stats` неделю до включения на всех; диск — чистка до выката;
- **качество русского у 4B**: проверять на 30 реальных вопросах до выбора;
  память проекта фиксирует, что даже Sonnet галлюцинирует «наблюдаемые»
  детали в квестах — пользовательский ассистент не должен ничего утверждать
  без фрагмента из индекса;
- **Беларусь-правило**: промпты и ответы проходят тот же скан на
  экстремистские источники, что и тексты (память
  `feedback_belarus_sources_no_extremist_media`); индекс строится только из
  нашего контента, внешние ссылки модель не придумывает;
- **локализация**: индекс RU, ответ — на локали пользователя (модель
  переводит), квесты индексируются во всех 5 локалях, потому что есть готовый
  перевод; UI-строки — через `@/i18n`.

Platform impact: web desktop/mobile — новый блок поиска/похожих; Android/iOS —
тот же API, экран позже; native не блокирует этап 1.

## 6. План реализации

Этап 0 — замер и выбор (1–2 дня, только Mac):

1. `ollama pull qwen3.5:9b`, `qwen3.5:4b`, `gemma4:e4b`; 20 реальных задач
   редакции (черновик абзаца, SEO-заголовки, перевод шага квеста на PL) —
   слепая оценка владельцем.
2. Экспорт корпуса из прод-API в `.codex-temp/ai-index/raw/`; индекс двумя
   моделями (EmbeddingGemma-300M, Qwen3-Embedding-0.6B); 30 запросов
   владельца («замки под Краковом на день», «куда с собакой в Беловежскую
   пущу») — recall@5 вручную. Выбор модели эмбеддингов.
3. Замер на проде без установки: `docker run --rm -m 400m` с ONNX-моделью
   запроса, 100 запросов — латентность и пик памяти. Если не укладывается в
   300 мс / 350 МБ — этап 1 идёт на хостед-эмбеддингах.

Этап 1 — индекс и контур редакции (3–5 дней, прод не трогаем):

4. `scripts/ai-index/build.ts` (экспорт, нарезка, эмбеддинг, manifest),
   тесты в `__tests__/scripts/`, инкрементальная пересборка.
5. MCP-сервер `metravel-knowledge` (search/similar/coverage/gaps) +
   регистрация в `.mcp.json`; подключение к `travel-writer`,
   `instagram-planner`, `quest-expert` одной строкой в их инструкциях
   («перед темой проверь coverage»).
6. Open WebUI/Ollama на Mac с тем же MCP — локальный чат для владельца.

Этап 2 — семантический подбор на сайте (5–8 дней):

7. Контейнер `metravel-assist` (FastAPI + onnxruntime + numpy), compose-файл
   в `../metravel-backend/deploy` — `area=back` карточка (compose, nginx
   `location /ai/`, лимиты), выкат с индексом в `dist/ai-index/`.
8. Фронт: `/ai/search` клиент в `api/`, блок «Похожие статьи» на travel
   details, «Квесты рядом» и поисковая строка с объяснением совпадения;
   локали RU/BE/UK/PL/EN через `@/i18n`; проверка 320/390/1440.
9. Нагрузочный тест на проде: 10 параллельных запросов не должны поднять
   p95 `/api/travels/` выше baseline; алерт по `docker stats`.

Этап 3 — текстовый ассистент (3–5 дней):

10. Эндпоинт `/ai/ask` в том же контейнере: retrieve top-8 → промпт с
    фрагментами и правилом «только по фрагментам, со ссылками» → провайдер
    (Haiku 5.5 по умолчанию, Ollama-совместимый клиент как опция для варианта B).
11. UI чата с показом источников; лимит 20 вопросов/сутки на IP; логирование
    вопросов без ответа → `docs/QUEST_DEMAND_LOG.md`-подобный журнал спроса
    (это готовый источник тем для новых статей и квестов).

Этап 4 — опционально:

12. LoRA стиля Юли на Qwen3.5-4B через MLX на Mac (все 429 статей — это
    ~3 млн токенов, часы на M1) — только если локальные черновики
    «не звучат как мы».
13. pgvector в PostGIS (кастомный образ, `area=back`) — когда индекс
    перерастёт файл или понадобятся фильтры по гео прямо в SQL.

## 10. Индекс контента: сборка, формат, инкремент (#2454, 18.10.2026)

Ядро линии AI-ASSIST из раздела 4.1 реализовано: `scripts/ai-index/` строит
смысловой индекс всего публичного контента на Mac и кладёт его готовым
артефактом в `.codex-temp/ai-index/dist/`. Прод, бэкенд и UI не трогаются.

### 10.1 Команды

```bash
npm run ai:index -- export            # прод-API → .codex-temp/ai-index/raw/ (инкремент)
npm run ai:index -- chunk             # raw → work/chunks.jsonl (нарезка, метаданные)
npm run ai:index -- embed             # work/chunks.jsonl → dist/ (инкремент по id фрагмента)
npm run ai:index -- manifest          # проверка артефакта: count = строки = size/(dim×2), sha
npm run ai:index -- query "вопрос"    # top-5 фрагментов с URL (--k N)
npm run ai:index -- eval --queries q.jsonl --threads 1 [--report out.md]
npm run ai:index -- build             # export + chunk + embed + manifest
```

Опции: `--out <dir>` (корень, по умолчанию `.codex-temp/ai-index`), `--dist <dir>`,
`--model embeddinggemma-300m | qwen3-embedding-0.6b`, `--threads N` (потоки
ONNX; `1` — замер «как на проде»), `--full` (без инкремента), `--limit N`
(smoke на первых N статьях и квестах), `--locales ru,be,uk,pl,en` (экспорт и
нарезка квестов). Запуск — Node ≥ 22 с `--experimental-strip-types`; веса
моделей кэшируются вне `node_modules` в `~/metravel-ai/models/transformers-cache`
(`AI_INDEX_MODEL_CACHE`), первая загрузка ≈ 0,9 ГБ на обе модели.

### 10.2 Источники и нарезка

- Статьи: `GET /api/travels/?page=N&page_size=50`, в индекс попадают только
  `publish && moderation`; деталь `GET /api/travels/<id>/` урезается до полей
  контента (`description`, `plus`, `minus`, `recommendation`, гео, месяцы,
  категории, `updated_at`). Квесты: `GET /api/quests/?page=N` и
  `GET /api/quests/<id>/?lang=<locale>` по каждой локали из `available_locales`
  (параметр именно `lang`; `locale` игнорируется). Пауза 0,5 с, `User-Agent:
  metravel-ai-index/1.0`.
- HTML → текст: блочные теги → перевод строки, `script/style/iframe` выброшены,
  сущности декодированы. Текст статьи = описание + разделы «Плюсы/Минусы/
  Рекомендации»; текст квеста = история интро + шаги (название, история,
  задание; подсказки не индексируются) + финал.
- Окна по границам предложений: ≤ 800 символов, следующее окно начинается с
  хвоста предыдущего длиной ≥ 100 символов (но не больше половины окна);
  предложение длиннее окна режется по словам. Средняя длина фрагмента ≈ 720
  символов.
- Запись `chunks.jsonl` (контракт — `scripts/ai-index/format.ts`): `{id, type:
  'travel'|'quest', source_id, url, title, city, country, lat, lng, month, tags,
  locale, text}`. `id = t<source>-<locale>-<sha256(text)[0:16]>` — зависит
  только от содержимого, поэтому правка одного абзаца пересчитывает только его
  окна. URL квеста локализован как на сайте (`/pl/quests/<city_id>/<slug>`,
  через `utils/questLocaleRouting`). Теги статей — `category:<id>`: публичного
  словаря категорий в API нет, имена подставляются при появлении словаря.
- В эмбеддинг уходит `title: <заголовок> | text: <фрагмент>` (промпт документа
  модели), в запрос — `task: search result | query: <вопрос>`; вектор —
  штатный выход `sentence_embedding` ONNX-графа EmbeddingGemma (mean pooling по
  маске → Dense 768→3072 → Dense 3072→768 → L2), как в карточке модели, а не
  усреднение `last_hidden_state`. Рецепт (`recipe`), промпты и `dtype` заданы
  в `scripts/ai-index/models.ts` и обязаны байт в байт совпадать у индекса,
  сервиса и MCP: Python-сервис берёт тот же `onnx/model_quantized.onnx` и выход
  `sentence_embedding`.

### 10.3 Артефакт и инкремент

`dist/`: `chunks.jsonl`, `vectors.f16` (N × dim binary16 little-endian, векторы
нормализованы — косинус = скалярное произведение), `manifest.json`
`{model, dim, count, built_at, source_sha256}`; `source_sha256` считается по
содержимому записей, повторная сборка на тех же данных даёт тот же sha
(тест). Файлы пишутся через tmp + rename по одному, поэтому читатель, попавший
между переименованиями, может получить `chunks.jsonl` одной сборки и
`manifest.json` другой; `readIndex` сверяет `count`, длину `vectors.f16` и
`source_sha256` и такой набор отбрасывает — сервису читать `dist/` только с
той же проверкой (или с повтором через секунду).

Инкремент на трёх уровнях: `export` перечитывает статью только при смене
`updated_at` в списке; квестам API не отдаёт `updated_at`, поэтому их детали
перечитываются всегда, а на диск пишутся только при смене sha ответа (≈ 9 минут
на 635 деталей — кандидат на `area=back`: `updated_at` в списке квестов);
`embed` берёт вектор из предыдущего `dist/` той же модели по id и заголовку и
считает только новые фрагменты («пересчитано 0 фрагментов» без изменений на
сайте). `export --locales ru` читает только запрошенные локали и raw чужих
локалей не удаляет; `--limit` тоже ничего не удаляет.

### 10.4 Этап 0: выбор модели эмбеддингов

Замер на RU-корпусе (429 статей + 280 квестов = 12 100 фрагментов), 30 запросов
посетителя по-русски с размеченными источниками, попадание — ожидаемый
источник среди top-5 источников; латентность — эмбеддинг запроса на одном

проигрывает статьям-подборкам («однодневная вылазка из Кракова с собакой»

## 11. Сервис metravel-assist (#2456, 18.10.2026)

Сервис подбора реализован на Node без фреймворка: код — `scripts/ai-assist/`
(исполняемые модули репозитория живут в `scripts/`, их видит guard
`unimported-modules`), образ и описание — `services/ai-assist/` (как у
`metravel-llm`), тесты — `__tests__/scripts/ai-assist/`. Контракт эндпоинтов и
переменные — `services/ai-assist/README.md`. Запуск на Mac:
`AI_INDEX_DIR=.codex-temp/ai-index/dist npm run ai:assist:dev`, замер —
`npm run ai:assist:bench`.

### 11.1 Что подтвердилось и что разошлось с планом

- Индекс читается `readIndex` (count + длина `vectors.f16` + `source_sha256`) с
  повтором через секунду; модель берётся из `manifest.model`, а `AI_ASSIST_MODEL`
  (в образе — запечённая) закрепляет её, и несовпадение — отказ старта.
- Вектор запроса считается тем же `createEmbedder`, что и индекс. Паритет:
  `POST /ai/search` для «однодневная вылазка из Кракова с собакой» (векторная
  часть) отдаёт источники в том же порядке, что `npm run ai:index -- query --k 40`:
  636, 568, 516, 478, 461, 506, 563, 595, 455, 475, 609, 541.
- Лексика: `searchextended` на проде отдаёт 404; `cards/?query=` не кэшируется
  и отвечает 3,6–5,5 с на любой запрос; `travels/?query=` кэшируется бэкендом на
  час (5,4 с первый раз, 0,43 с повторно) — сервис ходит в него. Пока бэкенд не
  ускорит поиск (#1581 на 1 vCPU), гибрид на первом запросе почти всегда
  упирается в `AI_ASSIST_LEXICAL_TIMEOUT_MS` (1,5 с) и отвечает `degraded: true`
  векторной частью; такие ответы не кэшируются. Это кандидат на `area=back`:
  индекс/кэш для `TravelCatalogSearch` или отдельный лёгкий эндпоинт
  «id + title по запросу».
- `/ai/similar` — нормализованное среднее фрагментов источника (на нужной
  локали, если есть) → top-k без модели: 10–21 мс на полном индексе.
- `UV_THREADPOOL_SIZE=1` из карточки отменён: с одним IO-потоком первое
  HTTPS-соединение Node к бэкенду занимает 1,3 с (с пулом 4 — 0,2 с), лексика
  упирается в таймаут 1,5 с, а абортированный keep-alive делает «первым» каждый
  следующий запрос — гибрид деградирует навсегда. С пулом 4 гибрид на тёплом
  бэкенде отвечает за 302 мс без `degraded`; CPU ограничивают очередь к модели и
  `AI_ASSIST_THREADS=1`. Замеры таблицы ниже сняты с пулом 1 — векторной части
  это не касается.

### 11.2 Замеры на Mac (M5 Pro, один поток: `UV_THREADPOOL_SIZE=1`, `AI_ASSIST_THREADS=1`, бэкенд недоступен → чистая векторная часть, кэш ответов мимо)

| модель индекса и запроса | RSS старт / после 1000 запросов | куча | `/ai/search` took_ms p50 / p95 / max | 20 параллельных: p50 / p95, 503 |
| --- | --- | --- | --- | --- |
| `embeddinggemma-300m` (q8, `model_quantized.onnx`) | 1 935 / 1 993 МБ | 171 → 183 МБ | 114 / 124 / 152 | 996 / 2 014 мс, 0 из 20 (очередь укладывается в 2 с) |
| `embeddinggemma-300m-q4` (`model_q4.onnx`) | 779 / 704 МБ | 153 → 161 МБ | 23 / 24 / 29 | 200 / 397 мс, 0 из 20 |

Главная находка: **q8-граф EmbeddingGemma на CPU не помещается в прод.** После
первого прогона onnxruntime разворачивает int8-веса (таблица эмбеддингов
262 144 × 768 и matmul-веса) в fp32: RSS 439 МБ после загрузки → 1 577 МБ после
первого запроса, 70 мс на запрос; опции сессии (`enableCpuMemArena: false`,
`graphOptimizationLevel: basic/disabled`, `enableMemPattern: false`) не меняют
картину. Тот же граф в `q4` (MatMulNBits) — 541 → 547 МБ и 10,8 мс; `q4f16` —
551 → 560 МБ и 15 мс; `fp16` — 678 → 686 МБ и 15,9 мс; `int8`/`uint8` в репо
onnx-community нет. Поэтому в реестр моделей добавлен ключ
`embeddinggemma-300m-q4` (тот же рецепт и промпты, dtype `q4`); индекс и запрос
обязаны считаться одним ключом, переход — `npm run ai:index -- embed --model
embeddinggemma-300m-q4 --full`. Качество q4 против q8 на наборе этапа 0 (30
запросов, полный индекс 20 513 фрагментов, `--threads 1`):

| модель | recall@1 | recall@5 | MRR | запрос p50 / p95, мс |
| --- | --- | --- | --- | --- |
| `embeddinggemma-300m` (q8) | 0,93 | 1,00 | 0,95 | 69 / 78 |
| `embeddinggemma-300m-q4` | 0,83 | 1,00 | 0,90 | 10 / 12 |

Решение по смене ключа индекса (и пересборке `dist/` на проде) — за владельцем:
дефолт `DEFAULT_MODEL_KEY` в `scripts/ai-index/models.ts` не менялся. Образ
(`services/ai-assist/Dockerfile`, `ARG AI_ASSIST_MODEL`) запекает любой ключ.
Память индекса в процессе: `vectors` 60 МБ (Float32Array, вне кучи) + 30 МБ живой
кучи после GC (метаданные и сниппеты; полный текст фрагментов освобождается
при загрузке). `heap_mb` в `/ai/health` показывает кучу до сборки мусора
(150–180 МБ на Mac без лимита), в контейнере её держит
`--max-old-space-size=320`. Итог для q4 на проде ≈ 0,6–0,7 ГБ RSS — выше
ожидания карточки (≤ 400 МБ), но в пределах свободных ~850 МБ; q8 не помещается.
Пересчёт индекса в q4 на Mac — 26,5 мин (длинные документы через MatMulNBits
медленнее, чем q8: 14,5 мин), запрос — в 7 раз быстрее. Цена q4 — recall@1 0,83
против 0,93 при равном recall@5 = 1,00; порядок top-10 для «однодневная вылазка
из Кракова с собакой» меняется (q4: 516, 636, 568, 478, 455, 506, 546, 563, 461,
595), набор источников тот же. Артефакт q4 лежит в
`.codex-temp/ai-index/dist-q4/` рядом с основным `dist/`.

### 11.3 Образ

`node:22-slim` + `@huggingface/transformers@4.3.1` (версия из `yarn.lock`, без
остальных зависимостей репозитория) + `scripts/ai-index` + `scripts/ai-assist` +
веса модели, скачанные на этапе сборки (`scripts/ai-assist/fetch-model.ts`);
бинарники onnxruntime для darwin/win32 (221 МБ) удаляются. Оценка размера по
слоям: ~220 МБ база + ~90 МБ зависимости + веса (q8 330 МБ / q4 200 МБ) —
≈ 640 МБ для q8, ≈ 510 МБ для q4. На Mac владельца docker отсутствует (как и для
`metravel-llm`): первая сборка и точный размер — на хосте прода при #2457, где же
проверяется запуск под `USER 1000:1000` и `HEALTHCHECK` без curl (проба через
`node -e fetch`).
