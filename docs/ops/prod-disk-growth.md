Карточка: [#2186](https://metravel.by/board#task-2186). Предшественники:
[#1997](https://metravel.by/board#task-1997) (образы app),

данных на нём ограничен сам по себе, а суммы никто не держал: пределы классов
в сумме больше диска. Здесь записано, из чего состоит диск, чем ограничен
каждый класс и кто владелец предела, что проверяет выкат фронта и что делать,
когда он предупреждает о заполнении. Реквизиты SSH сюда не записываются
(`scripts/deploy-target.sh`).

Platform impact: none. Localization impact: none.

## Что делает выкат фронта

Правило живёт в репозитории и срабатывает в каждом выкате
(`scripts/deploy-prod.sh` → `build-prod.sh prod`):

- **Overlay ограничен дважды** (`scripts/deploy-expo-overlay.sh`): сроком
  `EXPO_OVERLAY_RETENTION_DAYS` (14) и объёмом `EXPO_OVERLAY_MAX_MB` (256).
  Поколения переносятся целиком, от нового к старому; на первом непоместившемся
  перенос прекращается. Поколение заменяемого релиза переносится всегда. В
  отчёте выката — строка `📊 Overlay старых чанков: перенесено … отброшено …`.
  Вкладка старше бюджета при подгрузке отсутствующего чанка один раз
  перезагрузится (`utils/chunkReloadGuard.js`). Почему 256: за 23 часа лога
  nginx 04.10.2026 браузеры 75 раз запросили уже заменённый чанк (0,8 % запросов
  к чанкам), самый старый отставал на 22 выката — всем хватило бы 223 МБ; при
  128 МБ перезагрузку получили бы 36 из 75. Бюджет — это байты, поэтому при 20
  выкатах в день он покрывает около полутора суток, при пяти — пять.
- **Проверка места до заливки** (`scripts/deploy-disk-guard.sh preflight`):
  на хосте должны быть `perl` и `cpio` (они нужны переносу overlay уже после
  заливки), а свободного должно хватать на релиз и резерв
  `DEPLOY_DISK_RESERVE_MB` (720 — 5 % диска, уровень аварии для монитора), а
  пока идёт сборка образа бэка (`docker compose … build`; бэк собирает образ вне
  лока, поэтому сборка узнаётся по процессу) — ещё и на её 1 536 МБ. Отказ
  происходит до любой записи на сервер. Обратный порядок ловит сам бэк: если
  места хватает, но на время заливки останется меньше 1 536 МБ, выкат
  предупреждает, что сборку образа в эти минуты остановит её preflight.
- **Строка о диске в отчёте** (`deploy-disk-guard.sh report`):
  `📊 Диск прода после выката: занято N %, свободно M МБ; static/dist — K МБ`.
  Предупреждение `⚠️` со ссылкой сюда — когда свободно меньше 1 536 МБ, то есть
  когда выкат бэка уже невозможен. Порог в процентах здесь не годится: пределы
  чужих классов сами держат диск выше 80 %, и предупреждение шло бы в каждом из
  двадцати выкатов в день. Предупреждение выкат не роняет.

Срочно освободить место силами фронта: выкатить с `EXPO_OVERLAY_MAX_MB=0` —
останется только поколение заменяемого релиза.

## Порядок действий при предупреждении или отказе

0. Если выкат отказал и назвал каталоги прерванного выката, снять их тем же
   путём, каким это делает сам выкат (root внутри контейнера app, на хосте у
   `sx3` прав на них нет), и повторить. Список тот же, что у уборки в
   `build-prod.sh` и у подсчёта в отказе (`dist.old*` — это ещё и
   `dist.old-*`, `dist.old.stale-*`). Имя контейнера не вписывается руками —
   его отдаёт общий резолвер `scripts/deploy-target.sh` (#1636):

   ```bash
   bash <<'RUN'
   source scripts/deploy-target.sh && require_deploy_target >/dev/null || exit 1
   {
     metravel_container_remote_snippet
     cat <<'EOF'
   app="$(metravel_resolve_container app)" || exit 1
   docker exec -u 0 "$app" sh -c 'rm -rf /app/dist /app/static/dist.new /app/static/dist.old /app/static/dist.old-* /app/static/dist.old.stale-* /app/static/dist.failed.*' </dev/null
   echo DONE
   EOF
   } | ssh "$PROD_SSH_TARGET" bash -s
   RUN
   ```
1. Снять состав по классам (блок ниже) и сравнить с таблицей бюджета: какой
   класс вышел за свой предел или вырос.
2. Зона фронта — правится выкатом: overlay (`EXPO_OVERLAY_MAX_MB`), размер
   релиза.
3. Зона бэка — карточка `area=back`: лишние образы и `release-rollback`
   (`deploy/prod/README.md` бэка, «App Image Retention»), `max_size` кэша nginx,
   пределы логов, срок хранения дампов. Git-tracked пути бэка на проде не
   править (`docs/RULES.md`).
4. Хост, sudo — запрос владельцу: `apt-get clean`, удаление старого ядра после
   перезагрузки, полный `du` под root.
5. Разовые каталоги (`metravel-monitor/task-<N>`, дампы в `/tmp`) удалять
   только по списку с размерами, согласованному с владельцем.

Удалять можно только то, что доказанно не нужно и восстановимо. БД, медиа,
`db-backups` и dotfiles сервера не трогать.

## Замер состава (только чтение)

```bash
bash <<'RUN'
source scripts/deploy-target.sh && require_deploy_target >/dev/null || exit 1
{
  metravel_container_remote_snippet
  cat <<'EOF'
gis="$(metravel_resolve_container metravel-gis)" || exit 1
nginx="$(metravel_resolve_container nginx)" || exit 1
app="$(metravel_resolve_container app)" || exit 1
df -B1 -P / | tail -1
du -x -B1M -d1 / 2>/dev/null | sort -rn | head -8
du -x -B1M -d2 /home/sx3 2>/dev/null | sort -rn | head -12
docker system df -v </dev/null
docker exec "$gis" du -sx -m /var/lib/postgresql/data </dev/null
docker exec "$nginx" du -s -m /var/cache/nginx </dev/null
for c in "$nginx" "$app"; do
  printf '%s ' "$c"; docker logs "$c" </dev/null 2>&1 | wc -c
done
D=/home/sx3/metravel/static/dist
du -B1M -d1 "$D" | sort -rn | head -4
find "$D/_expo" -type f \( -name '*.js' -o -name '*.css' \) -printf '%TY-%Tm-%Td %s\n' |
  awk '{ n[$1]++; b[$1] += $2 } END { for (d in n) printf "%s %d %.0f\n", d, n[d], b[d] / 1048576 }' | sort
echo DONE
EOF
} | ssh "$PROD_SSH_TARGET" bash -s
RUN
```

Запускать из корня репозитория. Имена контейнеров отдаёт общий резолвер
(`scripts/deploy-target.sh`, #1636): compose меняет разделитель в имени при
пересоздании, вписанное руками имя ломается молча. Каждая docker-команда
закрывает stdin (`</dev/null`): программа сама идёт по stdin, и читатель stdin
проглотил бы её остаток. Признак полного прогона — `DONE` в конце. `du` хоста
без root не видит `/var/lib/docker`, `/root` и каталог PostGIS; первые два
закрываются `docker system df -v`, каталог БД — `du` внутри контейнера.

## Алерт

- В отчёте каждого выката — строка о диске; предупреждение — когда свободно
  меньше 1 536 МБ.
- Хостовый `/home/sx3/monitor.sh` (cron раз в 5 минут, письмо владельцу):
  `DISK_THRESHOLD`, условие строгое (`usage > порог`). Состояние у монитора
  одно на все причины (`OK → PENDING → ALERT`, письмо на втором плохом замере
  подряд, дальше молчание до восстановления). Поэтому порог ниже устойчивого
  уровня диска вреден: монитор навсегда останется в `ALERT` и перестанет
  сообщать и о диске, и о CPU с памятью. Порог ставится выше устойчивого
  уровня. Файл живёт только на хосте, вне checkout бэка; значение с 05.10.2026
  — 84 (раздел «Решения владельца»).

## Решения владельца (05.10.2026, #2186)

- Бюджет старых чанков — 256 МБ. `docs/RULES.md` → «Web caching policy»
  приведено к этому: согласованность релиза держится на уровне HTTP в двух
  пределах (14 дней и бюджет), а для вкладки старше пределов единственное
  разрешённое восстановление — одна перезагрузка сторожем `chunkReloadGuard`.
- Порог письма монитора: `DISK_THRESHOLD=84` (95 → 90 до чистки, 90 → 84
  после неё; копии прежних файлов — `~/metravel-monitor/monitor.sh.before-2186`
  и `.before-2247`). Письмо приходит на 85 %; со всеми классами на их пределах
  диск — около 81 %, так что порог стоит над устойчивым уровнем.
- Почасовые снимки `metravel-monitor/task-2045` прорежены до суточной цепочки
  (15 из 244, каждый хранит окно 24 часа), дампы `/tmp/c2150*.log` удалены.
- Владелец под sudo удалила две старые копии каталога данных БД
  (`deploy/prod/postgis_1` и `~/pg_dump_17_11_2025`, 794 МБ), очистила архивы
  apt и после перезагрузки на ядро 6.8.0-142 удалила 6.8.0-139. Осталась копия
  `deploy/local/postres_dump_11_08_2024` (46 МБ): на неё ссылаются локальные
  compose-файлы разработки.

## Замер под root

Каталоги, закрытые от `sx3` (`/var/lib/docker`, `/root`, каталоги данных БД),
меряются одноразовым контейнером только на чтение — sudo не нужен, на сервере
ничего не меняется; печатать только размеры:

```bash
docker run --rm --pull never --network none --read-only -v /:/host:ro \
  --entrypoint sh redis:latest -c 'du -x -m -d2 /host/var /host/home | sort -rn | head -40' </dev/null
```

Команда выполняется на хосте (внутри блока замера выше); образ уже есть на
проде, `--pull never` не даёт ничего скачать.
