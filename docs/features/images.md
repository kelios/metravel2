# Изображения: архитектура, контракт и границы

Актуализировано: 2026-07-30; блок «Legacy-роут `/media-resize`» в §2.3, цепочка
закрытия бакета в §2.2 и статусы тикетов в §9 — 2026-08-01; storage-
политика, q85 print и q60 quest в §3–4 — 2026-08-02. Числа замеров
прода привязаны к указанной рядом дате; целевые наборы помечены как
политика, а не как уже созданные в S3 файлы.
Источник замеров указан рядом с каждым.

Документ существует, чтобы **не переизобретать пайплайн картинок заново**.
Раздел «Решено, не переобсуждается» фиксирует выбор, сделанный владельцем;
менять его можно только новым явным решением, а не по ходу задачи. Всё
остальное оптимизируется — но с обоснованием и замером, а не «на глаз».

История показывает, зачем это нужно: #1104, #1112, #1113, #1120, #1103 — пять
тикетов подряд про один и тот же класс дефекта «фронт попросил размер, который
бэкенд не умеет, и молча получил оригинал». Каждый чинился разовым `curl`, а
выводы этих замеров оседали комментариями в коде и через месяц устаревали,
уводя следующего разработчика в неверное решение.

## 1. Решено, не переобсуждается

1. **Оригинал не хранится.** То, что пришло с камеры, конвертируется в памяти
   при загрузке и на диск не попадает. Уже так работает.
2. **Хранится один мастер на изображение** — не оригинал, а лучшее, что нам
   реально нужно. Из него делаются все производные.
3. **Производные должны лежать готовыми, а не считаться на лету.** Фронт
   запрашивает размер и получает уже существующий файл. Ресайз в момент
   запроса — переходное состояние, а не целевое (#1136, #1168).
4. **Набор размеров фиксирован и записан.** Не «сколько получилось из
   измеренного слота», а перечисленный набор, одинаково известный фронту и
   бэкенду (#1167).
5. **Ширина обязательна в каждом запросе.** Запрос без `w` отдаёт мастер
   целиком — это дефект, а не фолбэк (#1161).
6. **Один визуальный слот = один растр.** На web у слота ровно одна картинка:
   ни второго `<img>`, ни CSS `background-image` с тем же фото, ни `blob:` из
   blurhash. Поля `contain`-слота заливает `dominant_color` из манифеста — ноль
   запросов и ноль декодов. Правило действует для карточек каталога, галереи и
   hero travel-детали, включая его SSG-шелл (#1208).

   **Заливка раздаётся ОДНИМ механизмом** (2026-08-05). Цвет раздавался пропом
   `placeholderColor`, и каждый экран доставал его из манифеста сам, своей формой
   пейлоада. Экраны волны #1208 заливку получили, остальные молча остались с
   прозрачными полями: замер прода 2026-08-05 на `/map` — 7 карточек списка,
   `object-fit: contain` в боксе 360×173, слоёв заливки **0**, фон медиа-бокса
   `rgba(0, 0, 0, 0)`. Теперь data-слой один раз индексирует манифест
   (`utils/mediaPlaceholderIndex.ts`), а `ImageCardMedia` находит цвет по URL сам:
   после правки на том же экране 7 из 7 (`rgba(92, 98, 82, 0.75)` и т.д.), на
   mobile web 390 — те же 7 из 7. Явный проп по-прежнему главнее индекса.

   - Точки прогрева: `normalizeTravelItem` (обложка, галерея, точки, тело статьи),
     `api/map.ts` (оба нормализатора точек), `utils/placesCatalog.ts`,
     `api/quests.ts` (мета и бандл). Новое семейство пейлоада — это ОДИН вызов
     `indexMediaImage`/`indexTravelMedia` в его нормализаторе.
   - Ключ индекса — storage key: путь без роут-префикса и без query. Один файл
     приходит и как `/address-image/355/conversions/x.webp?w=640` (манифест), и как
     `/media-resize/legacy/355/conversions/x.webp?v=…&w=720` (разметка).
   - `aliasUrls` нужны там, где UI рисует не тот файл, что описан манифестом:
     карта показывает legacy-конверсию `thumb`, а манифест точки — полный кадр.
   - Ступеней ровно две, и обе в этом модуле: (1) `dominant_color` из манифеста —
     бесплатный и доступен ДО декода; (2) `sampleDominantColor` — усреднение уже
     загруженного кадра в канву 1×1 для семейств без манифеста (тело статьи #1266,
     шаги квестов / обложки поездок / фото точек пользователя #1267). Результат
     второй ступени ложится в тот же индекс, поэтому «манифест или сэмпл»
     разбирается один раз. Рамка тела статьи (#1233) больше своего сэмплера не
     держит — берёт общий.
   - Гейт: `npm run check:image-architecture` падает и на чтении `dominant_color`
     где-либо кроме `utils/travelMediaVariants.ts`, и на `getImageData` где-либо
     кроме этого модуля (кроме двух файлов с другой задачей: средняя яркость кадра
     и проверка однотонности плитки карты).
   - На native ничего не меняется: поля там закрывает blur-слой expo-image, индекс
     читается только на web.
   - Ограничение проверки: вторую ступень нельзя увидеть в dev-браузере — медиа
     там приходит с чужого origin и тейнтит канву (`getImageData` → SecurityError,
     штатная ветка `null`). Замер прода 2026-08-05 на
     `/travels/reka-isloch-…`: после загрузки кадра рамка получает
     `--travel-rich-image-fill: rgba(198, 199, 179, 0.75)`.
7. **Перед любой операцией с хранилищем — полный локальный бэкап** (#1165).
   Удаление чего-либо в S3 требует отдельной авторизации владельца по
   dry-run-отчёту (#1155 → #1157).

## 2. Как это работает сегодня

### 2.1 Загрузка

```
клиент → (web: downscale >9 МБ; native: всегда ≤1920)
       → POST /api/files или PATCH /api/<model>/{id}/
       → ValidatedImageUploadField (лимит 10 МБ, whitelist расширений)
       → ImageUploadMixin.set_image()
       → ImageProcessingService.process_upload()
           EXIF-поворот → ресайз ≤1920×1920 → WebP q85 → watermark
       → S3
```

Оригинал до S3 не доходит. Имя результата всегда `<base>.webp`.

**Дыра:** ресайз вызывается из метода `set_image()`, который вызывающий код
обязан помнить. Прямое присваивание `instance.image = file` (Django-admin,
скрипты, фикстуры) кладёт в S3 сырьё. Следствие в данных: `quests/*/main/` —
188 PNG, средний 2390 KiB, максимум 4370 KiB. Замер:
`quests/1/main/f137…png` = **2 438 301 B, PNG 1536×1024**, тогда как через
прокси тот же файл — 88 978 B WebP. Закрывается в #1152.

### 2.3 Раздача

```
браузер → nginx (кэш) → Django → Redis (кэш байтов) → S3 (источник)
                                   ↓ промах
                          Pillow: decode → resize → encode
```

- Контракт прокси: `GET /api/media/proxy-contract`. 15 ступеней ширины
  `32, 96, 160, 320, 480, 640, 720, 800, 960, 1024, 1200, 1280, 1600, 1920, 2500`;
  неподдержанная ширина **округляется вверх** (проверено: `w=47` → 2 582 B =
  `w=96`; `w=240` → 17 738 B = `w=320`); апскейла нет.
- `q` — 20…90, дефолт 85. `fit=contain|cover` схлопываются в одну идентичность.
  `h`, `dpr`, `blur` игнорируются.
- Приложение отдаёт `Cache-Control: public, max-age=31536000, immutable`.

**Legacy-роуты `/media-resize/*` (исправлено 2026-08-02).** Для legacy-ключей вне
family-роутов на проде с 2026-07-11 живут первопартийные роуты (backend commit
`e3f7fcd`, `media_assets/views.py`). Их **два**, и они объявлены в
`route_behavior` контракта:

| класс ключа | роут | режим |
|---|---|---|
| `uploads/**` | `GET /media-resize/uploads/<ключ>?w=` | `legacy_upload`, `transform` |
| `**/conversions/**` | `GET /media-resize/legacy/<ключ>?w=` | `legacy_conversion`, `transform` |

> Запись от 2026-08-01 «`conversions/**` отдаёт 404» была верна на тот день:
> второй роут добавлен 2026-08-02 backend-коммитом `d338d22` по задаче #1175
> (закрыта). Замер после деплоя на `3994/conversions/HcQK…-detail_hd.jpg`:
> `?w=320` → 25 062 B против 765 231 B у оригинала.
>
> Путь роута для conversions — `/media-resize/legacy/…`, а не
> `/media-resize/conversions/…`: имя роута не повторяет имя класса ключей.
> Сверяйтесь с `route_behavior` в контракте, а не угадывайте путь по классу.

- Ceil-up по той же лестнице, что у family-роутов (`w=47` ≡ `w=96`, `w=240` ≡
  `w=320`; проверено 2026-08-02). Пример: `uploads/1591620319350_original.jpg?w=320`
  → WebP 7 820 B при S3-оригинале 141 354 B.
- Запрос **без `w` молча выбирает legacy-default 800** (36 972 B; тот же размер,
  что у явного `?w=800`, повторно проверено 2026-08-02). Это скрытый default, а
  не допустимый frontend-контракт: `optimizeImageUrl` всегда материализует
  канонический `w`, включая явный fallback `w=800`, если динамический caller ещё
  не передал измеренную ширину.
- `q` роут принимает (`?w=320&q=20` → 2 378 B), `fit` в идентичность не входит.
- Фронт использует их с #1176: `toLegacyResizePath` в `utils/mediaUrl.ts`
  переписывает прямые и weserv-обёрнутые ссылки на бакет, снимает S3 signature
  params, но сохраняет кодировку ключа и обычный cache-buster; `htmlTransform` и
  `imageProxy` дальше строят обычный srcset по лестнице. Классы без роута
  (`**/responsive-images/**` — удалён в #1157, плоский корень — живёт под
  family-роутами) не переписываются намеренно.
- С 2026-08-02 та же функция переписывает и **первопартийный** family-URL, если
  его ключ попадает в класс `**/conversions/**`: путь после имени роута и есть
  storage key (`/travel-image/682/conversions/x.webp` → `682/conversions/x.webp`).
  Это обход #1195 (ниже) для того класса, у которого свой `transform`-роут уже
  есть. Хост при этом обязан быть нашим (прод, `EXPO_PUBLIC_API_URL`, origin
  страницы, dev-LAN) — чужой домен с похожим путём не трогаем. Точек применения
  две, потому что URL манифеста в `srcSet` идут мимо `optimizeImageUrl`:
  `imageProxy.optimizeImageUrl` и `travelMediaVariants.resolveMediaVariantUrl`.

**Регрессия `uploads/**` — 2026-08-04, #1233 (P0; обход снят в #1753, см. ниже).**
У класса `uploads/**` durable-производных нет **вообще**: `backfill_image_derivatives`
идёт по `IMAGE_FIELD_STORAGE_PROFILES`, то есть по полям живых моделей, а эти ключи не
поле модели — они вшиты прямо в HTML тел легаси-статей, и в §2.2 весь класс помечен
«кандидаты в сироты». Пока чтение производных было fail-open, роут резал динамически
и пробел не был виден. После `MEDIA_IMAGE_DERIVATIVE_READ_ENABLED` чтение стало
fail-closed, и на 2026-08-04 **каждая** ступень отвечала 404 `derivative-missing`
(сегодня на том же месте объявленный фолбэк на мастер — см. ниже).

Замер прода 2026-08-04, `media-resize/uploads/1642189225IMG_6113.jpg` (кадр 800×533):

| запрос | ответ |
|---|---|
| `w=320|480|640|800|960|1600` | **404** `derivative-missing` |
| `w=1800`, `w=2000`, `w=2500` | 400 |
| `w=1920` | 200 `stored-master`, 216 786 B |
| `w=320&f=jpeg` | 200 `dynamic-transform`, 22 142 B, `immutable` |
| `w=800&f=jpeg` | 200 `dynamic-transform`, 122 145 B, `immutable` |

То есть ни одна ступень наборов `articleBodyMobile`/`articleBodyDesktop` не
отрисовывалась. Обход сайта в тот же день: **5 044 фото в телах 259 из 397 статей**.
Десктоп доживал до 2026-08-03 случайно — потолок `articleBodyDesktop` был 1920, и
браузер на DPR2 выбирал ровно ту ступень, что отдаёт мастер; #1224 опустил потолок
до 1600 по замеру на **legacy_conversion**-роуте и тем снял последнюю рабочую ступень
у `uploads/**`. Мобильный набор (потолок 800) был сломан с самого включения флага.

Фронт был закрыт точечным обходом: класс `uploads/**` спрашивался с явным `f=jpeg`
(`LEGACY_UPLOAD_TRANSFORM_FORMAT`). Это было объявленное поведение контракта v7 —
`explicit_format_overrides: {"jpeg": "transform"}` в `route_behavior.legacy_upload`
уводил явный jpeg в динамический ресайз.

**Обход снят в #1753.** В proxy-contract v16 то же поле объявлено как
`{"jpeg": "unsupported_format"}`: динамический ресайз убран вместе с #1168, и
запрос с `f=jpeg` отвечает **400** `unsupported-format`. Замер прода 2026-09-04,
`uploads/1620061579IMG_6533.JPG?w=800&q=80&fit=contain`: с `&f=jpeg` → 400, без него
→ 200 `stored-master-fallback` 190 060 B. По access-log за 72 часа обход давал 17
запросов и 17 ответов 400 на живой опубликованной странице.

Сегодня класс обслуживается объявленной v16 политикой
`missing_derivative: v1_then_master_no_transform`: любая ступень отдаёт мастер
целиком с `cache-control: no-store` (замер того же дня: w=320…1600 → 200, 190 060 B
на каждой). Картинка видна, но ширина на вес не влияет и кэш её не держит. Точек,
которые обязаны совпадать, по-прежнему три: `htmlTransform` (тело статьи),
`imageProxy.optimizeImageUrl` (остальные потребители) и гейт
`scripts/post-deploy-media-check.js` — у последнего класс вынесен в
`DECLARED_MASTER_FALLBACK_FAMILIES`, чтобы объявленный фолбэк не считался поломкой,
но 400/404 и `source-pass-through` на нём валят гейт по-прежнему.

Цена сегодняшнего состояния — мастер целиком на каждый показ плюс `no-store`, то есть
повтор на каждую загрузку страницы. Насколько это дороже производной, видно по таблице
ниже на одном ключе: `1591876434DSC_0089.JPG` — 273 905 B мастером против 110 500 B в
w800. Это цена видимого фото вместо битого, и снимает её только backfill (ниже). Обход
#1233 стоил дешевле — JPEG вместо WebP, +25% к весу производной (замер 2026-08-04 на
здоровом ключе, `legacy/5741/…-detail_hd.jpg?w=800`: webp 128 836 B против jpeg
161 390 B), — но в v16 он перестал работать вовсе.

### Лестницы у `uploads/**` нет и не будет — одна ширина 800

Обмер **160 мастеров класса** на проде 2026-08-04: ширина **500…1000 px**, медиана
750, шире 1024 нет ни одного файла. Legacy-загрузки приходили из редактора уже
ужатыми, поэтому ступени выше 800 покупают ноль пикселей за реальные байты:

| ключ (ширина мастера) | мастер | w800 | w960 | w1600 |
|---|---|---|---|---|
| `1591264022IMG_5838.jpg` (≤800) | 136 637 | 95 789 | 95 789 | 95 789 |
| `1591264094IMG_5870.jpg` (≤800) | 148 034 | 100 171 | 100 171 | 100 171 |
| `1591876434DSC_0089.JPG` (~1000) | 273 905 | 110 500 | 156 890 | 185 587 |
| `1592240006IMG_6121.JPG` (~1000) | 178 548 | 72 033 | 101 526 | 123 715 |

Колонки `w*` сняты 2026-08-04 на ещё живой ветке динамического ресайза (`f=jpeg`).
Сегодня такого ответа у класса нет вовсе: по `v1_then_master_no_transform` любая
ширина отдаёт мастер (замер 2026-09-04 — 190 060 B на w=320…1600). Таблица остаётся
как **обоснование ширины для backfill**, а не как описание сегодняшней выдачи.

У 56% класса ступени 800/960/1600 отдают **байт в байт один файл** (`upscale: false`),
у остальных — те же 1000 px, но на 40–70% тяжелее. Поэтому `htmlTransform` для этого
класса эмитит **один `src` шириной 800 и не выводит `srcset`/`sizes` вовсе**
(`LEGACY_UPLOAD_FIXED_WIDTH`): браузеру не из чего выбирать, а бэкенду не надо
держать шесть производных на ключ.

800 выбрано по слоту, а не «на глаз»: мобильный слот 100vw при 390 CSS @DPR2 — ровно
780. На desktop слот 720/920 CSS, ему @DPR2 нужно 1440/1840, но такого исходника в
классе не существует вовсе — максимум, что удалось бы добрать, это 1000 px за +40%
веса.

Это же снимает вопрос «зачем телу статьи ресайз»: он нужен не ради подгонки под слот,
а ради веса (мастер 273 905 B → 110 500 B на том же кадре) и перекодирования. Ради
этого достаточно ОДНОЙ производной, а не набора.

**Лечится по-настоящему** не backfill'ом: заводившаяся под него BE-задача закрыта как
ненужная (#1222 `wont_do` — «backfill `uploads/**` снят миграцией #1245»). Класс
уходит перезаливом тел статей в канонический `travel-description-image` (#1245),
и остаток виден пересчётом: на 2026-09-04 это **8 ссылок** — статьи 116 (3 фото),
171 (2), 220 (1), 290 (1) и один PDF в 525. Когда остаток обнулится, цель
`media-resize-uploads` перестанет строиться, запись `DECLARED_MASTER_FALLBACK_FAMILIES`
в гейте станет мёртвой и снимается вместе с ней; `LEGACY_UPLOAD_FIXED_WIDTH` остаётся
до последней ссылки.

### Лестницу тела статьи надо клэмпить по семейству ИСТОЧНИКА

Наборы `articleBody*` описывают **слот-потребитель**, а не то, что есть у файла. В
телах статей лежат ключи чужих семейств, и потолки у них разные:

| ключ в теле | профиль | верхняя производная | `w=1600` |
|---|---|---|---|
| `gallery/**`, `travel-image/**` | `travelMedia` (мастер 2500) | 1600 | 200 |
| `travel-description-image/**` | `articleBody` (мастер 1920) | 1600 | 200 |
| `address-image/**` | `routePoint` (мастер **1200**) | **960** | **400** |

Замер прода 2026-08-04, `address-image/15601/conversions/…webp`: `w=800` и `w=960`
→ 200, `w=1600` → **400**. На desktop @DPR2 слот 920 CSS требует 1840, кандидата
такой ширины нет, и браузер берёт самый широкий — 1600. Проверено в живом браузере
на `/travels/zabroshennye-dvortsy-…`: **14 из 14** таких фото не отрисовывались.
По сайту — 30 фото в 5 статьях.

`optimizeImageUrl` этот клэмп имеет с #1224, трансформация тела — не имела: она
тогда единственная строила `srcset` сама, мимо `imageProxy`. Теперь клэмп есть в
обеих ветках, где фронт **строит URL сам**, и берётся из одного места —
`familyDerivativeCeiling` в `constants/imageContract.ts`, — и тот же клэмп
применяется к префетчу, иначе `<link rel=prefetch>` грел бы 400 (#1213).
Семейство считается по адресу **до** rewrite на legacy-роут
(`familyRouteOfMediaUrl` в `utils/mediaUrl.ts`): после rewrite путь выглядит как
`/media-resize/legacy/15601/conversions/…`, где первый сегмент — id записи, а не
роут.

Если семейство определить всё-таки нельзя — в теле статьи лежит ссылка прямо в
бакет или уже переписанный legacy-адрес, — лестница клэмпится
`UNKNOWN_FAMILY_DERIVATIVE_CEILING`. Это **самый узкий** из профилей, достижимых
через legacy-роут, а не самый широкий: `proxy-contract` отдаёт для класса
`legacy_conversion` ровно два семейства, `travel` (верхняя производная 1600) и
`route_point` (960), и какое из них за конкретным id — по адресу не видно. Ошибка
несимметрична: перелёт — это 400 и битое фото (`address-image/15601/conversions/…`
→ `w=1600` → 400), недолёт — только резкость. Раньше такой адрес не клэмпился
вовсе, и это было безопасно лишь потому, что набор `articleBodyDesktop` сам
обрывался на 1600 — свойство набора, а не роута: у `route_point`-конверсий уже
`w=1600` отвечает 400. Клэмп появился в #1373 и остаётся при любом составе
набора; замер прода 2026-08-10 по `legacy/682/conversions/…webp`: `w=1600` → 200
`stored-derivative`, `w=1920` → **400**.

Этот запасной потолок — только у лестницы тела статьи: `optimizeImageUrl` его не
применяет, потому что его вызывающие передают ширины из собственных контрактных
наборов, включая осознанный запрос мастера для печати (`printFull` 2500). Общий
для обеих веток остаётся `familyDerivativeCeiling`.

#### На адресах манифеста клэмпа больше нет (#1260 → #1261)

С #1256 клэмп какое-то время стоял и на готовых адресах: `media.article_body`
строил лестницу по слоту-потребителю и обещал `w=1600` ключам `address-image/**`.
Причина устранена на стороне контракта — #1260 сделал `storage_policy` и лестницу
производными от **профиля источника**. Замер прода 2026-08-05 на том же
`address-image/15601/conversions/…webp`: `profile: route_point`, `master_width:
1200`, `srcset` обрывается на 960; обход 4 статей (885 URL манифеста) — 0 non-200.

Поэтому фронт (#1261) потребляет `src`/`srcset` манифеста **дословно**, а своей
таблицы потолков для этой ветки не держит: две таблицы ширин расходятся молча
(#1170, #1220), а фронтовая ещё и слепа к `/media-resize/legacy/…`. Что осталось
на фронте — это отбор ступеней под слот, и он к семействам отношения не имеет:
мобильный слот 100vw @DPR3 просит 1170, и с полной лестницей браузер взял бы 1600
(+48% мобильного трафика на выборке из 10 кадров статьи 544).

Регресс контракта ловит не клиентский код, а пост-деплой гейт: `npm run
test:media:postdeploy` обходит **каждую** ступень `media.article_body[*].srcset`,
считает любой non-200 ошибкой и сверяет верхнюю встреченную ширину с профилем
семейства (`scripts/post-deploy-media-check.js`). Выборка статей задаётся
`--article-body-scan <n|all>`; сколько статей и ступеней проверено, гейт печатает
всегда, чтобы усечённое покрытие не выглядело как полное.

> Обход шлёт сотни запросов подряд, и прод под такой нагрузкой отвечает 503
> `capacity-rejected` (тот самый ярус «Django, concurrency = 1» из таблицы ниже).
> Гейт отличает backpressure от дефекта контракта и ретраит его, иначе правило
> «любой non-200 — ошибка» валило бы деплой по нагрузке, которую гейт сам создал.
> Краткий 502 (разовый сбой upstream-цепочки, #1373) ретраится тем же
> ограниченным механизмом; постоянный 502 после исчерпания попыток — ошибка.

> Урок общий: ширину нельзя выбирать только по слоту. Слот говорит, сколько
> пикселей нужно; профиль источника — сколько их существует. Ошибка ровно в этом
> месте уже стоила #1224 и этой регрессии.

**Регрессия family-роутов — 2026-08-02, открыт #1195 (P0).** Model-owned роуты
(`/gallery/`, `/travel-image/`, `/quest-cover/`, `/avatar/` и остальные восемь)
переключены на `default_mode: source_passthrough` при отсутствующей
предгенерации `d/v1/` и отдают **мастер на любой ширине**, помечая ответ
`x-metravel-image-transform: source-pass-through` и `cache-control: no-store`:

```
travel-image/682/conversions/10f0a8f2….webp   w=96 / 320 / 720 / 1920 → 132 344 B во всех
   (замер 2026-07-30 на том же URL: w=96 → 2 582 B, w=720 → 69 494 B)
тот же URL с ?f=jpeg          w=96 → 2 888 B, w=720 → 81 114 B — движок ресайза жив
8 обложек каталога на w=480   1 147 090 B вместо 250 968 B (×4.6)
```

Пока #1195 не закрыт, любые замеры «сколько весит картинка на проде» через
family-роут показывают размер мастера, а не ступени. Legacy-роуты
`/media-resize/*` этой регрессией **не затронуты** — они `transform`.

*Частичный фронтовый обход (2026-08-02).* Класс `**/conversions/**` уведён с
family-роутов на `/media-resize/legacy/` (см. `toLegacyResizePath` выше), поэтому
карточки каталога и фото точек снова получают ступень и `immutable`. Замер
`/search` desktop 1280: 6 обложек 985 914 B `no-store` → 864 200 B `immutable`,
повторный заход 0 B из сети (был полный перезапрос на каждый показ); выборка из
30 обложек на `w=320` — 5 705 100 B → 589 160 B. **Обход не покрывает** классы
без legacy-роута, и они ждут #1195:

```
плоский корень       /gallery/<hash>.webp?w=320   110 084 B no-store  (?f=jpeg → 14 848 B immutable)
именованная конверсия /address-image/4005/conversions/…-thumb_400_wp.webp
                                                   25 528 B no-store  — размер верный, кэша нет
```

**Узкие места (все замерены):**

| ярус | конфигурация | следствие |
|---|---|---|
| nginx | `proxy_cache_valid 200 1h` в общей зоне `metravel_cache` 1536m, `inactive=24h`, вместе с OSM-тайлами и API | immutable-производная живёт час |
| Redis | `redis-images`: `maxmemory 256mb`, `allkeys-lru`, контейнер 320m | горячий набор не помещается физически |
| Django | 1 vCPU, transform concurrency = 1, при переполнении `capacity-rejected` 503 | 33 события `capacity_rejected` и 33 image-5xx за 10 минут; transform p95 **1322 мс** |

Ни один ярус не вмещает 11 ГиБ × N вариантов, поэтому производные
пересчитываются постоянно. Это и есть корень «картинки конвертируются на каждый
запрос». Закрывается #1154 (ёмкость и TTL) и #1136 (предгенерация).

CDN нет: `cdn.metravel.by` присутствует в CSP и preconnect, но не отвечает
(код 000). Решение владельца 2026-07-30: **CDN пока не поднимаем.**

### Тело статьи берёт адреса из манифеста — #1256, 2026-08-04

`htmlTransform` был последним местом на фронте, которое собирало медиа-URL само
(`?w=…&q=80&fit=contain`): #1203 перевёл на манифест обложку, галерею, точки и
квесты, но `media.article_body` доехал на прод позже и остался непрочитанным.
Теперь `<img>` тела адресуется ступенями из манифеста, а сопоставление разметки с
ним идёт **по ключу изображения**, не по индексу (до `normalizeImgTags` в HTML
успевают появиться чужие `<img>` — instagram-фасады).

Что при этом осталось на фронте — и почему:

- **`sizes`.** Подсказка манифеста описывает слот вслепую:
  `(max-width: 768px) 100vw, 1280px`. Реальные слоты тела — 720 CSS на 1280vw и
  920 на 1920vw. С подсказкой манифеста desktop @DPR1 выбирал бы 1600 вместо
  800/960: замер 2026-08-04 на 10 кадрах travel 544 — 1 403 792 B против
  946 638 B. Адресация файла — дело бэкенда, размер слота — дело вёрстки.
- **Наборы `articleBody*`.** Теперь это не копия лестницы, а ЗАПРОС слота: каждая
  ширина ложится на ближайшую ступень манифеста, поэтому смена набора производных
  на бэкенде правки фронта не требует. Без набора мобильный слот 100vw @DPR3
  просил бы 1170 и брал 1600 — те же +48% трафика на тех же 10 кадрах.
- **Клэмп по семейству.** Обязателен и для готовых URL: манифест помечает
  профилем `article_body` каждую картинку тела, включая ключи чужих семейств, и
  обещает им 1600. Независимая проба 2026-08-04 по всем 222 ступеням манифеста
  статьи `/travels/zabroshennye-dvortsy-…`: **14 ответов 400, все — `w=1600` на
  `address-image/**`** (реальный профиль `routePoint`, потолок 960); контроль на
  `travel-description-image` и `gallery` той же ширины → 200. То есть манифест
  переобещает, и дословная подстановка вернула бы регресс #1233. Заведено на
  бэкенд — #1260; после его закрытия клэмп на фронте снимается.

Классы, которых манифест не покрывает (`uploads/**` — `srcset` пуст, `src` ведёт
прямо в бакет; внешние картинки; legacy-цепочки weserv), идут прежним клиентским
путём. Это штатный фолбэк: подставить бакетный `src` значит вернуть #1176.

Сборка индекса и отбор ступеней — `components/travel/stableContent/articleBodyMedia.ts`;
разбор `srcset*` переиспользуется из `utils/travelMediaVariants.ts`, своей копии
разбора нет.

### 2.5 Что запрашивает фронт

`utils/imageProxy.ts` → `optimizeImageUrl(url, { width, quality, format, fit })`.
Ширина в подавляющем большинстве мест **вычисляется из измеренного слота**, а не
задана константой: `targetWidth`, `requestWidth`, `stableWidth`, `px * 2`, `maxW`.

Фронтовая лестница `DIMENSION_LADDER` приведена к бэкендовым 15 ступеням в #1170;
соответствие держит тест `__tests__/utils/imageProxy.ladder.test.ts`, который
сверяет её со снапшотом `GET /api/media/proxy-contract` (прод отдаёт version 4,
проверено 2026-08-02; `quality.values` явно включает 85, а `route_behavior`
описывает family- и legacy-роуты). Семантика quality тоже
зеркалит backend: промежуточное значение округляется **вверх** (`72 → 80`,
`82 → 85`), invalid/out-of-range возвращает default q85. Runtime-consumers
поэтому передают сразу канонические q60/q70/q80/q85, не рассчитывая на snap.

**Целевая storage-policy и переходные frontend-наборы —
`constants/imageContract.ts`** (#1167). Там теперь разделены:

- `IMAGE_STORAGE_POLICY_V1` — какие мастера и производные должны лежать в S3;
- `IMAGE_WIDTHS` — кандидаты ключевых frontend-слотов на время
  двусторонней миграции;
- `DIMENSION_LADDER` в `utils/imageProxy.ts` — вся capability-лестница
  текущего динамического proxy, а не список S3-файлов.

Проверяется тестом
`__tests__/constants/imageContract.test.ts`:

- каждая ширина набора — ступень лестницы, и **не снэпится**: запрошенное равно
  полученному (иначе бэкенду нечего предгенерировать под этот экран);
- каждое quality лежит на явной сетке backend-контракта
  `20, 30, 40, 50, 60, 70, 80, 85, 90` и не квантуется;
- мастер не дублируется среди derivatives, а ключевые frontend-наборы
  полностью покрыты storage-profile;
- в `htmlTransform.ts`, `TravelDetailsOptimizedLCPHero.tsx`, `QuestCard.tsx` и
  `printImageUrl.ts` не осталось собственных литеральных списков ширин;
- для каждого реального слота в наборе класса есть кандидат **не меньше** нужного
  (нет апскейла) и **с перелётом ≤ 35 %** (нет дыры вроде 640 → 1280 из #1170).

**Quality было 12 разных значений** (28, 40, 60, 65, 66, 70, 72, 75, 78, 80, 85,
90). В target policy остались q70 для малых, q80 для крупных и q85 для
мастера/print. Backend proxy-contract уже явно разрешает q85; старое frontend-
округление «до десятка» ошибочно превращало `q85` в `q90`; исправлено в
`utils/imageProxy.ts`, `scripts/generate-seo-pages.js` и print URL tests 2026-08-02.

Обложка квеста остаётся на q60 **как отдельный media-family profile**:
замер 2026-07-31 на нормализованной обложке дал 1 918 B для `w=320` и 5 390 B
для `w=640`; второй вариант закрывает DPR2 без видимого апскейла. Это не
означает «любой `w=480` имеет q60»: `travelMedia/480` имеет q70.

## 3. Почему нельзя просто «предгенерировать всё»

Число вариантов на одну картинку — произведение:

```
ширины × quality × форматы × fit
  10   ×    6     ×    2    ×  1   = 120 файлов на изображение
```

Форматов два, потому что ответ идёт с `Vary: Accept`: WebP клиентам и JPEG всем
остальным — это две разные записи кэша и два разных файла.

На ~10 000 живых изображений это **1.2 млн объектов**. Предгенерация в таком виде
невозможна ни по месту, ни по времени.

**Отсюда следует, что фиксировать нужно не только ширины.** Контракт размеров
(#1167) обязан зафиксировать три оси сразу:

1. **Формат** — свести к WebP. JPEG оставить только там, где он доказанно нужен
   (соцсети/краулеры, не понимающие WebP), и только для одной ширины.
2. **Quality — одно значение на пару `(media family, width)`**, а не на
   каждый вызов. Это позволяет quest cover оставаться на q60, не превращая
   все остальные файлы той же ширины в q60.
3. **Ширины — короткий перечисленный набор**, покрывающий реальные слоты, а не
   вся лестница прокси.

### Сколько файлов на одну картинку

Утверждение «2–3 файла на изображение» было неверным. Оно не покрывало уже
закреплённые слоты:

- quest card 320–420 CSS × DPR2 требует кандидата 640/800;
- article body имеет слоты 390, 720 и 920 CSS на DPR1/2, то есть от 480 до
  1600;
- travel cover/gallery одновременно используются как 60px-миниатюра,
  card, hero, gallery и print.

Целевая policy v1 хранит **3–11 файлов на source, включая один мастер**:

| storage profile / роуты | мастер | производные в S3 | всего |
|---|---:|---|---:|
| avatar / `avatar` | 320 q85 | 96, 160 q70 | **3** |
| badge / `badge-image` | 320 q85 | 96, 160 q70 | **3** |
| quest cover / `quest-cover` | 1200 q85 | 320, 480, 640, 800 **q60** | **5** |
| route point / `address-image` | 1200 q85 | 320, 480, 640 q70; 800, 960 q80 | **6** |
| quest supplement / `quest-step-image`, `quest-poster` | 1200 q85 | 320, 480, 640 q70; 800 q80 | **5** |
| trip cover / `trip-cover` | 1200 q85 | 320, 480, 640 q70; 800, 960 q80 | **6** |
| travel cover/gallery / `travel-image`, `gallery` | **2500 q85** | 96, 160, 320, 480, 640 q70; 720, 800, 960, 1280 q80; 1600 q85 | **11** |
| article body / `travel-description-image` | 1920 q85 | 480 q70; 800, 960 q80; 1600 q85 | **5** |

Таблица зеркалит `IMAGE_STORAGE_POLICY_V1`; тест проверяет, что все её ширины
поддерживаются текущим proxy-contract. Мастер считается один раз, и его ширина
никогда не дублируется производной — см. историю `content_1920` ниже.

Quality однозначно для **family + width**. Поэтому `questCover/480 q60` и
`travelMedia/480 q70` не конфликтуют, а у одного travel source не появляются
q60/q70/q80-дубли одной ширины.

**Ширина мастера у тела статьи — только мастер.** Профиль `article_body` прожил
одни сутки с производной `content_1920`, равной мастеру по ширине: бэкенд завёл
её, закрывая #1215 (двойное скачивание `no-store`-мастера на desktop @2x), и
FE-зеркало успело это состояние отзеркалить (#1373; проба прода 2026-08-10 23:41:
`w=1920` → 200 `stored-derivative` `immutable`, `w=1921` → 400). Тем же днём
shrink-коммит бэкенда `9136878` (openspec `shrink-article-body-derivative-profile`)
снял `content_1920` вместе с `content_320`/`content_640`: спека прямо запрещает их
раздавать («SHALL NOT expose content_320, content_640, or content_1920, regardless
of durable-read coverage state»), точная ширина мастера отдаётся мастером с
`no-store`, а 1601…1919 в durable-режиме отвечают 400.

Наутро 2026-08-11 сжатый профиль уже был на проде: манифест travel 544 отдаёт
`srcset` 480/800/960/1600 и `variants` без `content_1920`. Промежуточный контракт
ещё показывал `requested_mode: durable_s3_derivatives`, `active_mode:
dynamic_transform` и сброшенное покрытие, но это состояние прожило несколько
часов. Текущий `proxy-contract` v12 перешёл на пообъектную схему:
`route_behavior.*.default_mode: per_object_derivative`, отсутствующая производная
чинится как `bounded_repair`, а точная ширина мастера остаётся `no-store`.
`family_modes` и глобального coverage-switch в этом контракте больше нет.

Слот 920 CSS @DPR2 (нужно 1840) закрывается верхней производной 1600 с апскейлом
×1.15 — осознанная цена решения бэкенда: кэшируемая производная лучше и битого
фото (400), и `no-store`-мастера, качающегося на каждый визит. Веса потолок 1600
не меняет: у мастеров ≤ 1600 px ступени 1600 и 1920 отдавали байт в байт один
файл (замер 8 ключей трёх статей 2026-08-10, 1 642 540 B на обеих ступенях).
Подрезка лестницы манифеста по реальной ширине мастера конкретного кадра —
отдельная задача.

### История coverage-switch до пообъектного режима v12

До contract v12 раздача переключалась на готовые файлы **не флагом, а измеренным покрытием**.
Пока в семействе есть хоть один мастер без полного набора производных, fail-safe
держит семейство на ресайзе в момент запроса — том самом переходном пути, который
по §1.3 подлежит удалению (#1168). Наблюдать это можно без доступа к серверу, в
публичном контракте: `route_behavior.model_owned.family_modes.<family>` содержит
`requested_mode`, `active_mode` и `coverage`.

Замер 2026-08-09, контракт v9:

| семейство | active_mode | мастеров | полных | покрытие |
|---|---|---:|---:|---:|
| travel | durable_s3_derivatives | 5 181 | 5 181 | 100 % |
| route_point | durable_s3_derivatives | 2 529 | 2 529 | 100 % |
| quest_cover | durable_s3_derivatives | 139 | 139 | 100 % |
| quest_supplement | durable_s3_derivatives | 138 | 138 | 100 % |
| avatar | durable_s3_derivatives | 5 | 5 | 100 % |
| **article_body** | **dynamic_transform** | **6 650** | **5 607** | **84,3 %** |

То есть тело статьи — единственное семейство, которое не доехало, и именно
поэтому его фотографии до сих пор режутся на лету.

**Почему покрытие показывало 84,3 %.** Напрашивающееся объяснение — «перезалили
тысячи кадров и не прогнали backfill»: #1180 закрыл семейство на 100 %
2026-08-03 при 1 313 мастерах, а миграция тел статей (#1245) и чистка base64
(#1320) довели их до 6 650 уже после прогона. Оно оказалось **неверным**.

Догоняющий прогон 2026-08-09 обошёл все 6 715 источников модели и **не создал ни
одного объекта**: у каждого мастера набор производных уже был полным. При этом
утренний замер (`measured_at 05:59`) показывал 1 043 неполных мастера, а
вечерний, на тех же данных и без единого нового файла между ними, — 100 %.

То есть дыра была не в хранилище, а **в измерении**, на которое завязан
fail-safe. Практический вывод для отладки: расхождение `active_mode` и
`requested_mode` означает лишь то, что последняя МЕТРИКА не сошлась; прежде чем
списывать это на отсутствие файлов, прогон backfill в `--dry-run` покажет,
существует ли недостача на самом деле. Причина занижения принадлежит #1201.

Правило, которое из этого следует и которое стоило шести дней динамической
раздачи: **после массовой перезаливки картинок и вообще при любом расхождении
режимов метрику надо пересчитывать и проверять**, а не считать, что раз прогон
когда-то закрыл семейство на 100 %, оно там и осталось. Пока расхождение живёт,
семейство молча раздаётся переходным путём, и все замеры «почему у нас тяжёлые
картинки» уводят в сторону файлов вместо режима раздачи.

Догоняющий прогон живёт в `scripts/backfill-article-body-derivatives.sh`: он
гоняет штатную backend-команду `backfill_image_derivatives` партиями с курсором,
своей логики генерации не имеет и завершается по `objects_visited == 0`.

Три грабли этого прогона, каждая стоила отдельного круга:

- **Покрытие в контракте — снимок, а не живое значение.** Его считает отдельная
  команда `measure_image_derivative_coverage` и кладёт в контракт вместе с
  `measured_at`. Пока её не запустили, только что созданные объекты не видны,
  семейство остаётся в прежнем режиме, и прогон выглядит бесполезным. Скрипт
  пересчитывает метрику сам по завершении обхода.
- **В контейнере два лок-файла с правами 640 у разных владельцев.** Команда берёт
  свой лок и общий лок обработки изображений, который создаёт gunicorn при первой
  же загрузке картинки. `docker exec` без `-u` заходит как root и упирается в лок
  приложения, а после первого root-запуска его собственный лок становится
  недоступен уже приложению. Ходить надо всегда под uid веб-процесса.
- **Полнота определяется по `objects_visited == 0`, а не по `next_cursor`.**
  Курсор присутствует в ответе всегда, в том числе после полного обхода.

**`q` и `fit` на family-роутах мертвы.** Раз вариант нарезан заранее, качество
задаёт профиль, а `fit` — сам вариант, и присланные параметры бэкенд игнорирует.
Замер прода 2026-08-09 на `travel-description-image`: `?w=640`, `?w=640&q=70`,
`?w=640&q=70&fit=contain`, `?w=640&fit=cover`, `?w=640&q=20` — все пять отдают
157 952 B байт-в-байт; на `quest-cover` (семейство с cover-вариантами) — 3 486 B
на все формы. Но каждый набор параметров — ОТДЕЛЬНЫЙ URL: своя запись в
nginx-кэше, своя в браузерном, и один файл качается заново, стоит другому экрану
собрать адрес чуть иначе. Манифест таких параметров не ставит вовсе, поэтому
«через манифест» и «через `optimizeImageUrl`» давали два адреса на один слот.
`optimizeImageUrl` больше не отправляет `q`/`fit` на family-роуты; для
legacy-роутов (`/media-resize/**`), которые остаются на ресайзе в момент запроса,
оба параметра работают и отправляются по-прежнему.

**Гейт против рецидива.** `scripts/post-deploy-media-check.js` понимает обе схемы.
Для старого контракта он читает
`route_behavior.<key_class>.family_modes.<family>` и падает при откате с
`durable_s3_derivatives` (`coverage.mode_regressed`). Для v12 проверяет у каждого
класса `default_mode: per_object_derivative` (`delivery.mode_regressed`). Если
контракт не содержит ни одной из схем, это ошибка, а не молчаливый зелёный
результат.

### Что «большие картинки в теле статьи» значат на самом деле

Разбор 2026-08-08/09 (#1337), ещё при coverage-switch, прошёл три круга и
закончился не там, где начался:

1. **«Ресайз не работает».** Работает: `srcset` собирается из манифеста, каждая
   ступень отвечает 200 `image/webp`.
2. **«Кадры хранятся раздутыми, надо пересайзить».** Проверяемо, но почти
   бесполезно: у кадра 768×1024 ступени 800/960/1600 возвращают мастер
   байт-в-байт (317 486 B), потому что прокси не апскейлит, — и на первый взгляд
   уменьшение самого файла даёт −44 %. На ступенях, которые останутся после
   перехода на предгенерацию, тот же приём даёт лишь −10 %.
3. **Настоящая причина — режим раздачи.** Динамический путь кодирует ступень с
   q85 (совпадает побайтово с локальной перекодировкой webp q85), тогда как
   durable-производная той же ширины у обложки весит 91 256 B против 216 230 B у
   тела статьи. Профиль для `article_body` предписывает q70 на 320/480/640 и q80
   на 800/960 — этих качеств кадры тела не видят, пока семейство на динамике.

Вывод: вес фотографий в теле статьи лечится покрытием и параметрами профиля, а не
уменьшением исходников. Пересайз файлов остаётся точечным инструментом на время
переходного периода и массово не применяется.

### Чего в наборе НЕТ и почему

- **Нет отдельного 32px LQIP.** В манифесте уже лежат `blurhash` и
  `dominant_color` — заливка полей рисуется из данных, без сетевого запроса. Это
  и был смысл #1127. `lqip_url` был реальным файлом и реально качался, то есть на
  слот приходилось ДВА запроса. **Сделано в #1167:** фронт его больше не
  запрашивает нигде — ни в слайдере, ни в hero, ни в SSG-оболочке. Прекращение
  выдачи поля в API — задача бэкенда; до неё поле просто игнорируется.
  **С #1208 сетевой подложки нет вообще**: ни рантайм-hero, ни SSG-шелл не
  просят `w=96&q=40`, поля заливает только `dominant_color`.
- **Нет 2500 как отдельного варианта.** Для путешествий это сам мастер (#1156):
  поднимаем мастер до 2500 и убираем поле `print_image`, вместо того чтобы
  держать два носителя.

Старую оценку «20–30 тысяч объектов» тоже нельзя считать валидной: она была
выведена из ошибочных 2–3 файлов. Точный прогноз делает dry-run #1136/#1180 по
формуле `sources × (1 master + derivatives профиля)` и прикладывает число объектов/байт
до любой S3-мутации.

## 4. Контракт: как называется файл и как выглядит запрос

Проектируется под предгенерацию (#1136, #1167). Публичные URL при этом **не
меняются** — меняется только то, что происходит внутри при их обработке.

### 4.1 Ключ производной в хранилище

Мастера лежат по существующим ключам и остаются как есть:

```
<travel_id>/gallery/<uuid>.webp          галерея путешествия
<travel_id>/description/<uuid>.webp      картинка в теле статьи
<travel_id>/conversions/<uuid>.webp      обложка путешествия, фото точки
quests/<id>/main/<uuid>.webp             обложка квеста
profile/<id>/avatar/<uuid>.webp          аватар
<uuid>.webp                              легаси плоский корень (живой)
```

Производная получает **детерминированный ключ, выводимый из ключа мастера**:

```
d/v1/<ключ мастера без расширения>/<ширина>.webp
```

Примеры:

```
мастер       682/gallery/8e643f0e4e3845c793536a0dd2ff7949.webp
производные  d/v1/682/gallery/8e643f0e4e3845c793536a0dd2ff7949/480.webp
             d/v1/682/gallery/8e643f0e4e3845c793536a0dd2ff7949/800.webp

мастер       quests/1/main/f13761640bf34213866aeec5d6f50aa9.webp
производная  d/v1/quests/1/main/f13761640bf34213866aeec5d6f50aa9/480.webp
```

Почему именно так:

- **Выводится без обращения к БД.** Зная ключ мастера и ширину, обработчик
  запроса сразу знает, где лежит файл. Никакого дополнительного индекса.
- **Удаляется одним префиксом.** Удаление мастера = удаление префикса
  `d/v1/<ключ>/`. Это ровно то, чего не хватает lifecycle-сервису (#1132), где
  сейчас нужен «bounded per-source variant index».
- **Версионируется целиком.** Смена энкодера, quality или набора ширин → пишем в
  `d/v2/`, а `d/v1/` сносится одной операцией. Без версии любое изменение
  превращается в неразрешимую задачу инвалидации.
- **Не смешивается с мастерами.** Отдельный корень `d/` означает, что
  инвентаризация и аудит сирот (#1155) классифицируют объект по первому сегменту
  ключа, а не эвристикой по имени — как сейчас приходится делать с
  `conversions/` и `responsive-images/`.

Quality в имя не входит: оно **однозначно определяется storage-profile и
шириной** (см. §3). Профиль однозначно выводится из family/source key:
`quests/.../480.webp` — q60, `gallery/.../480.webp` — q70. Версия `v1`
фиксирует весь encoder/profile contract; смена quality создаёт `d/v2`, а не
перезаписывает immutable `v1`. Формат задан расширением `.webp`.

### 4.2 Публичный URL

Остаётся сегодняшний, ради обратной совместимости SSG, og:image и offline-паков:

```
GET /<family>/<ключ мастера>?w=<ширина>
```

где `family` — один из `gallery | travel-image | travel-description-image |
address-image | quest-cover | quest-poster | quest-step-image | avatar |
trip-cover | badge-image`.

**В целевом S3-контракте фронт отправляет ровно один параметр — `w`.**
Ни `q`, ни `f`, ни `fit`, ни `h`, ни `dpr`. Текущий runtime пока оставляет
`q/f/fit`, пока #1136 не создаст и не заполнит в S3 весь family-specific набор.

| параметр | почему не отправляем |
|---|---|
| `q` | однозначно выводится из family + `w` на стороне сервера |
| `f` | формат всегда WebP; JPEG — только отдельный роут для краулеров |
| `fit` | уже схлопывается в одну идентичность, влияния на байты нет |
| `h` | прокси игнорирует; каждое значение плодит cache-key |
| `dpr` | прокси игнорирует; DPR учитывается умножением самой `w` |

Результат: URL ↔ файл становится **отношением один к одному**, а ключ кэша
сводится к `family:ключ:w`. Сегодня в ключе участвуют ещё формат и quality
(`img:v3:$image_cache_format:$uri:w=…:q=…`), что размножает записи кратно.

### 4.3 Как сервер обрабатывает запрос

```
1. w отсутствует                        → HTTP 400
2. w не из набора family                → округление вверх до ближайшей ступени этого profile
3. w выше максимума                     → отдаём мастер (апскейла нет)
4. есть d/v1/<ключ>/<w>.webp            → отдаём файл, БЕЗ декодирования
5. файла нет                            → динамический ресайз (переходный
                                          фолбэк) + постановка в генерацию
```

Шаг 1 — изменение поведения: сегодня запрос без `w` молча отдаёт мастер целиком
(132 344 B вместо ~35 000 B на карточку). Это источник дефектов #1112, #1120,
#1170. Молчаливая отдача мастера должна стать ошибкой, а не фолбэком.

Шаг 5 удаляется в #1168 — но только после того, как метрика покажет, что он
практически не срабатывает.

### 4.4 Что меняется в коде фронта

`ImageOptimizationOptions` сокращается с семи полей до одного:

```ts
// было
{ width?, height?, quality?, format?, dpr?, fit?, blur? }
// станет
{ width: number }   // обязательное
```

`optimizeImageUrl(url, { width })` строит `?w=<snap(width)>` и больше ничего.
Снэп идёт к **набору storage-profile этой family**, а не к полной
capability-лестнице переходного proxy. Это включается только двусторонним
релизом после того, как #1136 положит все эти файлы в S3. До этого frontend
оставляет `q/f/fit` transition-параметры и снэпится к текущему proxy-contract.

## 5. Мёртвый код и no-op параметры

Найдено при разборе 2026-07-30. Всё перечисленное — проверенные факты
(подсчёт вхождений по `components/ app/ utils/ hooks/ screens/ services/`,
отдельно от тестов), а не подозрения.

### 5.1 Экспорты без единого использования в проде

| символ | прод | тесты | вердикт |
|---|---|---|---|
| `clearImageOptimizationCache` | **0** | 3 | удалить вместе с тестами |
| `getImageCacheStats` | **0** | 5 | удалить вместе с тестами |
| `getResponsiveSizes` | **0** | 5 | используется только внутри `imageSrcSet.ts` — убрать из экспорта |

(`buildLqipUrl`, `generateLQIP`, `createLazyImageProps`, `shouldLoadEager`).
Тесты на неиспользуемый код создают ложное ощущение покрытия.

### 5.2 Параметры, которые вычисляются и передаются, но никуда не идут

| параметр | где передаётся | что происходит |
|---|---|---|
| `height` | **11 call sites** | `optimizeImageUrl` не отправляет `h` начиная с #1113/#1116, прокси его игнорирует |
| `dpr` | 2 call sites | не отправляется и игнорируется |
| `blur` | 0 call sites | ветка построения `blur=` в `imageProxy.ts:163,213` недостижима |
| `format: 'auto'` | ~20 call sites | означает «не отправлять `f`», то есть значение по умолчанию |

Самое дорогое здесь — `height`: одиннадцать мест **вычисляют** высоту
(`MEDIA_HEIGHT * 2`, `COVER_HEIGHT * 2`, `optimalSize.height`, `stableHeight`,
`requestHeight`), передают её, и она отбрасывается. Это не только лишний код, но и
ложный сигнал: читающий думает, что высота влияет на результат.

| что | состояние |
|---|---|

### 5.4 Что удалять НЕЛЬЗЯ

## 6. Инварианты — нарушать нельзя

- Frontend всегда материализует `w`. Family-роут без `w` отдаёт мастер;
  `/media-resize/*` скрыто выбирает legacy-default 800, но полагаться на этот
  server default вместо явного канонического параметра запрещено.
- Ширина берётся из измеренного слота × DPR (DPR на web ограничен двойкой) и
  снэпится к набору из контракта. Не «круглое число на глаз».
- `h`, `dpr`, `blur` не отправляются: прокси их игнорирует, но каждое уникальное
  значение создаёт отдельный cache-key и отдельную конверсию.
- Один слот = один эффективный URL для резкого и размытого слоя.
- Изменение набора ширин или quality — **двусторонний релиз**. Односторонняя
  правка на фронте ломает предгенерацию: ровно так в #1137 прогрели 137 обложек
  под `w=1280`, фронт сменил карточку на `w=480`, и всё сломалось заново.
- Любое утверждение о поведении прокси в коде — со ссылкой на контракт, а не на
  разовый замер. Устаревшие комментарии хуже отсутствующих.
- Наличие производных `d/v1/**` **не влияет на выдачу**, пока на бэкенде выключен
  `MEDIA_IMAGE_DERIVATIVE_READ_ENABLED` (default `False`,
  `metravel/envs/common/settings.py`). Предгенерация и переключение выдачи — два
  независимых шага, и порядок между ними обязателен: флаг включается только при
  100% покрытии, потому что при включённом чтении непокрытая картинка отдаёт 404
  с `X-MeTravel-Image-Transform: derivative-missing`, а не мастер. Проверять
  «предгенерация заработала» по весу ответа бессмысленно, пока флаг выключен:
  прод отдаёт мастер даже для источников с уже готовыми производными (#1195).
- Инвариант раздачи проверяется постоянно, а не разово: `npm run
  test:media:postdeploy` (`scripts/post-deploy-media-check.js`, вызывается из
  `build-prod.sh` после SEO-check) берёт по одному URL на семейство из
  публичного API и падает при `source-pass-through`, `no-store` или одинаковом
  весе на двух ступенях семейства (`WIDTHS_BY_FAMILY`, свои у каждого). Исключение
  одно и явное — `DECLARED_MASTER_FALLBACK_FAMILIES`: у `uploads/**` мастер,
  `no-store` и равный вес ступеней объявлены контрактом v16, поэтому эти три
  проверки для класса сняты, а статус, тип, `derivative-missing` и
  `source-pass-through` продолжают валить гейт (#1753). Проверяются обе Accept-ветки:
  браузерная (`image/webp`) и generic (`*/*`) — бэкенд ветвится по `Accept`, и в #1195
  деградировала именно webp-ветка, тогда как явный `f=jpeg` продолжал
  ресайзиться (#1205).

### 8.1 Долгие прогоны на проде — грабли

Проверено 2026-08-02 на прогоне `backfill_image_derivatives` (#1180): 9 390
источников → 74 046 объектов, ~13 часов.

- Прод — **1 vCPU**, лимит памяти app-контейнера — **900 МиБ**. Во время
  генерации контейнер держит ~700 МиБ, запас ~200 МиБ: всплеск = OOM-kill.
  Запускать под `nice` и с паузой (`--sleep-ms`), иначе прогон конкурирует с
  раздачей.
- В crontab пользователя `sx3` стоит `0 4 * * * /home/sx3/restart_metravel_app.sh`
  — **контейнер перезапускается каждую ночь**. Любой прогон длиннее нескольких
  часов обязан переживать рестарт, иначе утром обнаружится мёртвый процесс.
- `docker exec`-процесс умирает вместе с контейнером и **сам не возвращается**:
  `restart=always` поднимает контейнер, но не exec. Нужен либо супервизор на
  хосте, либо запуск партиями (`--limit` + `--cursor`) с сохранением позиции.
- `pkill` с хоста по процессу контейнера не работает (`Operation not permitted`)
  — процесс принадлежит пользователю контейнера. Убивать только изнутри:
  имя контейнера узнать С РАБОЧЕЙ МАШИНЫ —
  `bash -c 'source scripts/deploy-target.sh; metravel_resolve_container_over_ssh app'`
  — и подставить его на хосте: `docker exec '<app-контейнер>' sh -c "kill -9 <pid>"`.
  На прод-хосте `source scripts/deploy-target.sh` не сработает: каталог деплоя —
  это checkout бэкенда, файла там нет, а пустое имя схлопнуло бы аргументы и
  docker принял бы `sh` за контейнер. Имя не хардкодим — compose v1 звал его
  `metravel_app_1`, v2 — `metravel-app-1`, и регулярка существует в одном
  экземпляре (#1636). `<pid>` искать по
  `/proc/*/cmdline` — в образе нет ни `ps`, ни `pkill`, ни `free`; `nice` есть,
  `kill` только как shell builtin.
- `scripts/deploy-target.sh` — bash-скрипт: под zsh `source` падает на
  `BASH_SOURCE`. Вызывать как `bash -c 'source scripts/deploy-target.sh; …'`.
- Файлы обвязки класть **только вне** git-checkout `/home/sx3/metravel`
  (например в `/home/sx3/`), иначе прод-checkout становится dirty и блокирует
  deploy gate по `AGENTS.md`.
- Курсор `next_cursor` печатается только в конце прогона, поэтому после обрыва
  повторный запуск идёт с начала. Это не потеря работы: готовые семейства
  проверяются по HEAD без декодирования — дёшево, но к концу прогона ре-скан
  занимает десятки минут.

**Паттерн супервизора** (применён в #1180, снимается по #1196): цикл на хосте
раз в 60 с проверяет `pgrep -f "manage.py <command>"`, при пропаже процесса
перезапускает команду, ждёт контейнер, если тот ещё не поднялся, и **выходит сам**,
когда полный прогон вернул `created: 0` и `changed: 0` — это же служит
доказательством идемпотентности для Done gate.

Две ошибки, на которых этот супервизор уже спотыкался, — обе тихие:

- **критерий выхода нельзя вешать на `failed: 0`.** В базе есть строки,
  указывающие на исчезнувшие в S3 файлы (#1182): они всегда дают `missing` и
  поднимают `failed`, повторный прогон их не чинит. С таким критерием супервизор
  крутил бы полный ре-скан бакета вечно. Считать завершением `created == 0 &&
  changed == 0`, а `missing`/`corrupt` писать в лог отдельно;
- **single-instance guard нельзя делать через `flock`.** Прогон запускается
  дочерним процессом и наследует открытый дескриптор, поэтому блокировка держится
  все многочасовые сутки прогона — и новый супервизор (например с исправлением)
  не может подняться, пока идёт старый прогон. Использовать pid-файл с проверкой
  `kill -0` плюс сверку `/proc/<pid>/cmdline`.

Отдельно про `pkill -f`: строка-паттерн присутствует и в cmdline самой
ssh/bash-обёртки, из которой её запускают, поэтому `pkill -f <имя-скрипта>`
убивает собственную сессию раньше цели. Убивать по PID либо паттерном с
`[п]ервой-буквой-в-скобках`. Плюс `@reboot` в crontab на случай
рестарта самого сервера. Такая обвязка временная: она заводится вместе с задачей
на её удаление, иначе на проде навсегда остаются процесс и cron-строка, которые
выглядят рабочей инфраструктурой.

## 10. Решения, принятые и закрытые

- **Удаление сирот в S3 остановлено после первого класса** (владелец, 2026-07-31:
  «всё, что есть сомнения — не трогай»). Удалён только `**/responsive-images/**`
  — 33 764 объекта / 5 576 МиБ, префикс мёртв целиком, подтверждено четырьмя
  независимыми способами (база, HTTP, код бэкенда, код фронта).
  Оставшиеся ~1.4 ГиБ (`quests` 520, `conversions` 504, `uploads` 362 МиБ)
  **остаются сознательно**: там сироты лежат вперемешку с живыми в одном
  префиксе, цена ошибки — безвозвратно удалённые фотографии, а выигрыш вчетверо
  меньше уже полученного.

  Отдельный урок: метод HTTP-проб дал ложный вердикт по `uploads/` — весь
  префикс выглядел мёртвым, хотя 4 471 объект живой. Поймал только аудит по
  базе. «Не отдаётся по роуту» не означает «не используется»; для решения об
  удалении годится только проверка по данным.

- **CDN не поднимаем** (владелец, 2026-07-30). Раздача остаётся на прод-хосте;
  выигрыш берём предгенерацией и кэшем.
- **Legacy `conversions/` не нормализуем.** `-detail_hd.jpg` — 1080×1080 по
  ~220 KiB, не раздуты, лишь не в том формате, а ссылки вшиты в HTML статей.
  Конвертация означает переписывание HTML всех статей ради умеренного выигрыша.
  Стоимость перекодирования на промахе закрывается #1154 и #1136.
- **Постеры финалов (141 JPEG, средний 229 KiB) не трогаем** — размер приемлемый,
  риск сломать экран финала не оправдан.
- **Картинки шагов квестов нормализовывать нечего:** прогон по всем 139 квестам
  даёт 0 объектов с `image_url`; все 76 PNG (70.3 MiB) — сироты, уходят в #1155.
