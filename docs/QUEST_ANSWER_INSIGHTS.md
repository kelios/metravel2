# Трение шага: от телеметрии ответов к правке квеста

Рабочий цикл редактора квестов. Инструмент существует, чтобы собранные данные
превращались в конкретную правку контента, — иначе они повторят судьбу
`quest_progress.attempts`, которые лежали в проде с июля и которые до ручного
SQL-разбора никто не прочитал.

## Откуда берутся данные

| слой | что делает | где |
|---|---|---|
| сбор | карточка шага снимает каждую попытку (вердикт, нормализованный ввод, номер попытки, подсказка, время) и кладёт в офлайн-очередь | `utils/questAnswerEvaluation.ts`, `utils/questAnswerTelemetry.ts` (#1276) |
| хранение | append-only таблица `quest_answer_attempt` + staff-агрегат | backend `POST /api/quest-answer-attempts/bulk/`, `GET /api/quests/{id}/answer-stats/` (#1275) |
| применение | этот отчёт | `npm run quest:insights` (#1278) |

Сырой ввод хранится **только** для закрытых типов ответа
(`exact`, `exact_any`, `range`, `approx`, `any_number`). Для `any_text` / `any`
(свободная рефлексия вида «что тебе запомнилось на набережной») не сохраняется
ни на сервере, ни на клиенте: у таких шагов в отчёте есть счётчики трения, но
колонка отклонённых вводов пуста. Это не баг отчёта.

## Как запустить

```bash
npm run quest:insights -- --quest 32 --since 365d
```

| флаг | по умолчанию | зачем |
|---|---|---|
| `--quest <id\|slug>` | — | числовой PK или `quest_id` (`minsk-cipher`) |
| `--since` | `90d` | окно данных |
| `--min-count` | `2` | сколько РАЗНЫХ игроков должны были ввести значение, чтобы оно стало кандидатом |
| `--all` | выкл. | обход всех квестов, сортировка по суммарному трению |
| `--json` | выкл. | машинно-читаемый вывод с теми же числами |

Staff-токен берётся из `.secrets/metravel-task-board.env` и никогда не печатается.

Пустое окно — это не результат: скрипт говорит «нет данных за окно» и выходит с
кодом 1, а не рисует таблицу нулей.

## Метрика трения

```
трение = rejected_per_solver + 2 × hint_open_rate + 3 × abandon_rate
```

Веса зафиксированы константой в скрипте: бросивший игрок дороже открытой
подсказки, подсказка дороже лишней попытки. Без весов шаг с десятком мелких
опечаток обгонял бы шаг, на котором квест просто заканчивают.

## Как читать группы кандидатов

Отчёт раскладывает отклонённые вводы на три группы — и решение по каждой разное:

- **похоже на синоним** — та же сущность другими буквами (`шест` вместо
  `шесть`, `папоротника` вместо `папоротник`). Решение: добавить вариант в
  `answer_pattern` шага.
- **фактически другой ответ** — игрок понял задание иначе, чем задумано.
  Решение: **переписать формулировку задания**, а не расширять словарь.
- **мусор** — заглушки (`хз`, `ааааа`). Решение: ничего.

### Почему нет автоприменения

На quest 32, шаг `3-pobeda` (правильный ответ `6`) самый частый отклонённый ввод
— `33`: игроки складывают цифры даты и не сворачивают сумму. По частоте это
идеальный кандидат в словарь, а по смыслу — нерешённая задача. Добавить `33` в
`answer_pattern` значит засчитывать неверный ответ.

Поэтому классификатор устроен так, чтобы такие вводы **не** попадали в синонимы:

- порог опечатки зависит от длины эталона (`min(2, ⌊длина/3⌋)`) — короткий ответ
  не имеет права на правки, иначе `33` оказывается в двух заменах от `6`;
- число против числа никогда не считается опечаткой: другое число — это другой
  ответ.

Оба правила закреплены регрессионными тестами в
`__tests__/scripts/questAnswerInsights.test.ts`. Они падают, если классификатор
начнёт деградировать в «добавь всё частое».

## Как ответ вообще проверяется: два прохода

С 29.08.2026 проверка текстового ответа двухпроходная, и это меняет то, что
редактор обязан выписывать в словарь руками.

**Первый проход — строгое сравнение.** `normalize()` (`utils/questAdapters.ts`)
приводит регистр, пробелы, пунктуацию и `ё`→`е`, после чего ввод сравнивается со
словарём на равенство. Так было всегда.

**Второй проход — словоформа** (`utils/questAnswerMorphology.ts`). Срабатывает
ТОЛЬКО если первый провалился, поэтому отменить уже работающий ответ он не может
— он умеет лишь принять дополнительную форму. Правило узкое:

- слова совпадают до хвоста, оба хвоста — настоящие окончания русского или
  белорусского словоизменения (`снаряд` ↔ `снаряды`, `драконом` ↔ `дракон`);
- отдельным шагом учитывается беглая гласная суффикса `-ок`/`-ец`
  (`щенка` ↔ `щенок`, `осколок` ↔ `осколки`) — там основа расходится и сравнение
  хвостов бессильно;
- каждое слово не короче четырёх букв, общая часть не короче трёх;
- составной ответ сравнивается пословно и только при равном числе слов: каждое
  слово обязано быть формой своего, порядок обязан совпасть.

**Чего второй проход НЕ делает:**

- не сводит числа и числительные словами: `пять` и `пятый` — количество против
  порядка, а `33` не синоним `6`. То же правило, что у классификатора выше;
- не покрывает беглую гласную внутри корня (`орла` / `орел`) и супплетивные
  формы — их по-прежнему пишет редактор;
- не живёт в `normalize()`, и это принципиально: нормализация симметрична и
  применяется до сравнения, поэтому морфология в ней заставила бы словарь
  принимать то, чего в нём нет, без единого следа в данных шага.

**Что это означает для редактора.** Падежи и число выписывать больше не нужно:
словарь с `пули` сам принимает `пуля`, `пулей`, `пулям`. Выписывать по-прежнему
нужно синонимы (`плинфа` и `кирпич` — разные слова), написания, стоящие на
объекте (#1536), и формы с чередованием корня.

**Замеры на момент введения** (прод, 2026-08-29): дыр «множественное без
единственного» закрыто 212 из 212; шагов с непокрытым чередованием основы — 0 из
48; дополнительно принимаемых слов — 1267 пар на 744 шага, то есть 0,07% всех
сочетаний, и выборочная проверка показала только законные формы.

**Как правило защищено от расползания.** Ошибка расширения тихая: игрок, чей
неверный ответ засчитали, об этом не сообщит. Поэтому в репозитории лежит корпус
реальных отказов — `__tests__/fixtures/questRejectedAnswerCorpus.ts`, 83 пары
«шаг + ввод», снятые с прода вместе с паттерном шага. Страж
`__tests__/utils/questRejectedAnswerCorpus.test.ts` падает, если хоть один из
них начнёт приниматься. Его чувствительность измерена, а не предположена:
отключение списка окончаний он ловит (пять вводов), а снижение порога общей
части с трёх до двух — нет, такой пары в корпусе просто не оказалось.

Эту дыру закрывает второй страж —
`__tests__/utils/questAnswerMorphologyBoundaries.test.ts` с фикстурой
`__tests__/fixtures/questMorphologyBoundaryPairs.ts`. Он сторожит числовые
пороги парами настоящих слов, которые формами друг друга не являются:
`стой`/`стая`, `свой`/`свая`, `крой`/`края`. У каждой общая часть ровно две
буквы, а хвосты — валидные окончания, поэтому снижение `MIN_COMMON_PREFIX`
с 3 до 2 их склеивает. Тест проверяет обе стороны: на текущем правиле пара
отклоняется, на ослабленном — принимается; запись, которая ослабление не
ловит, считается ложным спокойствием и роняет прогон.

Почему в фикстуре только один порог — это тоже замер, а не умолчание.
A/B-прогон 2026-08-31 (порог опускается в `utils/questAnswerMorphology.ts`,
прогоняется весь набор стражей) по каждому из трёх:

Прогон один и тот же: `npx jest __tests__/utils/questAnswerMorphology` —
3 сюиты, 31 тест.

| ослабление | краснеет | чем поймано |
| --- | --- | --- |
| `MIN_COMMON_PREFIX` 3 → 2 | 5 из 31 | пары фикстуры `стой`/`стая`, `свой`/`свая`, `крой`/`края` |
| `MIN_WORD_LENGTH` 4 → 3 | 3 из 31 | пара `рот`/`рота` в `questAnswerMorphology.test.ts` |
| `MAX_ENDING_LENGTH` 3 → 4 | 1 из 31 | поведение не меняется вовсе — краснеет только закрепление значения; хвост всё равно обязан лежать в `ENDINGS`, а там нет ничего длиннее трёх букв |

Отдельной записи в фикстуре `MIN_WORD_LENGTH` не требует — его уже держит пара
`рот`/`рота`, — но и утверждать, что порог «ничего не держит», нельзя: держит.
До 2026-08-31 в документе и в шапке фикстуры стояло обратное. Ошибка родилась
из копии списка окончаний внутри теста, где потерялось нулевое окончание — то
самое, ради которого `снаряд` принимается при словаре `снаряды`. Теперь тест
берёт `ENDINGS` из модуля, и такой расход невозможен.

`MAX_ENDING_LENGTH` охраняет не пара, а проверка состава списка: самое длинное
окончание обязано быть не длиннее порога.

Где именно лежит охрана. Блок «границы правила» стоит в
`__tests__/utils/questAnswerMorphology.test.ts` — в тестах самого модуля,
а не только в соседнем файле. Причина конкретная: приёмка 31.08.2026 опустила
`MIN_COMMON_PREFIX` до 2, запустила `npx jest
__tests__/utils/questAnswerMorphology` и получила зелёные 20 из 20 — под этот
шаблон единственный чувствительный страж тогда не попадал из-за имени файла.
Теперь тот же прогон даёт 3 сюиты и краснеет на ослаблении, а имя файла-стража
начинается с имени модуля. Сверх поведения там же закреплены сами значения
порогов: правка константы падает с явным требованием обновить пары.

Почему пороги не сторожатся корпусом. Замер по живой базе 2026-08-30: среди
97 отклонённых попыток `quest_answer_attempt` подходящей пары нет ни одной, а
среди 2451 однословного варианта из 703 словарей нашлись только три, и все
родственные (`змей`/`змий`/`змія`) — принять их друг за друга ошибкой правила
не является. Данных для корпусного контроля порогов в проекте пока нет;
чувствительность корпуса вырастет вместе с трафиком, а до тех пор границу
держит контрактный страж.

## Цикл

1. `npm run quest:insights -- --quest <id> --since 90d` — раз в месяц или после
   волны новых прохождений.
2. Взять шаги из верха списка по трению.
3. Для каждого решить по группе кандидатов: словарь / формулировка / ничего.
4. Правку контента внести штатно (скилл `metravel-quest`, агент
   `quest-editor`), правку словаря — в `answer_pattern` шага.
5. Через окно повторить прогон и сравнить трение того же шага. Если оно не
   упало — правка была не та.

## Разбор конкретного прохождения

Для ссылки вида `/admin/quests/questprogress/<id>/change/` используй
`$metravel-quest-playthrough-reviewer`. Один `QuestProgress` показывает сохранённые
ответы и следующий индекс, но не заменяет append-only журнал
`QuestAnswerAttempt`: старое поле `attempts` может оставаться нулевым даже при
реально отправленных ответах.

Ревьюер сопоставляет прогресс, попытки и актуальный production bundle, а затем
отделяет четыре разных результата:

- правильный наблюдаемый ответ отклонён — кандидат на узкую правку
  `answer_pattern`;
- разные неверные ответы указывают на другую трактовку — кандидат на уточнение
  задания после отдельного подтверждения текстовой правки;
- checker отвергает уже разрешённый вариант — code handoff;
- следующий шаг открыт, но попыток по нему нет — drop-off до отправки ответа,
  причина не доказана и контент автоматически не меняется.

Три неверных ввода одного человека — сигнал для ревью, но не разрешение принять
неверный ответ. Для обобщения нужны другие игроки, независимая проверка ответа
на месте/по источнику или объективное несоответствие `task` и `answer_pattern`.
