# Трение шага: от телеметрии ответов к правке квеста

Рабочий цикл редактора квестов. Инструмент существует, чтобы собранные данные
превращались в конкретную правку контента, — иначе они повторят судьбу
`quest_progress.attempts`, которые лежали в проде с июля и которые до ручного
SQL-разбора никто не прочитал.

## Откуда берутся данные

| слой | что делает | где |
|---|---|---|
| сбор | карточка шага снимает каждую попытку (вердикт, нормализованный ввод, номер попытки, подсказка, время) и кладёт в офлайн-очередь | `utils/questAnswerEvaluation.ts`, `utils/questAnswerTelemetry.ts` (#1276) |
| хранение | append-only таблица `quest_answer_attempt` + staff-агрегат | backend `POST /api/quest-answer-attempts/bulk/`, `GET /api/quests/{id}/answer-stats/` (#1275) |
| применение | этот отчёт | `npm run quest:insights` (#1278) |

Сырой ввод хранится **только** для закрытых типов ответа
(`exact`, `exact_any`, `range`, `approx`, `any_number`). Для `any_text` / `any`
(свободная рефлексия вида «что тебе запомнилось на набережной») не сохраняется
ни на сервере, ни на клиенте: у таких шагов в отчёте есть счётчики трения, но
колонка отклонённых вводов пуста. Это не баг отчёта.

## Как запустить

```bash
npm run quest:insights -- --quest 32 --since 365d
```

| флаг | по умолчанию | зачем |
|---|---|---|
| `--quest <id\|slug>` | — | числовой PK или `quest_id` (`minsk-cipher`) |
| `--since` | `90d` | окно данных |
| `--min-count` | `2` | сколько РАЗНЫХ игроков должны были ввести значение, чтобы оно стало кандидатом |
| `--all` | выкл. | обход всех квестов, сортировка по суммарному трению |
| `--json` | выкл. | машинно-читаемый вывод с теми же числами |

Staff-токен берётся из `.secrets/metravel-task-board.env` и никогда не печатается.

Пустое окно — это не результат: скрипт говорит «нет данных за окно» и выходит с
кодом 1, а не рисует таблицу нулей.

## Метрика трения

```
трение = rejected_per_solver + 2 × hint_open_rate + 3 × abandon_rate
```

Веса зафиксированы константой в скрипте: бросивший игрок дороже открытой
подсказки, подсказка дороже лишней попытки. Без весов шаг с десятком мелких
опечаток обгонял бы шаг, на котором квест просто заканчивают.

## Как читать группы кандидатов

Отчёт раскладывает отклонённые вводы на три группы — и решение по каждой разное:

- **похоже на синоним** — та же сущность другими буквами (`шест` вместо
  `шесть`, `папоротника` вместо `папоротник`). Решение: добавить вариант в
  `answer_pattern` шага.
- **фактически другой ответ** — игрок понял задание иначе, чем задумано.
  Решение: **переписать формулировку задания**, а не расширять словарь.
- **мусор** — заглушки (`хз`, `ааааа`). Решение: ничего.

### Почему нет автоприменения

На quest 32, шаг `3-pobeda` (правильный ответ `6`) самый частый отклонённый ввод
— `33`: игроки складывают цифры даты и не сворачивают сумму. По частоте это
идеальный кандидат в словарь, а по смыслу — нерешённая задача. Добавить `33` в
`answer_pattern` значит засчитывать неверный ответ.

Поэтому классификатор устроен так, чтобы такие вводы **не** попадали в синонимы:

- порог опечатки зависит от длины эталона (`min(2, ⌊длина/3⌋)`) — короткий ответ
  не имеет права на правки, иначе `33` оказывается в двух заменах от `6`;
- число против числа никогда не считается опечаткой: другое число — это другой
  ответ.

Оба правила закреплены регрессионными тестами в
`__tests__/scripts/questAnswerInsights.test.ts`. Они падают, если классификатор
начнёт деградировать в «добавь всё частое».

## Цикл

1. `npm run quest:insights -- --quest <id> --since 90d` — раз в месяц или после
   волны новых прохождений.
2. Взять шаги из верха списка по трению.
3. Для каждого решить по группе кандидатов: словарь / формулировка / ничего.
4. Правку контента внести штатно (скилл `metravel-quest`, агент
   `quest-editor`), правку словаря — в `answer_pattern` шага.
5. Через окно повторить прогон и сравнить трение того же шага. Если оно не
   упало — правка была не та.

## Разбор конкретного прохождения

Для ссылки вида `/admin/quests/questprogress/<id>/change/` используй
`$metravel-quest-playthrough-reviewer`. Один `QuestProgress` показывает сохранённые
ответы и следующий индекс, но не заменяет append-only журнал
`QuestAnswerAttempt`: старое поле `attempts` может оставаться нулевым даже при
реально отправленных ответах.

Ревьюер сопоставляет прогресс, попытки и актуальный production bundle, а затем
отделяет четыре разных результата:

- правильный наблюдаемый ответ отклонён — кандидат на узкую правку
  `answer_pattern`;
- разные неверные ответы указывают на другую трактовку — кандидат на уточнение
  задания после отдельного подтверждения текстовой правки;
- checker отвергает уже разрешённый вариант — code handoff;
- следующий шаг открыт, но попыток по нему нет — drop-off до отправки ответа,
  причина не доказана и контент автоматически не меняется.

Три неверных ввода одного человека — сигнал для ревью, но не разрешение принять
неверный ответ. Для обобщения нужны другие игроки, независимая проверка ответа
на месте/по источнику или объективное несоответствие `task` и `answer_pattern`.
