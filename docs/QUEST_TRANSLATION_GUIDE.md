# Перевод квестов: стайл-гайд, глоссарий и конвейер

Правила перевода квестов metravel.by с русского на языки приложения и порядок
работы конвейера `quest:translate` (#2199, серия QUEST-L10N). Архитектура —
`openspec/changes/add-quest-content-localization/design.md`, решение D7.

Читают: агент `quest-translator` (перевод и смысловая проверка) и тот, кто ведёт
пачку перевода. Набор целевых языков задаёт `i18n/config.ts`; русский — источник
и через этот конвейер не пишется.

## Как устроен конвейер

Скрипт текст не переводит. Он готовит задание, проверяет результат и пишет его
в базу; переводит и выносит смысловой вердикт агент. Источник правды — база:
файлы лежат в игнорируемом `.codex-temp/quest-translations/<locale>/`.

| шаг | команда | результат |
| --- | --- | --- |
| что переводить | `npm run quest:translate -- next --count 10` | квесты без полного перевода и города без названия на локали |
| название города | `npm run quest:translate -- city-name --city <id> --locale <код> --name <название>` | название города на локали |
| задание | `npm run quest:translate -- prepare --quest <id> --locale <код>` | `<id>.task.json` |
| перевод | агент `quest-translator` по `<id>.task.json` | `<id>.json` |
| структурные проверки | `npm run quest:translate -- check --quest <id> --locale <код>` | отчёт по шагам, `<id>.review-task.json` |
| смысловая проверка | новый экземпляр `quest-translator` по `<id>.review-task.json` | `<id>.review.json` |
| запись | `npm run quest:translate -- upload --quest <id> --locale <код> [--publish]` | черновик или публикация |
| волна | `npm run quest:translate -- sweep <id>… \| --from-next <n> [--json]` | строка на каждую пару «квест + локаль»; готовые пары публикуются |
| сводка | `npm run quest:translations:status -- [--locale <код>]` | published / draft / missing / stale + finale_missing / finale_stale |

Правила конвейера:

- `upload` без `--publish` пишет черновик: игроки его не видят. `--publish`
  проходит только при зелёных структурных проверках и зелёном вердикте смысловой
  проверки по каждому шагу. Частично квест не публикуется.
- Вердикт привязан к содержимому перевода и к русскому источнику из задания:
  правка файла после проверки или новый `prepare` по изменившемуся источнику
  делают его недействительным, смысловую проверку нужно повторить.
- Черновик поверх опубликованного перевода пишется только с `--unpublish`:
  игроки при этом возвращаются на русский текст.
- Повторный `prepare` опубликованного квеста даёт задание только на недостающие
  и устаревшие шаги; остальные копируются из принятого перевода без изменений.
- Шаги с ручным переводом (`origin: human`) не переводятся и не перезаписываются
  без `--force`.
- `next` и `sweep --from-next` выбирают также опубликованные пары с актуальными
  шагами, если status API сообщает `finale: missing` или `finale: stale`. Причина
  видна в списке (`published, finale missing/stale`). `none`, `ok` и отсутствие
  поля на старом сервере сохраняют прежнюю полноту. `status` считает
  `finale_missing`/`finale_stale` отдельно, не меняя published/draft и счётчики шагов.
- Порядок `next` — по числу стартов из `npm run quest:funnel` (топ за 90 дней),
  дальше по каталогу. Если воронка недоступна, порядок каталожный — это видно в
  выводе.
- Ошибку русского текста переводом не исправляют: её оформляют отдельной
  карточкой, перевод следует источнику.

### Волна: `sweep`

Пачка «10 квестов × 4 локали» — это 40 пар, и `check` с `upload` по одной паре
здесь не масштабируются: оператор гонял их по 40 раз и вёл учёт состояний сам.
`sweep` принимает список `quest_id` (аргументами либо `--from-next <n>` — первые
`n` квестов выборки `next`, с тем же `--order`) и проходит каждую пару «квест +
целевая локаль»:

| состояние | что значит | что дальше |
| --- | --- | --- |
| `no_task` | нет `<id>.task.json` (а полного опубликованного перевода на сервере нет) либо квест правили после `prepare` и задание относится к прежнему тексту | `prepare` |
| `awaiting_translation` | задание есть, `<id>.json` нет | `quest-translator` по заданию |
| `struct_fail` | структурные проверки красные либо `<id>.json` или `<id>.review.json` — не JSON (причины — в строке, полностью — в `--json`) | вернуть переводчику; битый вердикт — повторить смысловую проверку |
| `needs_review` | структурные зелёные, а вердикта нет либо он вынесен по другой версии | `quest-translator` по `<id>.review-task.json` |
| `review_refused` | вердикт по этой версии — с отказом (причины в строке) | вернуть переводчику |
| `upload_failed` | сервер отклонил публикацию (причина сервера в строке) | по причине |
| `error` | пара не дошла до вердикта: сервер не отдал источник или перевод, битый `<id>.task.json` | по причине; повтор волны безопасен |
| `published` | опубликован этой волной либо уже лежал на сервере в этом же виде | ничего |

- Пара публикуется только при зелёных структурных и смысловой проверках — тот
  же гейт, что у `upload --publish`, и та же запись.
- Старый вердикт — не отказ. После правки файла или `prepare --force` старый
  `<id>.review.json` остаётся на месте и относится к другой версии: `sweep`
  показывает такую пару как `needs_review`, а `<id>.review-task.json` уже
  пересобран под новую версию.
- Пропуск по серверу — по содержимому, а не по одному статусу. Если сервер уже
  показывает опубликованный перевод, совпадающий с файлом (ручные шаги сервера
  при сравнении сохраняются, как и при записи), пара помечается `published` без
  проверок и записи. После повторного перевода файл отличается, и пара снова идёт
  через проверки — повторный `prepare --force` не теряется. Пара без задания с
  полным опубликованным переводом на сервере — тоже `published`: `prepare` на ней
  задания не создаёт. Перевод с устаревшими или недостающими шагами (`stale` /
  `missing` в статусе) при том же тексте записывается заново: так сервер узнаёт,
  что его проверили по новому источнику.
- Задание сверяется с текущим русским источником (один запрос на квест) ещё до
  ожидания переводчика: если квест правили после `prepare`, перевод и вердикт
  относятся к прежнему тексту, и пара показывается как `no_task` — запись
  отметила бы старый перевод на сервере как актуальный. Если при этом сервер
  уже считает перевод полным и актуальным, пара — `published`: `prepare` на ней
  задания не создаст, а повторный перевод открывает `prepare --force`.
- Свежесть включает границы `range`, цель и допуск `approx`, минимальную длину
  `any_text`, даже если текст и тип ответа не менялись. Старое задание без
  `answer_rule_parameters` у этих типов требует нового `prepare`. Прямой
  `upload` также сверяет текущий источник до записи; устаревшее задание не
  публикуется обходом `sweep`.
- Ненулевой выход дают отказы: `struct_fail`, `review_refused`,
  `upload_failed`, `error`. Состояния ожидания (`no_task`, `awaiting_translation`,
  `needs_review`) — норма волны. Пустая выборка `--from-next` — тоже ненулевой
  выход (контракт ops CLI), а не зелёный отчёт.
- `--json` — тот же отчёт для скриптов: `quests`, `pairs[]` со `status` и полным
  `details`, `summary` по состояниям, `failed`.

## Стиль

- **Обращение на «ты»**, как в источнике: `be` — «ты», `uk` — «ти», `pl` —
  формы 2-го лица единственного числа без «Pan/Pani», `en` — «you». Рассказчик —
  проводник, который идёт рядом; тон живой, без канцелярита и без панибратства.
- **Перевод, а не пересказ.** Абзацы, порядок фактов и шутки сохраняются; факты
  не добавляются и не убираются. Допуск длины шага — от 0,6 до 1,6 длины
  источника.
- **Естественный язык локали.** Кальки с русского порядка слов и русские
  фразеологизмы заменяются принятыми в языке оборотами. Русских слов и букв в
  тексте перевода нет: для `be` это «и», «щ», «ъ», для `uk` — «ы», «э», «ъ», «ё»,
  для `pl` и `en` — любая кириллица. Исключение — цитата в кавычках (см. ниже).
- **Числа — цифрами, как в источнике.** Каждое число, год и URL источника обязаны
  остаться в том же шаге. Время — в 24-часовом формате (`10:00–18:00`), валюты и
  единицы не пересчитываются (`35 PLN`, `82 метра` → `82 m`).
- **Названия кнопок приложения** берутся из `ui_labels` задания — это настоящие
  подписи интерфейса на языке перевода. Своего варианта не придумывай. В
  `ui_labels` всегда есть «Начать квест», «Далее», «Проверить ответ», «Пропустить» и «Подсказка», а
  кнопки, которые квест называет в «ёлочках», добавляются по тексту.
- **Термины** — по глоссарию ниже и по `glossary` задания; **имена и названия
  мест**, уже принятые в переводах других квестов города, — по `accepted_names`.
  Одно имя пишется одинаково во всех шагах квеста.

## Топонимы и надписи «как на табличке»

Игрок стоит на месте и сверяет текст с тем, что видит. Отсюда правило:

- **Надпись, которую игрок читает на месте** (табличка, вывеска, памятная доска,
  название на фасаде), не переводится и не транслитерируется: она стоит в
  оригинале и в кавычках — `«Brama Floriańska»`, `„Здесь жил…”`. Годятся
  кавычки, принятые в языке перевода: `« »`, `„ ”`, `“ ”`. Пояснение-перевод
  можно дать рядом в скобках.
- **Название места в рассказе** — в принятой на языке перевода форме: `Kraków`
  для `pl`, `Kraków` или `Krakow` для `en`, «Кракаў» для `be`, «Краків» для `uk`.
  Объект без устоявшегося перевода называется местным именем, как на карте
  города (`Sukiennice`, `Barbakan`); для `be`/`uk` — принятой транслитерацией.
- **Оригинал в другой письменности — только в кавычках.** Кириллица в польском
  или английском тексте вне кавычек считается непереведённым куском и не пройдёт
  проверку.

## Варианты ответа

`answer_variants` заполняется только у шагов с типом ответа `exact` и
`exact_any`; у остальных типов (`any`, `any_text`, `range`, `approx`) это пустой
массив. Русские варианты источника сервер добавляет к вариантам перевода сам —
переносить их в перевод не нужно.

Главный вопрос по каждому шагу: **игрок это читает или называет сам?**

- **Читает на месте** (слово с таблички, имя на памятнике, название улицы) —
  вариант остаётся в оригинале. Для `pl` и `en` к кириллической надписи
  добавляется латинская запись, которую наберёт игрок без русской раскладки
  (`Купала` → `Kupala`, `Kupała`).
- **Называет сам** (что изображено, сколько, какого цвета, какое животное) —
  вариант переводится, и к нему добавляются формы, которые игрок реально
  наберёт: синонимы, единственное и множественное число, падежи для `be`, `uk`,
  `pl`. Для `pl` — запись с диакритикой и без (`orzeł`, `orzel`).
- Хотя бы один вариант обязан быть на языке перевода. Число вариантов — того же
  порядка, что в источнике: не один и не тридцать.
- Задание в переводе обязано вести к этим вариантам: если источник просит
  «назови одним словом», перевод просит о том же.

## Подсказка

Подсказка направляет взгляд и ответа не содержит. Ни один вариант ответа не
должен встречаться в переведённой подсказке словом или фразой. Если так устроен
сам русский источник — это ошибка источника, перевод ему следует, а проверка об
этом сообщает.

## Форма файла перевода

Файл `<quest_id>.json` — тело запроса `PUT /api/quests/{id}/translations/{locale}/`:

- `title`, `status: "draft"`, `finale: { "text": … }` (или `null`, если у
  источника финала нет), `steps[]`;
- в каждом шаге: `step_id` — **число** из `source.steps[].step_id` задания (не
  текстовый slug), `title`, `location`, `story`, `task`, `hint`,
  `answer_variants`, `poi_opening_hours`, `poi_ticket_price`, `origin: "machine"`;
- вступление квеста — такой же шаг (`is_intro` в задании), его тоже переводят;
- пустое в источнике поле остаётся пустой строкой; `title`, `story` и `task`
  пустыми быть не могут.

Массив `checks` в файл дописывает `check` — руками его не заполняют.

## Структурные проверки

`check` работает без сети по снимку источника из задания и проверяет:

| проверка | что значит отказ |
| --- | --- |
| `shape` | файл не в форме тела запроса |
| `step_set` | шаг пропущен, лишний или повторяется |
| `required_fields` | пустое обязательное поле либо поле, непустое в источнике |
| `finale` | финал потерян или появился без источника |
| `script` | в тексте вне кавычек остались буквы другого языка |
| `numbers`, `urls` | потеряно число, год или ссылка источника |
| `length_ratio` | перевод короче 0,6 или длиннее 1,6 длины источника |
| `answer_variants` | нет варианта на языке перевода либо варианты у типа без списка |
| `hint_leak` | подсказка выдаёт ответ |
| `kept_steps` | изменён шаг, который не входил в задание |
| `origin` | переведённый шаг помечен не `machine` (черновик тоже не пишется) |
| `semantic` | отказ или отсутствие вердикта смысловой проверки |

## Смысловая проверка

Проверяющий — отдельный запуск агента, который перевод не делал. Он получает
`<quest_id>.review-task.json` (источник и перевод по шагам, `accepted_answers` —
ответы, которые примет сервер; у шагов без списка вариантов принимаемый ответ
описан в `accepted_answers` и строке `answer_rule`, а структурированные параметры
переданы отдельно в `answer_rule_parameters`: «целое число от 6 до 8», «число около 50.5,
допуск ±0.5») и по каждому шагу решает:

1. **Ответ достижим.** Игрок, читающий только перевод задания и подсказки и
   стоящий на месте, придёт к одному из `accepted_answers` (у числового шага — к
   числу по `answer_rule`), причём наберёт его на языке перевода.
2. **Смысл сохранён.** История и задание говорят то же, что источник; надписи
   «как на табличке» не переведены; подсказка не выдаёт ответ.

Вердикт пишется в `<quest_id>.review.json`:
`{ "kind": "quest-translation-review", "translation_sha256": "<из задания>",
"verdicts": [{ "step_id": <число>, "ok": true|false, "detail": "…" }] }`.
Запись с `"step_id": null` — вердикт по названию квеста и финалу. Проверяющий
перевод не правит: отказ возвращает шаг переводчику на одну повторную попытку.
